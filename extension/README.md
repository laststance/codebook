## Set up editor AI chat

The same VSIX includes `skills/codebook/SKILL.md` with its version in the skill frontmatter. VS Code registers it through `contributes.chatSkills`. Cursor's setup command installs that skill to `~/.cursor/skills/codebook/SKILL.md`, with one difference from the packaged bytes: the placeholder `{{CODEBOOK_PUBLISHER_PATH}}` is replaced by the path of this installation's Wiki publisher (`skills/codebook/publish-wiki.mjs`), since a skill copied out of the extension cannot find it beside itself. It installs only when the target is absent or an existing directory is empty, or updates a skill whose file identity and bytes still match Codebook's private ownership receipt. The VSIX manifest records the packaged file's SHA-256. A pre-existing nonempty unowned directory, later manual edit, symlink or mismatched receipt is preserved and reported instead of overwritten.

1. Install the **same identified** preview VSIX in the editor being used, then open the intended trusted local Git repository in a **new** dedicated work window. If that repository was open while updating the VSIX, save its work, close only that work window, and reopen the repository in a new window. Keep other work windows and files intact.
2. Run **Codebook: Set Up AI Chat** in that window. VS Code starts its workspace-local server and advertises it through its MCP provider. Cursor installs the bundled user skill and registers a local stdio bridge for this window's authenticated MCP instance. To wake Cursor's MCP catalog after dynamic registration, setup updates only the modification time of an existing nonempty `~/.cursor/mcp.json`, preserving its bytes; if absent, it creates a private `0600` file containing `{"mcpServers":{}}` and records that exact file's identity in private extension storage. An existing empty file is preserved and reported for inspection before retrying setup. It does not add a static Codebook server or place a credential in the skill, MCP configuration or chat.
   For the tested VS Code 1.139.1 / Copilot 0.67.0 client, configure [inline image transfer](#copilot-image-transfer) before a runtime question.
3. In Cursor, check **Customize > MCPs** for the connected Codebook entry with 16 tools and 6 resources before chatting. Setup records a registration request; its notification alone does not prove Agent has those tools. If the entry is absent, save and close only the dedicated work window, reopen this repository in a new window, and recheck; run setup again if the extension reports a failed reconnect. Then open a new chat in a **Local** session of Copilot Chat (VS Code; a new chat in the Copilot harness, which VS Code may open by default, cannot reach Codebook: it asks to authenticate the Codebook MCP server and finds no Codebook tool) or an Agent chat (Cursor), choose `/codebook` from the slash list, and ask a natural source/runtime question. If the skill is not visible in Cursor, reopen that dedicated window and use the same workspace. Check that the AI's first Codebook call is `codebook_status` for this repository. A general source explanation without Codebook calls is not runtime evidence. If the chat cannot open a returned `codebook://` MCP resource URI, it should use `codebook_read_resource` with that exact URI; this reads the same guarded help, run, manifest, snapshot, recording or image content through a tool.

   `codebook_status.build.dirty` reports whether the packaged Codebook extension source differed from its recorded revision. `workspaceGitStatus: not-inspected` means that status call did not check the selected repository for uncommitted changes; confirm that separately before describing its Git state.

4. To remove a Codebook-owned Cursor user skill, run **Codebook: Remove Managed Cursor Skill** and confirm the shared-user-skill warning. This also retires the empty `~/.cursor/mcp.json` only when Codebook created and receipted that exact unchanged file. A pre-existing, edited, replaced, symlinked or older unreceipted config stays in place; removal does not erase other MCP entries. **Codebook: Restore Managed Cursor Skill** repeats setup and creates a new receipted empty config only if none exists. If another skill is present under the name `codebook`, Codebook will not replace it: the refusal names its folder, and that folder is yours to keep. Rename that folder to keep the skill beside Codebook's, or move it elsewhere, then run **Codebook: Set Up AI Chat** again; as long as it stays where it is, Codebook installs no skill. A skill file that was edited or replaced after setup is left alone too, as long as it is there: delete or rename that file, then run the command again; setup then installs Codebook's skill again, and the removal finishes. A previous owned skill version and an explicitly retired empty config are retained privately during managed changes.

A window that refreshes the Cursor MCP catalog while another window holds the catalog's lock (windows that restart together all refresh it at once) asks for the lock again up to 20 times, after a short random pause each time, before it reports the lock.

A Cursor setup/update/removal that an editor or process crash interrupted leaves its `writer.lock` behind. A lock whose process is gone on this machine is taken over: the next setup, update or removal removes it by itself, one window at a time, and resumes the journal. The lock records its writer's process id and when that process began, the host name, two digests that stand for the machine (of the host name, and of the editor's machine id where the window has one), the boot and, in a local window, the editor's machine id. A window of this build judges a lock that names this machine by the start of its writer's process: the lock counts as left behind when no process has its process id any more, when the process that has that id now began at another time (the id went to another process), or, on Linux and macOS, when the lock names another boot of the computer than the running one. A correction of the clock changes none of this. A lock without a process start (written by 0.2.29.0, or by a window that could not read its own start) is judged as 0.2.29.0 judged it, by its process id and its boot. A lock that was created and stayed empty for 10 seconds counts as left behind too. A lock stays when its writer may still be alive: a process that still runs, a lock written on another host (a home directory shared between machines), a lock written by an editor of another system of this computer (a Windows window and a WSL window that reach the same file: they share the host name, and a process id of one names another process, or none, in the other), or a file without a readable owner record. [What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits. The operation then fails with `Learning storage is locked by another writer or an interrupted session (lock file: <path>). No data changed; retry after resolving the lock.`, where `<path>` is the lock file. For such a lock the manual steps remain: preserve the skill/config and their private recovery records. Save open work, close every window using that Cursor profile, and inspect the named file, `User/globalStorage/laststance.codebook/cursor-skill/writer.lock` or `User/globalStorage/laststance.codebook/cursor-mcp-catalog/writer.lock` under that profile's user-data directory (the default macOS profile is under `~/Library/Application Support/Cursor/`). Confirm on the host the lock names that the process with its `pid` has exited (Activity Monitor on macOS); if the process is live, missing from the file or uncertain, leave the lock untouched. With the profile closed and that process confirmed gone, **move** `writer.lock` to a distinct retained name in the same private directory, then reopen the intended workspace and run **Codebook: Set Up AI Chat** to resume either journal. Keep the moved lock for diagnosis. Do not delete a pending or removal record, a retained file or another user's skill/config on your own to force setup through. The one exception is a record that a refusal names: where Codebook can neither finish nor undo an interrupted step by itself, or cannot read a record, the refusal names what to delete and ends with how to start over, for example `To start over, delete <record path>, then run Codebook: Set Up AI Chat again.` If catalog cleanup alone failed after skill removal, the warning leads with the cause and ends `The managed Cursor skill itself was removed; Codebook left the Cursor MCP config in place and deleted no unverified file. When the cause above is resolved, run Codebook: Remove Managed Cursor Skill again: it goes on with the config.` Resolve that cause, then run **Codebook: Remove Managed Cursor Skill** again: it retires the empty config Codebook created and leaves an existing or changed config in place.

**Cursor setup needs a file system with hard links.** Codebook puts its Cursor skill (`~/.cursor/skills/codebook/SKILL.md`) and the empty `~/.cursor/mcp.json` it creates in place with a hard link, because that is the one call that never replaces a file that is already there. On a home folder whose file system has no hard links (exFAT, FAT, some network shares) **Codebook: Set Up AI Chat** cannot finish in Cursor. It ends with a sentence that names the path and the file system's code, for example "Cursor skill could not be installed: the file system refused to put Codebook's new file in place as <path> (EPERM). No existing file was changed. Check that this folder allows new files and hard links, then run Codebook: Set Up AI Chat again.", and a setup that had no skill of Codebook's to replace changes no file. An update of a skill Codebook installed earlier has moved that skill aside before the link is tried; when the link is refused then, the previous skill stays under the name it was moved to, and the sentence says `Codebook's previous skill is kept as <kept path>; move it back to <path> to go on using it.` where the other says `No existing file was changed.` Codebook does not place the file another way. VS Code installs no such file and is not affected.

**Cursor setup does not go below a link.** When `~/.cursor`, `~/.cursor/skills` or `~/.cursor/skills/codebook` is a link (a home folder whose settings are linked from elsewhere), Codebook refuses the setup, the reconnect and the removal, and leaves the link and what it points to as they are. The refusal names the path and the step, for example `Codebook will not follow a non-directory skill path: /home/user/.cursor/skills. That path is a link, and Codebook leaves what it points to as it is. Put the folder it points to in the link's place, or remove the link, then run Codebook: Set Up AI Chat again.` Either step ends the link at `~/.cursor` and at `~/.cursor/skills`. At `~/.cursor/skills/codebook` the step reads `Remove the link or give it another name`, because what that link points to may be a skill of your own.

## Save learning replay

During a Codebook explanation, the editor's bottom status bar shows **Recording explanation · Save learning replay**. Clicking it (or running **Codebook: Save Learning Replay**) finishes that Codebook run and waits for the saved recording and matching source/explanation context. It does not repeat application inputs or mark anything understood.

- **Saving learning…**: finalization is pending; repeated clicks share the same operation.
- **Learning saved · Open replay**: the saved evidence includes the summary, sequence and captured debugger history. Click to open that saved replay.
- **Learning partially saved · Open replay**: available evidence is retained. The tooltip identifies missing summary/history or incomplete execution/capture evidence; inspect the retained replay before relying on it.
- **Learning save failed · Retry**: completion was not verified. The tooltip reports the failure; retry after resolving it. Existing saved material remains retained.

A `chrome-extension` run saves the same way and is saved as an **Extension replay** (see **Explain a Chrome extension**). The status bar remains available while reading standard chat or native source/debugger panes. New agent annotations invalidate the earlier saved label until saved again. This development implementation still needs installed-host validation in both editors; its unit tests do not establish full product acceptance.

### Test replays

A Vitest test run that the chat explained (the `node-test` profile) is saved the same way, as a **test replay**: its test output, the executed source and the native debugger's recorded values and stack at each stop; it has no application video. A test history's events list is lean (each entry's sequence, source path, line and hash, facts, output text or result code, never the executed source text), and one entry's full detail, a stop's debugger snapshot included, is its own resource, so a test of a large file can be read and saved. Its status bar item reads:

- No item while Codebook checks the run's article, files, hashes and Vitest; a run these checks refuse ends with its `error` and records nothing.
- **Preparing the test run…** once those checks have passed and until the run records its first stop; there is nothing to save yet. Running **Codebook: Save Learning Replay** then does nothing but say `Nothing to save yet: the test run has not reached its first stop.`, and the run keeps preparing.
- `Recording explanation · stop <n> of <m> · Save learning replay` while the run records. Saving before the test's result asks first (`Saving ends the test run before its result (<n> of <m> stops reached). Save now?`), because it ends the run.
- **Recording finished · Save learning replay** once the run has ended: Save reads the sealed history and the chat's learning material.
- **Learning saved · Open replay** when the test passed, every stop's recorded debugger state verifies, and the learning material explains every stop and the result.
- **Learning partially saved · Open replay** otherwise. The tooltip names the result and every missing part, and a notification says what to ask the chat for (a missing explanation) or that only a new test run records it (missing capture). A failing test's replay is saved too: it holds the failing run.
- A test run that ends before it records any output, stop or result leaves no test replay: it is not listed in Saved studies and takes no place of the saved study limit. A read error that a retry can clear (a busy or locked file, too many open files) shows a replay as unavailable only until the next refresh. Codebook runs a Vitest only from inside the repository; a `node_modules/vitest` that links outside it is named as such in `codebook_status` and refuses the start. A history sealed with no entry is removed when it seals, also when a list or a count meets one that an earlier version sealed; a history that holds a saved learning material or understanding marks is kept, and so is one whose seal records entries but whose journal was lost: a status call or a list never removes it.
- Saved studies in a second editor window of the same workspace lists a test replay that another live window is still recording as `recording`, not interrupted, and refreshes it by reading only what was appended; once the recording window seals it, the window shows the sealed status, and a replay whose recording window crashed reads as interrupted, with no verified final seal. A history that is being recorded carries a small writer record (`writer.json`) in its folder, which is removed when the history seals; earlier versions ignore it, a record that could not be read for a moment is judged again within 5 seconds, and test histories, learning materials and reader positions open in both directions unchanged.
- A stop before the first stop reads stopped, not refused. A run stopped before its history began, or whose history sealed with no entry, offers no `read-history`. After a stop whose release failed, the run offers only `stop`, and a continue is refused with `STALE_PAUSE`.
- **Learning save failed · Retry** when stopping the run did not finish (Retry stops it again) or the sealed history could not be read back (Retry reads it again; the test does not run again), and **Learning save failed · Open retained history** when the history could not be sealed (the recorded part opens read-only). Each tooltip names the cause; the details are in **Output › Codebook**.

The bundled skill (since 1.0.48) routes a question about a test, or about library behavior a test exercises, to the `node-test` profile, and the chat explains each test stop in the chat. A value the chat asks for at a test stop is also read when it is a name the stopped file imports (`revalidatePath.mock.calls.length` of a mocked `next/cache`, for example), through the module Vitest binds it to, as the export its import declaration names: an alias reads the module's original export and a default import its default export, each from that declaration's own module, never from another module that happens to export the same name; a namespace import, a name the file does not import, and an import whose module the stop cannot see stay unavailable rather than guessed. A step that only a Proxy's `[[Target]]` holds (a library's tracked query result, for example) is recorded under the path naming that hop (`state.[[Target]].status` for the declared `state.status`), because Codebook never runs the Proxy's get trap and the program may read another value than its target holds; the declared path is named among the stop's limitations, so the history seals partial, and a Proxy whose target lacks the step leaves that value unavailable. #### Tests inside a workspace package

A test runs the way its package's own `vitest` command would: in its **Vitest root**, the nearest folder above the test that holds a Vitest or Vite config (`vitest.config.*` or `vite.config.*`), with that config and the Vitest 4 or later that Node resolves from there (the package's own, or one hoisted to a folder above it inside the repository), unless the repository root's own config already selects the test exactly once, which keeps it running from the root as before. That root claim is made only when the root's own Vitest is usable (4 or later, with its program), the root holds no folder or link out of the repository named like a config, and the test's path does not start with `-`; otherwise the test runs in its Vitest root and the manifest's `rootClaim` reads `not-applicable`. When the root listing selects the test zero times or under several projects, or Vitest itself ends that listing with an error or no readable list, the test runs in its Vitest root (`rootClaim` `not-selected`, `several-projects` or `listing-failed`); a listing Codebook could not run (its own folder, the spawn or a file read failed), a stopped start and a passed preparation deadline refuse the start instead. A test with no config above it, up to the repository root, runs from the root. Codebook looks for configs only up to the opened folder; a run from the opened folder loads whatever config its Vitest itself finds from there, as running `vitest` in that folder would.

1. Open the repository root (the monorepo, not the package) in VS Code or Cursor. The test's package, or a folder above it, needs Vitest 4 or later in its `node_modules`. Yarn Plug'n'Play installs have no `node_modules/vitest` and are not supported.
2. Ask `/codebook` about the code a package's test exercises, for example `/codebook explain how QueryCache decides to reuse a query, running its test`.
3. The run's manifest (the run resource's `manifestUri`) names the folder it ran in as `vitestRoot` (`packages/query-core`, or `.` for the root), why (`vitestRootReason`: `nearest-config`, `root-config`, `root-claim` or `no-config`), the root claim's result (`rootClaim`), the config files there (`vitestConfigFiles`) and config-named entries it passed over on the way (`skippedConfigFiles`).
4. Unlike the package's `test` script, the run uses Codebook's fixed environment (`CI=true`, `NODE_ENV=test`, no inherited credentials) and none of the script's own variables or options. Vite and Vitest still load the chosen config and read the Vitest root's `.env*` files for `import.meta.env`, as the package's own `vitest` would. The test runs in whatever environment that config sets (`jsdom` or `happy-dom` included) in Vitest's Node mode (browser mode is not supported): Codebook passes no `--environment`, so a test's environment changes only through that config or the test file's own `// @vitest-environment` comment, as with the package's own `vitest`.
5. Verified on macOS, each run explained, saved and replayed with that environment applied: `jsdom` with Vitest 5 in VS Code (Copilot Chat, GPT-6.1 Terra) and in Cursor (Agent, Grok 4.6 High), `jsdom` with Vitest 4 in VS Code (Copilot Chat), and `happy-dom` with Vitest 5 in VS Code (Copilot Chat). Other combinations are not verified.

#### Terms

- **Learning replay**: a saved explained run that you can replay after it ended; a browser run's holds the application video.
- **Test replay**: the learning replay of a test run: its test output, the executed source and the debugger's recorded stops; no application video.
- **Server replay**: the learning replay of a server run: the recorded request Codebook sent, the server's output, the executed source at each declared stop, the debugger's recorded values and the response; no application video. Opening it never sends the request or starts the server.
- **Study pane**: Codebook's reader beside the editor, with Saved studies, a replay's summary and its controls.
- **Application pane**: the pane that shows the recorded application of a browser replay, or the recorded test output of a test replay. When you seek or Play reaches another moment of a browser replay, the pane keeps the frame on screen while the next one is read and swaps to it at once, so it shows no dark page between moments; only a read that takes longer than one second blanks the pane to its loading line. The recorded-source label of a stop leaves together with the stopped line.
- **Stop**: a place in source where the run paused for the explanation, numbered in the order the run reached it.
- **Saved studies**: the list of saved replays in the Study pane and the Learning summary.

## First LLM Wiki

The **LLM Wiki** is the browser site your editor's AI writes for the whole repository: overview, architecture and module chapters with diagrams, citations into your editor and repository questions. The bundled skill draws the flow diagrams itself: where two conditional arrows join the same two parts, an arrow crosses a row, or arrows between different parts have one midpoint, each label keeps its own place beside its arrow, clear of the other labels and of the parts. It is not the **Repository Wiki** view in Codebook's Activity Bar, which lists repository articles an MCP agent wrote ([Learn this repository](#learn-this-repository)). No runtime MCP connection, debugger or running application is needed.

1. Prerequisites. VS Code: Copilot Chat enabled and signed in. Cursor: the `cursor-agent` CLI installed and signed in (`cursor-agent --version` answers; Codebook looks for `~/.local/bin/cursor-agent`, then `cursor-agent` on the editor's PATH).
2. Open the project folder and press **Generate LLM Wiki** in the **LLM Wiki** view of Codebook's Activity Bar, run **Codebook: Generate LLM Wiki** from the Command Palette, or press **Generate LLM Wiki** in the notice **Open LLM Wiki in Browser** or **Update LLM Wiki** shows in a folder without a Wiki (`Codebook found no LLM Wiki in <folder>.`).
3. Confirm. The confirmation names the folder the Wiki is written to and where the request goes. **Change location** opens the `codebook.wikiOutputDirectory` setting and starts nothing; dismissing it starts nothing either.
4. Wait for `LLM Wiki generated in <folder>.` and press **Open in Browser**. Codebook waits up to 55 minutes.

The chat route works without the command; paste it into Copilot Chat or Cursor Agent:

```text
/codebook Generate the LLM Wiki for this project
```

To write the Wiki elsewhere, set the folder in your settings (a path inside the project is relative to it):

```json
{ "codebook.wikiOutputDirectory": "docs/wiki" }
```

### Generate LLM Wiki

**Codebook: Generate LLM Wiki** writes the first Wiki of a folder that has none, through your editor's agent and the bundled skill's DeepWiki procedure:

- **VS Code.** The generate request goes into a new Copilot Chat session, as an update's does ([LLM Wiki: open and update](#llm-wiki-open-and-update)). The chat asks you to approve its commands and may stop at its request limit and ask you to **Continue**, so keep the Chat view open: a measured first generation needed about 38 approvals. It uses your chat plan. The status bar shows `$(sync~spin) Watching for the LLM Wiki · Stop watching` while Codebook watches for the publish.
- **Cursor.** The request goes to `cursor-agent` with the same flags as an update's, without further prompts; a notification `Generating the LLM Wiki in cursor-agent…` with Cancel shows the run. It uses your Cursor plan. Codebook readies the managed Codebook skill in `~/.cursor/skills/codebook` first, without starting the MCP connection: a missing or outdated managed skill is installed, and a skill of your own or one you edited stays and refuses the generation with its sentence. The model is the one `cursor-agent` is set to use (the `model` of `~/.cursor/cli-config.json`); Codebook does not choose it.
- **Existing Wiki.** Generate never overwrites a Wiki: in a folder that holds a manifest it says `An LLM Wiki already exists in <folder>. Update it instead?` with **Update LLM Wiki**, also when a Wiki was published between its first look and its start. To generate again from scratch, ask the chat `/codebook Generate the LLM Wiki for this project`; the publisher keeps the earlier Wiki beside the new one.
- **Its bound.** A generation runs up to 55 minutes in both editors, the longest measured first generation times 1.5; the time counts while the computer sleeps. A generation that publishes counts as generated even when sources changed meanwhile: the notice then says `LLM Wiki generated in <folder>. <N> source files changed while it was written.` and offers **Update LLM Wiki** first.
- **Stopping it.** **Codebook: Stop LLM Wiki Run** stops this window's generation or update. In VS Code it stops Codebook's watch, not the chat (the status bar's **Stop watching** does the same): the chat may still publish, Codebook waits for it 55 minutes after the watch's end before it starts another generation or update of that Wiki, and a publish of that chat ends the wait. In Cursor it stops the agent. While the run is still starting (its checks, the confirmation, the claim of the Wiki), it says `Codebook is starting an LLM Wiki run in this window. Once it runs, its progress shows and Stop LLM Wiki Run stops it.`; **Open LLM Wiki in Browser** says the same then instead of offering a second generation. A second press of Generate or Update LLM Wiki (or the browser reader's **Update**) during that start joins it and says so once while that start lasts: `Codebook is already starting an LLM Wiki <generation|update> in this window; this press joins it.` A press of **Generate anyway**, **Update anyway** or the offer's **Update LLM Wiki** during that start joins it without its choice and is told once instead: `Codebook is already starting an LLM Wiki <generation|update> in this window, so this choice was not applied. If that start stops for the same reason, choose it again.` In Cursor the start also readies Codebook's skill for up to 30 seconds with the Wiki's marker claimed: **Stop LLM Wiki Run** ends it at once with `The LLM Wiki <generation|update> was cancelled at <time> while Codebook readied the Cursor skill; no agent was started. Press <Generate|Update> LLM Wiki when you want to start again.`, and a step that passes 30 seconds ends it with `Codebook stopped readying the Cursor skill after 30 seconds; no agent was started. Press <Generate|Update> LLM Wiki again, or run Codebook: Set Up AI Chat.`; either way the start leaves the marker (it is removed, or a reservation of another window's stopped watch that **Generate anyway** or **Update anyway** took over is written back as it was, with its own window and its own bound). A window that closes during that step ends it the same way, so the marker is not left to expire. A reservation of another window's stopped watch that this window wrote back stays on disk when the window closes, until its own bound, because that window's chat may still publish; it is written back as that window's own text, so that window still removes it at its bound or when it closes, and a write-back that cannot be made at the close (another window holds the marker's claim at that moment) is tried again for up to 5 seconds. A reservation that is already gone from disk when a refused start ends (its window removed it) is never brought back. A marker a start cannot remove at once is removed on a retry (every 10 seconds for two minutes, [below](#llm-wiki-open-and-update)) instead of standing until its bound. A window that begins to close before a start has reached the skill step starts no check or deployment of the skill: the start ends without an agent and leaves its marker (removed, or a taken-over reservation written back). A step that was stopped may still be writing the skill: a new press of Generate or Update LLM Wiki waits for it to finish before it readies the skill again, so two deployments of the skill never run at once, and Stop LLM Wiki Run and the 30 seconds apply to that wait too; a step that never settles ends that wait at the 30 seconds with `Codebook could not ready the Cursor skill: an earlier Cursor skill step in this window is still running. Reload the window (Developer: Reload Window) to end it, then press <Generate|Update> LLM Wiki again.` (no agent starts, the marker is left as for the 30 seconds). With nothing running, Stop LLM Wiki Run says `No LLM Wiki run is going on in this window.`
- **Output record.** Every generation and update end writes one line to Output › Codebook (**Codebook: Show LLM Wiki Output**): the run's kind, editor, start and end time, how it ended in Codebook's words, the agent's exit code, the cause id of a block that refused a generation's start (the notice names the file in the way and leaves the id out) and the output folder with your home folder shown as `~`. It never holds the agent's reply, its errors or a chat's error text.
- **Buttons of an older notice.** **Generate anyway**, **Update anyway** and the offer's **Update LLM Wiki** wait only for the start whose notice showed them; pressed while another run of the window works, they are told that a run is under way at once and start nothing when it ends.
- **Names.** **Codebook: Open LLM Wiki in Browser** was titled **Open DeepWiki in Browser** before 0.2.45; its command id `codebook.openDeepWiki` is unchanged, so keybindings and scripts keep working. The bundled skill 1.0.50 names it in the reader's offline note.
- **Several windows.** Update every window of a project to this version before you generate: an earlier Codebook reads a generation's marker with an update's 15-minute bounds and may start an update beside a generation that still runs (the publisher still refuses a second publish while one runs). Stop a running generation before you go back to an earlier Codebook.

## LLM Wiki: open and update

**Codebook: Open LLM Wiki in Browser** serves the generated site from a loopback reader in your browser. The reader answers only on this computer: a request whose Host is its own loopback address, or any loopback address the editor has forwarded it to (each stays accepted if the editor forwards it again). A window whose forward goes to another host (a tunnel, a browser-based editor) gets no page, only a 403 that says so. The reader removes the effect of a page's own `referrerpolicy` attributes and `<meta name="referrer">` element, so a Wiki page cannot send the reader's private address to another site. **Update LLM Wiki** (the button in the right rail of that page, or **Codebook: Update LLM Wiki** in the Command Palette) asks the editor agent to regenerate the site. The button asks for confirmation in the editor first; in VS Code the confirmation says where the request goes: `Copilot Chat receives the update request for this project in a new chat; the chat you have open keeps its place in the chat list. A draft you typed into an empty chat is replaced by the request; a draft in a chat with messages stays with that chat.` The command starts at once and asks nothing: its request goes into a new chat in the same way (into the chat the Chat view restores, if that view opens only now) and replaces a draft in an empty chat in the same way; the Chat view shows the chat with the request. When the watch ends and what to do after you refused a step of the chat are in the row **Updating LLM Wiki…** below. The page then shows the run and its result under the button without a reload; the site stays readable the whole time.

A question asked on the page waits with `Asking the editor model… The editor may first ask you to allow Codebook to use it; answer there.` in both editors, because the editor may ask for your consent before its model answers the first question; the page cannot know whether you gave it.

In VS Code the update's request does not go into the chat you are using, with the one exception named below: Codebook reveals the chat, runs the editor's **New Chat** and sends the request into that new chat, so a request of yours that is in progress, waits for a confirmation or is queued is neither stopped nor held back, and the update does not wait behind it. Your chat is not closed: with a request in progress or waiting for a confirmation it goes on in the background, and you return to it from the Chat view's session list (its chat history). The update asks nothing about edits of that chat you have not decided on yet: they stay pending in their chat, with Keep and Undo, and the **Suggested Edits** editor that shows them stays open. Two limits, the first of them that exception. When the Chat view has not been opened in the window yet, it may still be restoring your last chat while New Chat runs: New Chat then does nothing, and the request goes into that restored chat; the confirmation names this case. When the chat you focused last is a chat in an editor tab, the new chat starts in that tab, and the chat that was shown there keeps its place in the chat list. When Codebook sees no sign within those 30 seconds, it leaves its request in the chat and runs none of the chat's commands: the chat's Cancel and its Remove All Queued act on the chat you focused last and on the session it shows, and the editor tells Codebook neither which session that is nor which request is its own, so they could stop or remove a request of yours instead. Your own work elsewhere in the window (a file you open, a command you run) is not taken for a sign. What the update's own steps touch counts whoever does it, because Codebook cannot tell you from the chat there: a file opened in the Wiki's folder, in a folder prepared beside it or in the Codebook skill's folder, a terminal command that names `publish-wiki.mjs` or the Wiki's folder, and a change in the Wiki's folder or in a folder prepared beside it. When the chat's command has not returned by then, the sentence reads `Codebook saw no sign of the update in the editor chat within 30 seconds and left its request in the chat without running any chat command on it, so the request may still be there. Stop or remove it in the Chat view, check that Copilot Chat is enabled and signed in, then retry, with Update anyway if Codebook still waits for that chat.` Codebook then waits for that chat as it does after a stopped watch, for 15 minutes: a retry in that time is answered with the wait and **Update anyway**, not with a second request beside the first. If the chat's command had returned without the chat taking a request, the sentence reads `Codebook saw no sign of the update in the editor chat within 30 seconds and the chat holds no request of it, so no update is running. Check that Copilot Chat is enabled and signed in, then retry.` Every supported VS Code (1.120 and later) has New Chat. An editor without that command, and one in which the reveal of the chat or New Chat fails or does not return within 5 seconds, gets the request in the chat that is open, where it acts like a message you typed: it waits in the queue behind a request in progress, the editor cancels a request that waits for a confirmation, and a draft in the chat's input is replaced. The confirmation says so before the press where the editor lacks the command; where the reveal or New Chat failed, nothing says so before, and the Chat view shows the request in the chat that was open. At the 30 seconds Codebook leaves its request in that chat as well, also where it waits in the queue, and removes none of yours.

The shared-chat sentence depends on whether the chat held the update's request. When the shared chat holds no request of the update, the sentence reads `Codebook saw no sign of the update in the editor chat within 30 seconds and the chat holds no request of it, so no update is running. The chat may be working on another request: wait until it has finished, or check that Copilot Chat is enabled and signed in, then retry.` When the chat may still hold it, it reads `Codebook saw no sign of the update in the editor chat within 30 seconds and left its request in the chat without running any chat command on it, so the request may still be there. Stop or remove it in the Chat view. The chat may be working on another request: wait until it has finished, or check that Copilot Chat is enabled and signed in, then retry, with Update anyway if Codebook still waits for that chat.`

While Codebook watches a VS Code generation or update the right of the status bar shows the entry `$(sync~spin) Watching for the LLM Wiki · Stop watching` (a spinning icon, then the words), for as long as the watch lasts; its tooltip reads `Watching the editor chat for the LLM Wiki. Stop watching stops Codebook’s watch, not the chat.` Pressing the entry is **Stop watching**: it stops Codebook's watch, not the chat. The entry leaves the status bar when the watch ends. The watch shows no notification: the editor stacks its notifications at the lower right of the window, where it shows the Chat view by default, so any other notification would push a notification that lasts the whole watch over the buttons of a step the chat asks you to approve. The status bar lies below every notification, and those buttons stay free. The entry says the same wherever the request went (a new chat, the chat the Chat view restored, or the chat that was open); where it went is said by the confirmation and above, and when the watch ends and what to do after a refused step by the page's running line and the table. Where the Wiki's output folder lies outside the project, the chat asks you to approve each step there (an output inside the project, `codebook.wikiOutputDirectory`, needs none); the confirmation and the page's running line say so, the status bar entry does not.

A sentence about a run that ended without success also says whether the site on disk was kept or replaced. Where a chat or another editor window can still publish after that end (a request Codebook left in the chat at the 30 seconds, a watch of Codebook's that broke off with an error, a start refused because an earlier chat or another window is still updating), it says `Nothing had been replaced by then.` in place of `The last usable site is kept.`, so that a later publish does not make the notice untrue. A watch that broke off reads `Codebook stopped watching the update because of an error (…). The VS Code chat was not stopped and can still publish: let it finish (the Wiki page says when it has), or stop it in the chat.`, and the next update is then answered as after a stopped watch, with **Update anyway**. A finished line gives way to the freshness label above it: **Updated** and **Already current** disappear once the label reads **Source changed · Update available**.

Under the outline in the right rail every page has the entry **Open in VS Code**, or **Open in Cursor** when Cursor serves the page. It opens the page's first cited source at its cited line in that editor and names that file and line under its label. A page opened from disk keeps the entry as it was published: **Open in VS Code**, which opens VS Code, and for a site published by 0.2.29.0 without the file and line.

Before it serves a page, the reader reads the page's tags as a browser reads them and makes inert each address that is no relative path, `#fragment`, `http`, `https` or `mailto` address and not Codebook's own (an editor address that opens a file or calls another extension, `javascript:`, `data:`, `file:`): the attribute's name becomes `data-codebook-unlinked`, so the element and its text stay and a browser follows nothing. A refresh (`<meta http-equiv="refresh">`), a frame's own page (`srcdoc`) and an svg animation of an address are made inert the same way. This holds for a page of any age, also one that a cloned repository carries or one written by hand into the Wiki folder. Codebook's own addresses get the scheme of the editor that serves the page.

The reader prepares each page in a worker thread, so the editor goes on working while a page is read: at most two pages at a time, each within 10 seconds and 512 MB of heap, and at most six pages are read, prepared, waiting for a worker or being sent at once (a worker that is still ending lets one more page wait). An answer of the reader whose browser takes none of it for 30 seconds is ended: a browser that stops reading holds a page in the editor for 30 seconds at most, and one that reads slowly, over a remote window's forwarded port for example, still gets the whole page or image. The reader keeps a file of the Wiki open only while it reads a part of it, not while the browser takes that part, so a slow or stalled browser does not keep an update from moving the Wiki folder. A page it does not prepare is answered with status 503 by a short page, `Page not shown`, with one sentence and a link to the Wiki's overview (the overview's own has no such link):

- `This page is too large for Codebook to prepare for reading. An earlier Codebook may have published a page this large, or its file may have been changed by hand. If you changed it, restore the page or move your change aside, then press Update LLM Wiki; otherwise ask the editor chat to split it into smaller pages and update the Wiki.` for a page file larger than 2 MiB, which is not read; the publisher of this build writes no such page, but one of 0.2.30.0 or earlier could.
- `This page needs more memory than Codebook gives one page to prepare it for reading. Ask the editor chat to split it into smaller pages and update the Wiki; Update LLM Wiki alone renders the same page again.` for a page whose preparation needs more than the 512 MB of heap.
- `Codebook stopped preparing this page after 10 seconds. No page of a Wiki needs that long, so its file may have been changed by hand. Restore the page or move your change aside, then press Update LLM Wiki.` for a page whose preparation passes the 10 seconds.
- `Codebook could not prepare this page for reading. Reload the page; if it is still not shown, press Update LLM Wiki.` for a page whose worker failed.
- `Codebook is preparing as many pages as it can at once, so it did not prepare this one. Reload the page in a moment.` for a page asked for while six pages are read, prepared, waiting or being sent, whose file is not read, and for a page that waited 30 seconds for a worker.

An HTML page asked for as a part of a page (an image, a style sheet, a script, a fetch), and not to be opened as a page or in an inline frame (the browser says which in `Sec-Fetch-Dest`), is refused with `A Wiki page is served only to be opened as a page.` (status 403); a request without that header, from a client that is no browser, is served. A file of the Wiki that is no regular file (a named pipe, a device, a folder) is never opened, a page or any other file: `The Wiki file is no regular file; a pipe, a device or a folder at its path is not served.` (status 403).

The folder is `.codebook/wiki` in the project unless `codebook.wikiOutputDirectory` says otherwise; the status names it. In a workspace you have not trusted, the editor does not use the workspace's own value of `codebook.wikiOutputDirectory` (a cloned repository's `.vscode/settings.json` could name any folder): your user setting, or else `.codebook/wiki`, applies. The status lives in the editor window: after a window reload, reopen the Wiki from the editor. A page opened from disk has no reader behind it and shows an offline note in place of the status. A link or a file on the Wiki's path inside the project, the Wiki folder included, is refused wherever Codebook reads or writes the Wiki. An update does not start when the Wiki folder itself is one (`Update not started (<time>): the Wiki folder itself (<name>) is a link or a file, or leads out of the project, and the publisher refuses anything there but a folder of its own. Replace it with a real folder (if it is a link to your Wiki’s folder, move its files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then press Update LLM Wiki again.`) or when a folder above it is one (`Update not started (<time>): the Wiki folder’s path in the project passes through a link or a file (<path>), and the publisher writes only into the project’s own folders, so nothing was written. Replace it with a real folder (if it is a link to a folder of yours, move that folder’s files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then press Update LLM Wiki again.`). The publisher refuses it too and writes nothing (`The Wiki folder <path> is a link, a file or a folder that leads out of the project. Nothing was written. Replace it with a real folder, or choose an output folder outside the project.` for the Wiki folder itself, and `The Wiki output lies inside the project, but its path passes through a link or an entry that is no folder of the project’s own: <path>. Nothing was written. Replace it with a real folder, or choose an output folder outside the project.` for a folder above it). **Codebook: Open LLM Wiki in Browser** and the Wiki reader read nothing through it (`The Wiki folder <folder> is a link or a file, or leads out of the project. Codebook reads no Wiki through it. Replace it with a real folder (if it is a link to your Wiki’s folder, move its files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then open the Wiki again.`, and for a folder above it `The Wiki folder <folder> lies behind a link or a file in the project (<path>). Codebook reads no Wiki through it. Replace it with a real folder (if it is a link to a folder of yours, move that folder’s files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then open the Wiki again.`; the editor's notice shows the refusal as it is). An output folder outside the project stays your choice, and a link on its path there is followed. One limit: on Windows an output folder whose last name is written as a short name (`WIKI~1`) is taken for no folder of its own and gets the update's sentence of a Wiki folder that is itself a link or a file; write the folder's long name in `codebook.wikiOutputDirectory`.

A Wiki folder you commit to Git must keep the publisher's bytes: mark it `-text` in `.gitattributes` (the line `".codebook/wiki/**" -text`, with your folder's path), so that a checkout with `core.autocrlf`, the default of Git for Windows, keeps its LF line ends. The skill's publisher writes every page with LF line ends only, also when the text of a page held CRLF, so that this way out restores every page. The skill's publisher refuses a Wiki whose files a checkout gave CRLF line ends, with a sentence that names them and the way out: add that line to the `.gitattributes` file in the folder the sentence names (the project's, for a Wiki folder inside it) and commit that file; then, in that folder, run `git rm -r --cached --quiet -- ".codebook/wiki"` and `git checkout HEAD -- ".codebook/wiki"` (with your folder's path from there), which write the folder's committed files again with LF line ends (a change of them that is not committed is lost), and run the step again. The publisher also refuses a manifest that starts with a UTF-8 byte order mark (PowerShell 5.1's `Set-Content -Encoding UTF8` writes one) and says: `Write the file again as UTF-8 without that mark`. It reads `--output=<path>` as it reads `--output <path>`; a separate value that begins with a dash gets its usage.

While an update runs, its window keeps a marker file beside the output folder, `<folder>.update-run.json` (`.codebook/wiki.update-run.json` unless the setting names another folder), so that a second editor window on the same project does not start a second update. That window's start is refused with `Another editor window is updating this Wiki (<editor>, started <time>). Wait for it to finish, then press Update LLM Wiki again.`, or for a generation with `Another editor window is generating this Wiki (<editor>, started <time>). Wait for it to finish, then press Open LLM Wiki in Browser.` Two shorter refusals name no run. `Another editor window is starting an update of this Wiki. Wait a moment and try again.` is shown while another window is writing its marker: a marker file without content, or one that cannot be read and is not dated ahead of the clock, that is younger than 2 seconds. `Another editor window is starting or ending an update of this Wiki. Wait a moment and try again.` is shown while another window holds the claim under which a marker is removed or replaced, and a leftover marker is in the way. A start of the window whose own last run is removing or replacing its marker at that moment (**Update anyway** chosen right after that run ended, for example) is not refused with it: the start waits until that change is made and claims the marker again. A marker file that cannot be read (another program holds it open, as a scanner or an indexer can on Windows, or this user may not read it) may be a running update's marker, so it counts until 61 minutes 30 seconds after its last write, as long as any marker counts (a generation's); once it is 2 seconds old, or when its time lies ahead of the clock, the start is refused with `Another editor window may be updating this Wiki: Codebook cannot read the Wiki’s marker file (<path>), which another program may hold open (as a scanner or an indexer can on Windows) or which this user may not read. Press Update LLM Wiki again once the file can be read; if the file stays as it is, this refusal ends at <time>.`, where `<time>` is the first whole minute after those 61 minutes 30 seconds. The marker usually lies in your project folder, so it holds nothing that names the computer, its host or its user in clear: it records the process id of the window's extension host and when that process began, a random id of the window, the editor, the time the run started, the id of the computer's boot on Linux and macOS, and two digests that stand for the machine. A digest is a pseudonym and no secret: a commit of the file publishes it, and the digest of a common host name can be found by trying names. When the run ends, its window removes the marker; after a stopped VS Code watch the file stays as that window's note that the chat may still publish, and the window removes it later or the next update does. Where the window cannot remove or replace its marker at that moment (another window holds the claim on it, the system refuses the claim or the change, or the marker cannot be read at that moment, as on Windows while a scanner or an indexer holds the file open), it tries again every 10 seconds for two minutes, and once more when it closes; a marker still left after that counts until its run's longest time has passed. A start that ends before its run began (refused, stopped or bounded while Codebook readied the Cursor skill, or ended by the closing window) leaves the marker it claimed the same way, with the same retries.

A marker of a running update that a killed editor left on this machine does not refuse a start: a window of this build judges a marker by the start of its owner's process, so the marker counts as nobody's when that process is gone and also when another process has its process id since, and the next start removes it. A marker whose owner cannot be judged here counts until its run's longest time has passed at the latest: 21 minutes after the run began for Cursor and 21 minutes 30 seconds for VS Code (a generation's marker: 61 minutes and 61 minutes 30 seconds, its 55 minutes in place of the 15) (the 15 minutes of a run, in VS Code after the 30 seconds for the chat's first answer, then 1 minute, then the 5 minutes by which two clocks may differ). That is a marker written on another computer (a project folder shared between machines), in another system or another pid namespace of this computer (a Windows window beside a WSL window, another WSL distribution, a container), where its process id means another process, by a window that could not read its own process start, or by a Linux window that could not read its own pid namespace (such a window also judges no other window's marker by its process). A running update's marker of this computer that names another boot than the running one (on Linux and macOS, which name their boots) is nobody's all the same. A marker of 0.2.29.0 counts that long when a process still has its process id. [What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits.

A stopped VS Code watch's reservation describes a chat that can still publish. If the editor could not store that watch's record, Codebook keeps the reservation when the window closes or reloads. Another window, including the reloaded one, still waits until 15 minutes after the watch ended (55 minutes after a generation's), also when the former extension host's process is gone. Stop that chat, then choose Update anyway if Codebook still waits for it; a publish the reader recognizes ends the wait sooner.

For tools: `GET <reader>/api/update-status` answers the current state as JSON (`Cache-Control: no-store`). `state` is one of `idle`, `running`, `succeeded`, `already-current`, `failed`, `cancelled`, `timed-out` or `conflict`; only `running` is not final. An `already-current` answer carries `addedFilesUnchecked: true` when the folder has no Git repository, so only the indexed sources were compared. Any other method answers `405` with `Allow: GET`.

### The LLM Wiki view

The **LLM Wiki** view in Codebook's Activity Bar shows where the generated site of the opened project stands and the next step; it sits below the **Repository Wiki** view, which lists repository articles, not the generated site. Its rows come and go with the facts they show, in a fixed order, and the tooltip of a row has its full text:

- With no folder open the view says `Open a folder to use the LLM Wiki` with **Open Folder**; in a folder you have not trusted it says `Trust this folder to use the LLM Wiki` with **Manage Workspace Trust**. If the editor has no Manage Workspace Trust command the view points to **Workspaces: Manage Workspace Trust** in the Command Palette (also when the editor's command list cannot be read); if the command fails, the view says it could not open, names that command, and the cause is in **Output › Codebook**.
- The view follows its Wiki folder on disk: creating the folder, or deleting or moving it or any folder above it inside your project (for example `rm -rf .codebook`), refreshes the rows one second after the last change on disk (a burst of changes is one read), and a deleted Wiki brings back the welcome without **Refresh**. A Wiki folder outside the project is watched from its own parent folder only, so deleting that parent shows after **Refresh** or the next time the view is shown (Codebook never watches your home folder or a drive root).
- In a folder with no Wiki and no run the view shows a welcome with a **Generate LLM Wiki** button, what runs it in your editor (Copilot Chat in VS Code, `cursor-agent` in Cursor) and the output folder with a **Change location** link (`The Wiki is written to .codebook/wiki unless the setting codebook.wikiOutputDirectory names another folder.`). A click on the **Output** row opens the same setting.
- **`<folder> Wiki`** is the published Wiki. A click opens it in the browser. Its description is the freshness label of the reader page (`Wiki source current`, `Source changed · Update available`, `Wiki freshness unknown: …`, or `Checking freshness…` while the check runs), and its tooltip names the generation: `Generated from <first 7 characters of the commit> on <date>`, `Generated on <date> (no Git revision)` in a folder without Git, or `Generated from <commit>` when the date cannot be read; when the Wiki records no Git revision, the tooltip also says in full that added files are not checked, which the description may cut off in a narrow sidebar. **Update LLM Wiki** is its action while no run shows. The row stays while a run works, so you can read the Wiki during an update.
- **`Generating…` or `Updating…`** is this window's run. In VS Code it reads `Waiting for the chat to start` and then `In chat · <N> min of <bound>`, with the actions **Stop Watching** (an eye-closed icon), **Open Chat** (the chat that waits for an approval or never started is one click away) and **Show Output**; the message above the tree says that Stop watching does not stop the chat. A failed generation's row offers **Try Again** (a restart icon). Inline action names are in Title Case (**Stop Watching**, **Change Location**, **Open Chat**, **Open Folder**, **Show Output**, **Try Again**, **Copy Recovery Request**); **Cancel** keeps the stop icon because it stops the agent. In Cursor it reads `cursor-agent · <N> min of <bound>` with **Cancel** and **Show Output**. The description is read again every 30 seconds. If the start time cannot be read, the row shows no minutes (`In chat` or `cursor-agent`) rather than a wrong number.
- **`Generating in another window`** or **`Updating in another window`** shows a run of another editor window on the same folder, with its start time.
- **`Waiting for chat`** shows the reservation a stopped VS Code watch leaves, from any window: `retry after <time> (about <N> min)`. **Open Chat** opens the chat view, where the session is in the chat history; Codebook allows a new start after that time even if the chat stopped earlier. In VS Code the message above the tree then says that Codebook stopped watching the chat, which may still publish this Wiki, and that you stop the request in the chat. Until that message replaces it, the message that Codebook is watching the chat stays: the message above the tree is never empty in between. It stays while Codebook turns its marker into the reservation, also while a change that failed waits for its retry (Codebook asks again every 10 seconds, for 2 minutes); if Codebook gives up, the view stops showing the watching message. Once that time has passed the row is gone, so **Generate LLM Wiki** or **Update LLM Wiki** is available again whether or not the recorded process still exists. A Wiki the chat publishes meanwhile ends the wait: the Wiki row shows at once and the notice `An LLM Wiki was published in <folder>.` offers **Open in Browser**.
- **`Last generation stopped`** shows how this window's generation ended without a Wiki (`stopped watching`, `cancelled`, `stopped after 55 minutes`, `no Wiki published`, `agent exit <code>`). A click shows the full sentence with **Copy details** (your home folder shown as `~`); **Try Again** starts a new generation. It goes away when a Wiki is published or a new run starts.
- **Attention rows** name what blocks an update or makes the manifest unusable, with the cause as the description; a click shows the sentence the reader page shows for it. **`Publish in progress or stopped`** (a publish lock or an unfinished publish) and **`Wiki manifest needs recovery`** (the manifest was edited or cannot be read) offer **Copy Recovery Request**, which copies `/codebook Recover the unfinished LLM Wiki publish for this project` for the editor chat; Codebook copies no shell command. **`Wiki folder belongs elsewhere`** (the output is a file or a link, a folder on its path is a link, or the manifest names another checkout) offers **Change Location**. **`Wiki files changed by hand`** (a generated page was edited or is missing, or the folder holds a link or special file) offers **Reveal Wiki Folder**, which opens the folder in your file manager; for a folder that is not there it says `The LLM Wiki folder <folder> does not exist (yet). Generate LLM Wiki creates it.`, for a file in the folder's place it says `The LLM Wiki folder <folder> is a file, not a folder. Remove or rename that file, or change the location.`, and in a window connected to a remote host (SSH, a container; a WSL window reveals the folder like a local one) it says `Reveal Wiki Folder opens folders on this computer only; the Wiki folder is on <remote name>. Open it from a terminal in this window, which runs in that remote environment, not on this computer.` and opens nothing. When the path cannot be looked at (no permission, or a file where a parent folder should be) it says `The LLM Wiki folder <folder> cannot be read (<error code>). Check the path and its permissions, or change the location.` instead of saying the folder does not exist; the look gives up after 3 seconds (a network drive that does not answer), with the code `ETIMEDOUT`. A link at the folder's place whose target is missing gets `The LLM Wiki folder <folder> is a link whose target is missing. Remove or fix the link, or change the location.`, because **Generate LLM Wiki** refuses a link. When the setting names no usable folder (empty, or outside the project) it says `Reveal Wiki Folder could not find the Wiki folder (<reason>). Change the location.` and Output › Codebook records the cause. An unreadable manifest, an edited manifest, a link or a file in the folder's place hides the Wiki row; the other causes leave the Wiki readable. **Refresh** reads the state again.
- **`Output: <folder>`** shows the resolved folder with **Change Location** (the `codebook.wikiOutputDirectory` setting) whenever another row shows. A folder outside the project shows its absolute path.
- A read that fails shows `Could not read the LLM Wiki state` with `Refresh to retry`; a click opens Output › Codebook, where the cause is written.

When the view's state changes, for example when a run starts or ends, Codebook hands the editor the message above the tree with the rows it belongs to, so in VS Code the message and the rows change in the same frame, not one before the other.

The view reads its state again after a change of this window's run and once this window has removed or turned into a reservation the run's marker (so `Waiting for chat` shows also without a file event), after a change of the Wiki's manifest or of the three marker files beside the Wiki folder (one second after the last change, so a burst of changes is one read), after a change of `codebook.wikiOutputDirectory` or of workspace trust, when the view is shown, every 30 seconds while the view is shown and a run row shows (a marker whose window died leaves no file event; the poll goes on across the error row of a read that failed after a run row showed), and with the **Refresh** action in its title bar. A collapsed or hidden view runs no poll and no freshness check, not even one that was waiting when it was hidden, and reads once when it is shown again. Inside the project the watch stands on the project folder from the start and stays there, also in a fresh project whose Wiki folder's parent does not exist yet, so creating the Wiki folder or deleting or renaming it or a folder above it is seen (never the home folder or a drive root: when the project folder is one of those, the watch stands on the nearest existing folder below it). An output folder outside the project is watched from its own parent only when that exists; the home folder and a file-system root are never watched. The editor reports nothing for the watched folder itself, so deleting or renaming the project folder (or a folder above it) shows after **Refresh** or the next time the view is shown; the same holds for the nearest existing folder that is watched when the project folder is your home folder or a root. If the editor refuses the watch, or there is no folder to watch, the view refreshes when it is shown and with **Refresh** only, the **Output** row's tooltip says so and Output › Codebook records the cause once. A failure of a read or of the freshness check is recorded once while it keeps happening (a message that differs only in its numbers counts as the same failure), and again when a different one comes or after a good read or check. The freshness label is read at each refresh, so a source edit shows as `Source changed` when the view is next shown or refreshed, not at the save. A refresh with nothing new changes nothing the screen reader announces and never moves the focus. Every action is also in the row's context menu (Shift+F10). **Codebook: Refresh LLM Wiki**, **Codebook: Copy LLM Wiki Recovery Request** and **Codebook: Reveal LLM Wiki Folder** are listed in the Command Palette only in an editor that shows the view. Only the first workspace folder is read. The 55 minutes of a generation count wall-clock time, so time asleep counts toward them.

### Troubleshooting the LLM Wiki

Each entry is a sentence Codebook shows when a generation ends or does not start, with what was kept and the next step.

#### Codebook found no LLM Wiki

`Codebook found no LLM Wiki in <folder>.` The folder holds no manifest. Press **Generate LLM Wiki**, or check `codebook.wikiOutputDirectory` if you expected the Wiki elsewhere. While a first generation is under way, **Open LLM Wiki in Browser** and **Update LLM Wiki** name it instead (`Codebook is already generating this project’s LLM Wiki. …` in its window, `Another editor window is generating this Wiki (…). Wait for it to finish, then press Open LLM Wiki in Browser.` in another) and offer no second generation.

#### Generation finished without publishing

`Cursor Agent finished without publishing an LLM Wiki in <folder>. …` or `The editor chat finished its reply without publishing an LLM Wiki in <folder>. …` Nothing was written. Read the chat's reply (VS Code), or ask Cursor chat `/codebook Generate the LLM Wiki for this project` to see what the agent says, then press **Generate LLM Wiki** again.

#### Generation stopped

`Codebook stopped watching the LLM Wiki generation at <time>. …` (VS Code) or `LLM Wiki generation cancelled at <time>. Cursor Agent was stopped; nothing was published.` (Cursor). A stop that came after a Wiki was published says so in the same verb (`Codebook stopped watching the LLM Wiki generation at <time>, after an LLM Wiki was published in <folder>.` in VS Code, `The LLM Wiki generation was cancelled at <time>, after …` in Cursor), and the Output record words the stop the same way (`stopped watching by the learner or the closing window` in VS Code, `cancelled by the learner or the closing window` in Cursor). In VS Code the chat may still publish, and **Open LLM Wiki in Browser** opens the Wiki once it has; stop the request in the chat to end it. A stop names a Wiki as published, with **Open in Browser**, only for a publish of the Codebook publisher that names this project and has its entry page; a manifest that appeared otherwise counts as nothing published. A new generation waits for that chat up to 55 minutes after the watch's end, and its refusal offers **Generate anyway** once you stopped the chat.

#### Generation timed out

`Codebook stopped waiting for the LLM Wiki generation after 55 minutes. …` In Cursor the agent was stopped and nothing was published: press **Generate LLM Wiki** to try again. In VS Code the chat may still publish, as above.

#### The Wiki folder exists without a Wiki

`The folder <folder> already exists but holds no LLM Wiki, and the publisher writes a first Wiki only into a folder it makes itself. …` The folder is there (made beforehand, or left by a generation that did not publish) and has no manifest; the publisher refuses to write a first Wiki into it, so Codebook starts no agent. Codebook leaves its files alone: move what you keep in it elsewhere and remove the folder, or set `codebook.wikiOutputDirectory` to a folder that does not exist yet, then press **Generate LLM Wiki** again.

#### Published Wiki does not identify this project

`The LLM Wiki published in <folder> does not identify this opened project. …` The publication names another checkout, so Codebook does not call it generated. Set `codebook.wikiOutputDirectory` to a folder of this project and generate again.

#### Published Wiki has no entry page

`The LLM Wiki published in <folder> has no entry page Codebook can open (index.html). …` Ask the editor chat `/codebook Generate the LLM Wiki for this project` to publish it again.

#### Published Wiki manifest cannot be read

`An LLM Wiki was published in <folder>, but Codebook cannot read its manifest. …` or `A manifest appeared in <folder> during the generation, but not through a publish of the Codebook publisher, …` Ask the editor chat `/codebook Recover the unfinished LLM Wiki publish for this project`.

#### A publish is still running or was stopped

`A publish of the LLM Wiki in <folder> may still be running or was stopped (<file>). …` Wait for it to end and press **Generate LLM Wiki** again; if it was stopped, ask the editor chat `/codebook Recover the unfinished LLM Wiki publish for this project` once its process exits.

#### The Wiki folder is a link, a file or holds a special file

`<folder> is a link or a file, not a folder of its own, …`, `A folder on the path to <folder> (<path>) is a link or a file, …` or `<folder> holds a link or special file (<path>), …` The publisher refuses to write there. Replace it with a real folder, move the entry out, or set `codebook.wikiOutputDirectory` to another folder.

#### Something else in the Wiki folder is in the way

`The folder <folder> cannot take a new LLM Wiki: <path> is in the way. Press Update LLM Wiki for the details and the next step.` The folder holds something a first generation cannot work around; where Codebook names no path, the sentence reads `The folder <folder> cannot take a new LLM Wiki. Press Update LLM Wiki for the details and the next step.` Press **Update LLM Wiki** for the details and the next step.

#### Another window or an earlier chat is generating

`Another editor window is generating this Wiki (<editor>, started <time>). …` or `The VS Code chat … may still be generating this Wiki; …` Wait for it; once that chat was stopped, choose **Generate anyway** in the notice.

#### The managed Cursor skill is in the way

A refusal that names the Cursor skill `codebook` (a skill of your own or one you edited): Codebook keeps it and does not generate. Move a skill of your own out of `~/.cursor/skills/codebook`, or run **Codebook: Restore Managed Cursor Skill** to put back the managed skill you edited, then generate again.

#### An earlier Cursor skill step is still running

`Codebook could not ready the Cursor skill: an earlier Cursor skill step in this window is still running. Reload the window (Developer: Reload Window) to end it, then press <Generate|Update> LLM Wiki again.` A check or deployment of Codebook's Cursor skill started by an earlier press did not finish, and a new press waits for it for up to 30 seconds. No agent was started and the Wiki's marker is left as after any ended start (removed, or another window's stopped-watch reservation written back). Reload the window to end the stuck step, then press the button again.

**Codebook: Remove Managed Cursor Skill** ends a Cursor skill step of the window and waits up to 5 seconds for it, so a late deployment cannot write the skill again after it was removed. A step that still runs after that leaves everything in place and says `Codebook did not remove the managed Cursor skill: a Cursor skill step of this window is still running and could write the skill again. Reload the window (Developer: Reload Window) to end it, then run Codebook: Remove Managed Cursor Skill again.` A Generate or Update pressed while the removal is under way readies no skill and starts no agent: `Codebook is removing the managed Cursor skill in this window; no agent was started. Press <Generate|Update> LLM Wiki again when the removal has finished, and Codebook installs its skill again.`

#### Cursor Agent CLI is not installed

`Cursor Agent CLI is not installed: Codebook looks for ~/.local/bin/cursor-agent, then cursor-agent on the editor's PATH. …` Install `cursor-agent`, sign in, and retry, or use Cursor chat.

## Install the private VSIX

Obtain the VSIX and `SHA256SUMS` from a successful **Build, test and package** workflow run on this repository's `main` branch. For a local build, follow the next section; the package command reports the VSIX SHA-256 in its JSON receipt and does not create `SHA256SUMS`. Verify downloaded workflow bytes in their directory:

```sh
shasum -a 256 -c SHA256SUMS
code --install-extension /absolute/path/codebook.vsix --force
cursor --install-extension /absolute/path/codebook.vsix --force
```

This checksum identifies the exact downloaded VSIX and detects changed bytes; it does not authenticate the publisher. Obtain both files from the same run on `main`, never from a pull request's run (anyone can open one on a public repository, and its run also makes a VSIX). Preview candidates can share an extension version. Use the linked validation and archive-comparison records to identify the checked build revision, sourceHash and per-file inventory. Rebuilt CI archives can have different ZIP-container checksums despite matching entry bytes; equivalence requires an explicit comparison that accounts for any build-metadata differences. Native execution remains evidence for the exact archive installed in that run.

Each command installs `laststance.codebook` in that editor. Install in whichever host you are using; testing one does not verify the other. The bounded installed workflow is demonstrated on **macOS arm64, VS Code 1.138.0 and Cursor 3.21.16 (API 1.128.0)**. A JavaScript-only VSIX and the manifest's engine range do not establish support for every OS/editor version. This preview is distributed only through this repository; it is not a Marketplace or Open VSX release.

Open a trusted local Git workspace. Source reading requires Git. For Cursor, disable **Settings → General → Layout → Open Chat as Editor Tabs** before opening Codebook. With **Codebook: Chrome Executable** unset, Codebook uses Google Chrome's usual path on macOS and the first `google-chrome`, `google-chrome-stable`, `chromium` or `chromium-browser` on `PATH` on Linux. To find the browsers it started, by their profile folder, Codebook lists processes: on macOS and Linux only this user's; on Windows those of the editor's logon session and, of this user's other sessions, only Codebook's browsers.

Run **Codebook: Start Agent Server**, then **Codebook: Copy Agent Connection** and configure your external MCP client with that current connection. The server is loopback-only and uses a private descriptor in the editor's extension storage. Treat copied credentials as private; do not commit them. Use **Codebook: Open Study Workspace** to open the learning panes. The installed extension includes its production runtime and bundled dependencies. Open the real target project as a separate workspace with its own dependencies installed; the extension requires no source checkout or package installation inside its installation directory.

Start the server and copy a fresh connection; the previous instance's connection is obsolete. Keep the editor's extension storage to retain books, recordings and explicit understanding decisions. Old captured source remains immutable; changed current source can show **Review needed**. If extension files are missing or damaged, reinstall the verified VSIX.

For isolated evaluation, use the same `--user-data-dir /absolute/profile` and `--extensions-dir /absolute/extensions` arguments on both the install and launch commands. These are ordinary installations. A different profile/workspace has separate persisted state.

## Build and verify a package

Package builds require a POSIX host (macOS or Linux); Windows builds are rejected before launching tools because the cleanup contract uses owned process groups. Maintainers use **Node 24.21.0** and the integrity-pinned **pnpm 12.4.2** in `package.json`. Installed-editor support remains the separately validated macOS matrix above. From the repository root:

```sh
pnpm --dir extension install --frozen-lockfile
pnpm --dir extension package
pnpm --dir extension package:check "$PWD/artifacts/packages/codebook-$(node -p "require('./extension/package.json').version").vsix"
```

The package command checks pnpm, clears only the extension compiler output, rebuilds, bundles production modules and stages an explicit file allowlist. Test/application fixtures and experimental dependencies are rejected. The independent checker validates archive entries, hashes, manifests and dependency notices before accepting the VSIX.

The VSIX includes `package-manifest.json` with file hashes, captured dependency/input identity, the running Node/pnpm/esbuild versions and the resolved extension TypeScript/vsce package versions, plus `dist/build.json` with source revision, dirty state and source hashes. `THIRD_PARTY_NOTICES.md` links the bundled dependency licenses. The separate check command verifies archive structure and metadata without executing supplied extension code; its self-consistency checks are not a publisher signature. The build additionally loads its own verified artifact in an unrelated temporary directory without repository dependencies. Normal installed activation and native workflow evidence are separate checks.

Archive checking and the reported SHA-256 use the same captured bytes. The checker rejects archives larger than 64 MiB, more than 2,048 entries, or more than 64 MiB of declared expanded content. Each package subprocess has a three-minute timeout and an 8 MiB limit for each output channel. The runner terminates its owned process group and waits up to five additional seconds for cleanup before returning. A failure to confirm cleanup rejects the build; combined failures retain the original error code/signal alongside the cleanup error. Failures preserve the previous VSIX. SIGINT/SIGTERM/SIGHUP/SIGQUIT during a package command reject with an interruption error after retiring its group, allowing the caller to remove its stage before the CLI exits nonzero. Existing caller signal handlers remain installed. Signal ownership ends when that command and its cleanup settle. A first or later signal during outer bundling, staging, verification or publication can terminate the process and leave scratch; transaction-wide cancellation is not promised. SIGKILL, immediate termination by a caller handler and independently detached descendants are outside this cleanup contract. Duplicate dependency-notice paths are rejected before their content is hashed again.

Local builds can record a dirty source tree; CI and accepted validation candidates require clean provenance. Clean means every selected source, fixture, script, patch and listed package/configuration input matches the raw bytes stored by its recorded Git revision. Ignored additions, index-hidden edits/deletions and clean/smudge transformations that change selected bytes remain dirty even if `git status` appears clean. Ambient `GIT_*` overrides and replacement refs cannot redefine that identity; provenance reads disable Git's optional index writes. Clean source identity does not attest that pre-existing `node_modules` or tool binaries match the lockfile and patch bytes. Run the frozen installs above before building an accepted candidate; CI repeats those installs and the package records the dependency bytes actually bundled. The inventory/checker accepts SHA-1 and SHA-256 Git revision formats; this does not establish a full build or native installation from a SHA-256 repository.

The private VSIX intentionally includes relative source/test paths and hashes in its build metadata. Those inventories are visible to anyone receiving the archive. Review or minimize that metadata before any public Marketplace/Open VSX distribution.

CI runs the product/runtime tests and real packaging/failure tests before uploading only the VSIX, build receipt, verification receipt and checksum, with clean provenance required. Native recordings and connection descriptors stay outside distribution. Workflow artifacts expire after 14 days; preserve any artifact needed for later acceptance together with its checksum in the private evidence store. For local regression testing, build the extension, run `node --test extension/dist/tests/*.test.js`, then run `pnpm --dir extension test:package`. Run packaging after runtime tests finish because its integration test cleans shared compiler outputs.

## Learn this repository

```sh
node --input-type=module <<'NODE'
import { readFile } from 'node:fs/promises';
import { z } from 'zod';
import { StudyClient, connectionSchema } from './dist/client.js';
import { repositorySourceSchema } from './dist/repositorySchemas.js';

const connectionPath = process.env.CODEBOOK_CONNECTION;
const sourcePath = process.env.CODEBOOK_SOURCE;
if (!connectionPath || !sourcePath) throw new Error('Set CODEBOOK_CONNECTION and CODEBOOK_SOURCE.');
const connection = connectionSchema.parse(JSON.parse(await readFile(connectionPath, 'utf8')));
const agent = await StudyClient.connect(connection);
try {
  await agent.discover();
  const source = await agent.tool('codebook_source', {
    instanceId: connection.instanceId, path: sourcePath,
  }, repositorySourceSchema.omit({ text: true }).extend({
    instanceId: z.uuid(), numberedText: z.string(),
  }));
  console.log(JSON.stringify(source, null, 2));
} finally {
  await agent.close();
}
NODE
```

The `repository-browser` profile has two adapters, `next-dev-webpack` for a Next app, App Router or Pages Router (see **Explain a browser interaction in a Next.js app** below), and `vite-dev` for a Vite app (see **The `vite-dev` adapter** below); `codebook_status` names both in the profile's `adapters` list, with the scope of each (the older `adapter` field still names `next-dev-webpack` for earlier readers), reports for the opened workspace which of them is ready, and a configuration names exactly one; for `next-dev-webpack` that report also counts the shared prerequisites (the configured browser, Node and the rest of the profile's checks) and whether another managed run is active, as it does for `vite-dev`, so it says ready only when a start would not be refused for those reasons. The `next-dev-webpack` adapter needs a trusted local Git root with dependencies already installed, an executable Next development server, a same-origin `entryPath` (default `/`), default `.next/dev` output, and webpack modules/maps that retain the exact original selected source. Codebook starts the owned server on `127.0.0.1` at the project's own port (Next is started with `--hostname 127.0.0.1`) and opens the app in the recorded browser at `http://localhost:<port>`, the origin that `AUTH_URL`, OAuth callbacks and cookies usually name. `localhost`, `127.0.0.1` and `[::1]` at that port count as the same application origin, so a sign-in redirect between them keeps the run going while another port or host still ends it. Because a host may resolve `localhost` to `::1`, Codebook also listens on `[::1]:<port>` for the whole run and forwards its bytes to the owned server (each direction ends as its source ends, so a client that half-closes still gets the reply), so no other process can answer there. The listener starts after the owned `next dev` has bound its port and reported ready, and never starts when that readiness fails or is cancelled; it closes with the run. If something else already holds `[::1]:<port>`, preparation is refused as a busy port naming `[::1]`; if the system does not let Codebook listen there it is refused as not permitted, and any other listen failure is refused with its error code. On a host without IPv6 loopback no `[::1]` listener is made and `[::1]` is not accepted. The recorded browser resolves `localhost` as the system does, so the app's own calls to your other local services, on `::1` or `127.0.0.1`, reach them as they do in your own browser; Chrome itself runs on a dynamic loopback endpoint. The port is the one the project's own `dev` script would start `next dev` on, and Codebook asserts it only for a fixed set of forms. The `dev` script, and each script it runs, may be one or more statements joined by `&&` or `;`, each one of these: `export PORT=4000`, or a `PORT=4000` or plain `NAME=value` assignment as a prefix before a command; a `next dev` command reached by `next`, `npx next`, `bunx next`, `pnpm exec next`, `yarn next` or a `node_modules/.bin/next` path (the path form only on its own or after `pnpm exec`, since `npx` and `bunx` take a package name and fail on a path), optionally after `PORT=4000`, `cross-env` or `env` with assignments only, with Next's own `dev` flags and literal values (`-p`/`--port` as `-p 4000`, `-p4000`, `--port 4000` or `--port=4000`, the last one winning, `-H`/`--hostname`, `--turbo`, `--turbopack`, `--webpack`, `--experimental-https` and its `--experimental-https-*` options); a script run with no arguments (`npm run x`, `pnpm run x`, `yarn run x`, `bun run x`; `pnpm x` and `yarn x` without `run` are followed only for `dev`, `start`, `serve`, `web`, `app`, `client`, `frontend` and a name with a `:`, since pnpm and yarn have many commands and aliases of their own (`deploy`, `ci`, `t`, `access`, `rebuild`) that run before or instead of a script of that name, and some of them change between versions: write `pnpm run deploy`), followed two levels deep at most; or one `concurrently` whose quoted commands are each read the same way and exactly one of which is a `next dev` command. The port is the last `-p`/`--port`, else the `PORT` the script exports or assigns before the command, else Next's default 3000, and `PORT` from the editor's own environment is not consulted. The `dev` script is read as text and never run. A `package.json` that is not a regular file (a FIFO, for example) or is larger than 1 MiB is not read, and `applicationPortSource` says so. A `dev` script that runs more than 256 statements in all, counting every line of it and of each script it runs, is unread, and `applicationPortSource` says the dev script runs more statements than Codebook reads. The last statement may end with one `;`. The script is read with the meaning of the shell that runs it: `sh` on macOS and Linux, `cmd` on Windows, where npm, pnpm and yarn run scripts with `cmd`. On Windows only the forms that mean the same under `cmd` are read: bare `next` or an `npx`-style launcher with `next dev` and literal flags (a program written as a path with `/`, such as `node_modules/.bin/next`, is unread), `cross-env PORT=4000 next dev`, delegations and a `concurrently` with double-quoted commands; single quotes, a `PORT=4000` or `NAME=value` prefix, `export`, `env`, `;` and a variable named `port` in any case other than `PORT` (Windows ignores the case of variable names) are unread there, and `applicationPortSource` names `cmd`. An empty `dev` script is told as empty. A word that has a quote before its `=` (`"PORT=4000" next dev`) is no assignment. Everything else is unread: any other program or option, a pnpm command whose meaning depends on the installed pnpm version (`pnpm rebuild`), a pipe, `&` or `||`, a group or subshell, `$`, a backtick, a redirection or heredoc, a comment, a backslash or a line break, `if`/`while`/`!`/`time`, `sh -c`, `cmd /c`, `dotenv`, `node`, `set`, `unset`, a bare `PORT=4000;`, a `${PORT:-4000}` default, arguments given to a delegated script, and a script that never runs `next dev`. For an unread script no port is asserted: Next's default 3000 is taken and `applicationPortSource` says so and quotes the statement that left the forms above by its structure only. Only names from fixed lists are quoted (the words of the forms above by their base name, Next's `dev` flags, `PORT=…` and plain `NAME=…` assignment names before the program, and `package.json` script names, without control characters and cut); every value, operand, path, token, header, `user:pass@host` and base64 text is shown as `…`, so declare the port with `-p` in the `dev` script in one of the forms above to name it. `.env` files are not read for the port, because Next reads `PORT` before it loads them. Bun is the exception: it loads `.env` files into the environment of the scripts it runs, so a `next dev` without a `-p`/`--port` flag and without a `PORT` assigned in the script is unread (Next's default 3000 is taken and `applicationPortSource` names Bun's `.env` loading) when it is reached by `bun run <script>` or the project is a Bun project: `bun.lock` or `bun.lockb` looked for in the opened folder and the folders above it up to the first folder that holds `.git` (a folder or a file), at most 16 folders counting the opened one, and when no `.git` is found in that range only the opened folder's lockfile counts (only the file's existence is checked), or a `packageManager` of `bun@…` in the opened `package.json`; an explicit `-p`/`--port`, or a `PORT` the script sets in a form read above, is still read, and only a `next dev` without a port flag in such a project is unread. A Yarn Berry (Yarn 2 and later) project, found by a `packageManager` of `yarn@2` or later or by a `.yarnrc.yml` looked for in the same folders and range, reads `export PORT=4000` as unread and `applicationPortSource` names Yarn's portable shell, which has no `export`; `PORT=4000 next dev`, quotes, `;` and `env` are still read, as Yarn runs them, but a `;;` and a `;` followed by blanks at the end of the line, which Yarn's shell rejects, are unread with the same note. A Yarn Berry project uses Yarn's portable shell on Windows too, not `cmd`, so those forms are read there as on macOS and Linux and `export` is unread with the Yarn note; a `packageManager` of `yarn@1` (or another manager) wins over a stray `.yarnrc.yml`. Each script is read with the shell of the program that runs it: Yarn's portable shell for the `dev` line of a Berry project and for scripts reached by `yarn run` or `yarn <name>`, `cmd` on Windows (`sh` elsewhere) for scripts reached by `npm run`, `pnpm run` and the quoted commands of `concurrently`, so `npm run b` with `b` set to `PORT=4000 next dev` is unread on Windows even in a Berry project. On Windows, Bun runs scripts with its own shell, or with `cmd` when `run.shell` is `system` in `bunfig.toml`, so the same text can mean different things: a `dev` script of a Bun project and any `bun run` are unread there, and `applicationPortSource` names Bun's shell. ## Declare a web flow as operations

Use configuration version 3 when a web flow needs several steps; keep version 1 or 2 for one click. The quick start is the `operationsQuickStart` section of `codebook://help/repository-browser`, and the update path is: update the extension, reload the window, run **Codebook: Set Up AI Chat**, start a new chat, and check that `codebook_status` lists 3 in the profile's `configurationVersions`.

- **Operations.** A run declares one to eight operations: `text` into an input, a textarea or a number input, `choose` an option of a native single `<select>` (a custom select is driven with `click`), and `click`. The chat sends them one at a time, and a receipt only says the run accepted the operation; its progress is `operations[i]` in the run resource, which the chat reads before it says an operation happened.
- **Waiting.** Before each operation Codebook waits up to 10 s for the page to finish loading and stay still; past that the run fails with `NAVIGATION_NOT_SETTLED` and sends nothing more. A slow route is warmed in the run's `before` conditions. A new page load before the last operation fails a Next run with `NAVIGATION_BEFORE_LAST_OPERATION`.
- **Secrets are typed by you.** A password or other secret is declared as `secret: "ask-learner"`: the editor asks you in a masked box, the chat never sees it, and text for a secret control that comes from the chat is refused with `SECRET_INPUT_FROM_CHAT`. If you dismiss the box the run stays ready (`OPERATIONS_NOT_CONFIRMED`).
- **Masking, and a behavior change in version 1 and 2.** Text a version 1 or 2 run types into a password or other secret control, and a chrome-extension click's input text, now reads `[masked]` in the run resource, the saved study and the configuration hash, and every prepared text reads `[pending]` until its control is resolved; the page still receives the real text. Recorded frames show what the browser draws, and Codebook relies on password dots: it drops frames where that cannot be verified and fails the run with `SECRET_BECAME_VISIBLE` if the control stops being a password input. Other secrets are masked by name and format only, so use a local test account.
- **While it runs.** The Codebook status bar item, after the capture state and **Save learning replay**, reads `Operation <k>/<m> · <title> · sending`, `Operation <k>/<m> · <title> · paused in code`, `<m>/<m> sent · checking result`, `Done · <m> operations` or `Stopped at operation <k> · <reason>`, never a bare count as a success, and the run resource carries the same words in `operationStatus`.
- **Saved and replayed with its operations.** A version 3 run is saved in study format 7 with each operation's state and time; a stopped or failed run is saved as a partial replay whose operations read done, failed or not run. Its replay draws a row of numbered operation buttons above the playhead (a filled number when done, a cross and the word failed when failed, a question mark when not run), with **Previous operation** and **Next operation**; choosing one moves the replay to the last frame before that operation was sent and says so under the row, and a Learning summary step can link to its operation. Codebook 0.2.70.0 lists a study saved in format 7 and refuses to open it, and keeps the file.
- **A failed browser run is a failure.** A failed `repository-browser` run of any configuration version now answers `isError: true` with the run state, as node-server and chrome-extension runs do; before, a version 1 or 2 failure could read as a success.

## Explain a browser interaction in a Next.js app

The quick start for this run is the `nextQuickStart` section of `codebook://help/repository-browser` (read its `startHere` sentence first, which names the quick start that fits the workspace): a minimal configuration, where each of its values is copied from, and the order of the calls. With `adapter: "next-dev-webpack"` the chat explains a click in the opened repository's own Next 16 app, whether its pages are App Router pages (`app/` or `src/app/`) or Pages Router pages (`pages/` or `src/pages/`): Codebook starts the app's development server itself, finds the entry page in Next's route manifests, seals each declared stop against the page's own client code before the browser opens, pauses at the declared line in the native debugger so the chat can explain with the live values, and saves the run as a learning replay, in VS Code and in Cursor. Development trials ran Pages Router pages of TanStack Query's Next 16.4.3 examples in VS Code 1.144.0 and Cursor 3.27.22 on macOS 26; installed host compatibility remains subject to native validation on other versions and systems.

- **Pages Router pages.** A stop may be in the page module of the entry route (`pages/` wins when both `pages/` and `src/pages/` exist; `.tsx`, `.ts`, `.jsx` or `.js`), in a client component the page imports, or in `_app`. Codebook matches `entryPath` against Next's route manifest segment by segment, as Next does: a static segment before a dynamic one, a dynamic one before a catch-all, a catch-all before an optional catch-all. The query and a trailing slash (except for `/`) are dropped and encoded segments are decoded; `/_app`, `/_document`, `/_error`, `/404` and `/500` are no entry routes. Before the first input the run waits until the page's Next router is ready and checks that it reports the entry route.
- **What `codebook_status` reports.** The `repository-browser` profile lists `nextRouters: ["app", "pages"]`, the Next routers this version serves, and the bundled skill reads `codebook://help/repository-browser` again when that list differs from the one it remembers. The `next-dev-webpack` readiness under `profiles[].prerequisites.adapters` adds `routerKind` (`app`, `pages`, `both` or `none`; for `none` a note names the folders searched: `app`, `src/app`, `pages` and `src/pages`) and, when the `dev` script does more than start Next, `preparation`: its `status` reads `skipped` with the number of `statements` Codebook skips (a `predev` script, or the `pre<name>` script of a script that `dev` runs through `npm run`, `pnpm`, `yarn` or `bun run`, counts as one when the package manager that runs it runs pre scripts: npm, Yarn 1 and Bun do, pnpm 9 and later do by default, pnpm 7 and 8 only with `enable-pre-post-scripts=true` in an `.npmrc`, and Yarn 2 and later never do; the project's manager is read from `packageManager`, else from its one kind of lockfile, and when Codebook cannot tell, the script counts and the readiness `notes` say it may or may not run), or `unknown` for a script it could not read, and its `envSettings` names the environment settings Codebook does not apply; the readiness `notes` say the same in sentences. Neither changes `ready`.
- **App Router projects with a plain `next dev`.** An App Router project whose `dev` script is plain `next dev` (Turbopack by default in Next 16) runs the same way, because Codebook always starts `next dev --webpack`.
- **Not supported.** Stops in App Router server components are not supported (a version 2 server stop is a server-action stop), nor stops in a Pages page's server-side code: a Pages Router page takes client stops only (see `NEXT_SERVER_ONLY_STOP` below).
- **What the bundled skill does (1.0.61).** The chat sends a question about a Pages Router page to `next-dev-webpack` as it does for an App Router page, tells you a refusal's code with the recovery of that code's section in the help (for `NEXT_SETUP_DEADLINE`, the recovery the run itself gives for the step it reached: one retry, a corrected `entryPath`, the input selector, or reading the captured history first), never moves a stop to unrelated code, never edits the project's files, config or scripts to make a run start or reach its stops, not even temporarily or after you agree to continue (when the page itself keeps the declared action from happening, such as an automatic load that races the click, it tells you what blocks it and offers only choices that change no project file), and says the learning is saved only once its save has completed, never while it is still saving. In a test run's summary or table it labels a value observed only when the run recorded it (a stop's captured facts or the test result) and calls a value it derived from source or test code, such as a mock's return value, source reasoning.

### Before starting

- Stop your own `next dev` for this workspace first: Codebook starts its own, and a `.next/dev/lock` that another process holds refuses the start with `PREREQUISITE_MISSING`. Codebook never removes another process's lock.
- Install the project's dependencies first; Codebook installs nothing.
- Codebook never runs your `dev` script. Statements before `next dev` in `scripts.dev`, and a `predev` script or a delegated script's `pre<name>` script that your package manager runs, are skipped, and the environment settings the script gives `next dev` are not applied (a `PORT` setting only chooses the port). `codebook_status` reports the skipped preparation and the unapplied environment settings in `preparation` and in the readiness notes, the settings by name and never by value; run that preparation yourself from the workspace root before the start. In a project with Pages Router pages, a refusal for a server that fails to start or to compile names the same skipped preparation and unapplied settings, also for a `dev` script that only sets environment variables (`NODE_OPTIONS=… next dev`).
- Codebook runs your Next app with webpack (`next dev --webpack`) even when your dev script uses Turbopack. The page is built from the same source; a Turbopack-only loader or setting has no effect during the run. In a project with Pages Router pages, when the server fails to start or to compile and your `dev` script does not ask for webpack, the refusal adds this sentence, the Next version and the arguments Codebook started Next with. Codebook reads only the `dev` script's own text, not a script it runs, and counts `--webpack` there only as a word of its own, with whitespace or the script's start before it and whitespace or the script's end after it: `next dev --webpack` and `next dev --webpack -p 3000` ask for webpack; `concurrently "next dev --webpack" "tsc -w"`, `next dev --webpack; echo ready`, `next dev --webpack=true` and `npm run dev:web` do not.
- Codebook supports Next 16, whose development server writes the default `.next/dev` output. Preparation has 90 s in all, with no override: starting Next, the entry page, the route manifests, sealing the stops, the browser and the page router.

### When Codebook cannot verify a stop

Each refusal names its code, says what already ran and what Codebook stopped, and ends with that code's section in `codebook://help/repository-browser` (`#<CODE>`); the chat tells you the code and its recovery and never moves a stop to unrelated code to make a run succeed.

- `NEXT_UNSUPPORTED_SETTING`: the project sets `basePath` or `i18n` routing (the message lists every one found, with the Next version), which the browser run does not support, so you choose another page or project, or a local branch without the setting; Codebook never edits `next.config`.
- `NEXT_ENTRY_REDIRECTED`: the entry page redirected (an HTTP 3xx, a final path after the load that differs from `entryPath`, a page router route that differs, as a rewrite or middleware gives, or a path change before the first input or before the click, also while the page's before conditions are still awaited), and the message names the final path without its origin and with query and fragment values redacted (a target on another origin is named as such and never fetched); the chat uses that final path as `entryPath` only when your question is about that page, and otherwise tells you that this run cannot observe the redirect. Paths compare without query, fragment or trailing slash and with each segment decoded, except that an encoded `/`, `\` or `%` stays encoded, so a page at `/posts/a%2Fb` is another path than an `entryPath` of `/posts/a/b`.
- `NEXT_ROUTE_NOT_COMPILED`: the entry route did not appear in Next's route manifests within 10 s of the server answering, or no `.next/dev` manifests exist at all, which is also how a custom `distDir` shows, since Codebook reads only the default `.next/dev` output; a listed Pages page that answers the entry request with a server error (HTTP 5xx) is refused with this code too, before the browser opens, and the message names the status and quotes the development server's output, masked (cookie and authorization header values, the values of secret-named assignments, and every query value of a URL the server logged, a bare query part whole: `/reset?<token>`, a token with `=` padding such as `?<token>==`, a token before a second `?`, or a part with an empty value such as `?debug=`, also when quotes or brackets surround the URL, and a secret-named assignment a flag forwards, such as `--env=API_TOKEN=<value>`; the value of a `dev` script flag such as `--token=<value>` never reaches the message either), so you see the error the page hit.
- `NEXT_ROUTE_CONFLICT`: both the App and the Pages route manifests list the entry path with equally specific routes (when one route is more specific, such as a static App page beside a Pages catch-all, that route serves the path as Next decides), or the more specific one has lost its source file (no file with the source's name is left, apart from style, declaration, source map, test, spec or stories files such as `page.module.css` or `page.test.tsx`, which are no source; a source with another extension, such as `page.mdx` or `about.mdx`, is not lost and is never called stale: the more specific route is then refused with `NEXT_ROUTE_NOT_FOUND` for its custom `pageExtensions`); when the message says stale you remove the stale `.next/dev` folder yourself, with no `next dev` running, since Codebook never deletes it.
- `NEXT_ROUTE_NOT_FOUND`: no route matches `entryPath`, or the Pages page the manifest lists for it answers the entry request with a client error (HTTP 4xx, such as `notFound` from `getServerSideProps`, a path `getStaticPaths` does not return, or a page that needs a sign-in), which is refused before the browser opens with the status named; otherwise the message names what was searched (Pages, App or both) with the folders and extensions tried; a route the manifest lists without a `.tsx`, `.ts`, `.jsx` or `.js` source means a custom `pageExtensions`, which Codebook does not read, so another URL does not help; in a project with both routers this also holds for the App route that serves the entry path, and the message then names the App route and its folder.
- `NEXT_SERVER_ONLY_STOP`: `getServerSideProps`, `getStaticProps`, API routes (`pages/api`) and `_document` run on the server and cannot be stopped in, and this code says so when Codebook establishes it (the file is `_document` or under `pages/api`, or the line maps in the page's server compile and in none of its client chunks, also when client code follows it, since such a line is never moved to that code), so move the stop to client code that serves the same question. A stop declared with `participant: "server"` (a version 2 configuration) is refused with this code in a Pages run too, before that stop's chunks are read and before the browser opens, because a Pages run observes only the page's client code in the browser.
- `NEXT_STOP_NOT_SEALED`: Codebook could not verify the browser code of the stop, because its line has no verified browser mapping (which does not make it server-only), or because its module is loaded later, as a `next/dynamic` module is, which cannot be sealed; move the stop to client code the page loads at once.
- `NEXT_SETUP_DEADLINE`: a Next run in a workspace with a Pages folder (`pages/` or `src/pages/`) did not get ready within 90 s, at its early steps (starting Next, waiting for the server to answer the entry page, reading the route manifests), before its route is known, or at any step once its entry path resolved as a Pages route (once it resolved as an App route, as in a workspace without a Pages folder, the run fails with "Repository setup deadline exceeded" and no Next code), and the message names the step it reached, whose recovery fits it: one retry before the browser opened or for a router that was late, a corrected `entryPath` for a page without a Next router, the input selector at the input step, one retry when the deadline came after every input was written and the first stop was being armed, and reading the captured history first when an input may have been written.
- Saving a change to a module the page loaded during a run (Fast Refresh) ends the run with `SOURCE_CHANGED`; the observations before it stay readable.

## Explain a Node HTTP server

The `node-server` profile runs the opened repository's own Node HTTP server (an Express or Hono API, for example) under the editor's debugger, sends one declared request to it, and stops in the route handler's actual source, so the chat can explain the request with the live values you see in the Variables view.

- **What the chat declares.** The server's entry file (`entry`, relative to `packageRoot`, default the repository root), the port the server's own code listens on (`port`, 1024–65535), one request (`method`, `path`, and for POST, PUT or PATCH a `body` with its `contentType`), and the stops with the values to read. `codebook://help/node-server` has the walkthrough, three samples and every error code. Codebook starts exactly `node [--import <the repository's tsx>] <entry>` in `packageRoot`; it runs no script, command line or watch mode, and never sets the port.
- **Environment.** The server reads its own `.env` file as it normally does. Codebook passes only `PATH`, `HOME`, `TMPDIR`, `SHELL`, `LANG`, `LC_ALL`, `PNPM_HOME`, `USER`, `LOGNAME` and the certificate variables `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` and `SSL_CERT_DIR`; `NODE_ENV` is unset, so the server's own default applies. A TypeScript entry runs through the repository's own `tsx`, which the repository's install command installs. A repository that needs a newer Node than the one on your `PATH` runs with **`codebook.nodeExecutable`** set to that Node.
- **One request, confirmed when it changes data.** The run sends its request once, to the server's loopback address. Before a POST, PUT, PATCH or DELETE, the editor asks you in a dialog, naming the method and path, the body's size in bytes and its content type (`unspecified content type` when none is declared; never the body itself), and that the server uses the repository's own configured database; only **Send** sends it, and the chat cannot answer the dialog. A GET is sent without the dialog, and the server's own handler decides whether it changes data. A dialog an earlier run left on screen never sends this run's request: each run, and each declared body, asks in its own dialog, which names its run. Use a local or test database, never production data.
- **Stops and your own pauses.** At each declared stop the run pauses, and the chat explains with the values the stop captured; your Variables, Watch and Call Stack views show the live values. A pause of yours (your breakpoint, a `debugger;` statement, an exception, the Pause button) stays yours: Codebook never resumes it, and the chat waits until you continue, within the same 300 s hold as a declared stop. A declared line reached outside the request (at start-up, for example) is reported, not explained as part of the request. A continue while the run is stopping is refused with `STALE_PAUSE`, also while your own pause is held.
- **What the run reports.** The response is reported as observed (HTTP 4xx and 5xx included; a redirect is not followed). A connection that fails, or a server that does not answer within 30 s of running time (paused time excluded), ends the request with `REQUEST_FAILED` or `REQUEST_TIMEOUT`, whose message names the limit that ran out; a run whose request still waits at the run's 10-minute deadline ends with `RUNTIME_FAILED`; the chat never sends it again on its own, since a POST, PUT, PATCH or DELETE may or may not have changed the data. The chat reads the first 8,192 bytes of a text body (`text/*`, JSON) as the server sent it, spacing and lines unchanged, with credentials masked and the workspace's folder paths hidden before that cut, so a path across the cut shows none of its start, then `… <n> more bytes`, where n counts what remains of that masked text after the cut; a body with bytes that are not valid UTF-8, also one that ends inside a character, is marked `(not valid UTF-8)` (a read cut at 1 MiB inside its last character alone is not), and a binary body shows only its size. A body Codebook cannot prepare for display ends the request with `REQUEST_FAILED`, whose message says that the server answered and with which HTTP status, instead of leaving it waiting. A pause held longer than 300 s, a declared stop or one of yours, ends the run without resuming the paused code (`PAUSE_HOLD_EXPIRED`).
- **The status bar** shows the run beside its learning replay: `$(record) Recording explanation · <where the run stands> · Save learning replay` while it lives (where it stands reads `Server starting`, `Listening on :<port>`, `Paused at stop <n> of <m>`, `Paused by you in the debugger`, `Responded <status>` or `Failed: <code>`), then `Recording finished · Save learning replay`; its tooltip names how many declared stops are recorded and whether a response is recorded. A run whose history could not start reads `<where the run stands> · Learning replay unavailable: <cause>` (storage unavailable, a full saved-study limit or a start slower than 2 s): the server still runs and Save answers that cause. A history that could not be written or sealed reads `Learning replay could not be saved: <cause>`; the server run is unaffected. A history that stopped recording while the run lives (a write failed) reads `$(warning) <where the run stands> · Learning replay will be partial: <cause>` at once; Save still stops the run and saves what was recorded before the failure. A partial notice prints no terminal control characters from the reason.
- **Every way a server run ends seals its history once.** Your Stop, the chat's `codebook_stop`, Save, closing the window, the server exiting by itself and a failed run all join the same seal, which is bounded by 10 s. A seal past that bound reads `Learning replay could not be saved: timed out after <s> s.` and the history folder lists as interrupted. A seal or summary read that stalls never holds Stop, Save or the next run. The history ends at the moment you stopped the run, not at the last output before it. A seal that was published stays sealed: when the cleanup after it stalls or fails, the live run, the run resource and Saved studies still read the history as sealed. A run ended by its whole-run deadline seals as failed with `RUNTIME_FAILED`, and a clean Stop after an earlier failure seals as stopped. A history's start counts recordings that are still open against the Saved Study Limit, so a recording that started while the limit had room can always be archived.
- **Save a server run as a Server replay.** A server run keeps a private, workspace-bound history of what happens while it runs: the request Codebook opens, its output, the executed source at each stop, the debugger's recorded values and the response (the executed source text is stored as it ran, privately in the workspace's learning storage; secret-named values and secret-shaped text are masked and a secret written as a literal in your source is not rewritten; the workspace, home and Codebook storage paths read `<workspace>`, `~` and `<storage>` in the server's output, even where two output chunks split one; the end of a chunk that may begin a path waits for the next output and is released after 1 s of silence, as the placeholder when it already shows part of a private name, and when later output completes that path its private part is still hidden, and in every debugger text the history stores; a debugger value the capture cut inside a private path keeps no part of that path, and secrets are masked before any captured text is cut). **Save learning replay** before the request was sent answers `Nothing to save yet: the server run has not sent its request.` and the run continues. While the server runs it asks `Saving stops the server run (<n> of <m> stops recorded; no response recorded yet, so the response will not be saved). Save now?` (or `… recorded, response recorded). Save now?`) with **Save and stop** and **Cancel**; a second Save while the question is open uses the same question. After the history is sealed one notice says `Server replay saved.`, `Server replay saved as partial: <first reason> (+<n> more).` or `Server replay saved; the chat's explanation is not saved yet.`, each with **Open replay**; **Open replay** right after the save opens the Server replay even before Saved studies has refreshed its list. When the history failed or its sealed summary cannot be read, the notice says `Learning replay could not be saved: <cause>` instead; a summary read still unanswered after the seal's 10 s bound gives `The sealed server history could not be read within 10 s.` as the cause, and Save is free again for another run. A second Save reads the summary again (joining a read still in flight) and says the cause again only if it still cannot be read. Save reads the stored history every time, so when another window saved the chat's explanation after the seal the notice reads `Server replay saved.` with that material's revision, and Save never reports a replay saved for a history the store no longer holds (it says `The sealed server history is not in the store.` instead). It reads **Saved** only when the capture is complete and the chat's explanation covers it; a 4xx or 5xx response is a complete capture. The history counts against the Saved Study Limit with saved studies and test histories. The chat saves its explanation with `codebook_explain_node_history` (API 1.9): `codebook://help/node-server` (section `save`) is the canonical text with the 16-hit stop budget, the three verdicts, the codes and a worked example. If it saves its explanation before or after the seal, the row becomes **Saved** without a reload.

  | Code in `captureMissing` | What happened | What to do |
  | --- | --- | --- |
  | `SERVER_HISTORY_NO_RESPONSE_REQUEST_FAILED` | The request failed, so no response was recorded. | Start a new run to record a response. |
  | `SERVER_HISTORY_NO_RESPONSE_STOPPED` | The run was stopped before the server answered. | Let the run reach its response before saving, or accept a partial replay. |
  | `SERVER_HISTORY_NO_RESPONSE_EXITED` | The server exited before it answered. | Read its exit in Output › Codebook and start a new run once the server stays up. |
  | `SERVER_HISTORY_NO_RESPONSE_RUN_FAILED` | The run failed before the server answered. | Read the run's error and start a new run after the fix. |
  | `SERVER_HISTORY_STOP_NOT_REACHED` | A declared stop was never hit. | Declare stops on lines the request runs. |
  | `SERVER_HISTORY_SNAPSHOT_MISSING` | A stop has no usable debugger snapshot. | Start a new run. |
  | `SERVER_HISTORY_SOURCE_UNAVAILABLE` | The executed source of a stop was not stored (too large, or not captured). | Declare stops in a smaller file. |
  | `SERVER_HISTORY_VALUE_UNAVAILABLE` | A required inspected value could not be read at a stop. | Declare a path that exists at that line. |
  | `SERVER_HISTORY_APPEND_FAILED` | Writing the history failed after the entry it names. | Check the disk's free space and start a new run. |
  | `SERVER_HISTORY_SIZE_LIMIT` | The history reached its size limit; later events were not recorded. | Declare fewer stops or a quieter server. |
  | `SERVER_HISTORY_CAPTURE_BUDGET_EXHAUSTED` | More than 16 stop hits happened; later hits were not recorded. | Declare stops the request hits less often. |
  | `SERVER_HISTORY_OUTPUT_TRUNCATED` | The server printed more output than the history keeps; later output was dropped, so the history reads partial. | The stops and the response are kept; start a new run with a quieter server only if the dropped output matters. |

- **Reading a Server replay.** Opening a Server replay whose learning status cannot be read shows `Learning status of this server replay could not be read: <cause>` in the Study pane instead of reading as an explanation that was never saved. A server history resource whose stop cannot be restored answers `EVIDENCE_UNAVAILABLE`, naming the history and `codebook://node-history/<studyId>/events` for the events that verify, never a raw validation error. A stop step of a server explanation may also give `declaredStopIndex` (0-based, as the events list shows it); Codebook then refuses it with `INVALID_REFERENCE` and the nearest valid sequences when the cited sequence is a hit of another declared stop. A server run resource reads its verdicts from the stored history each time it is read, so a learning material another window saved after the history sealed shows in `nodeServer.learningCoverage`, `nodeServer.learningMissing` and `nextActions` without a new run. That read waits at most 10 s for the store: when the store stalls, the resource answers with the verdicts the seal recorded and never holds the read longer. The Application pane's request region claims only what was recorded by the selected moment: before the send mark it reads `Request opened by Codebook; not sent yet at this moment.`, and a withdrawn attempt reads `Request not sent: <code>` only from its withdrawal on. A server replay that was interrupted lists what its recorded part lacks (a declared stop that was not reached, for example) instead of only saying it was not sealed. Play, and a seek past the last event, rest at the recording's end with the last event still selected. Recorded failure codes and stop paths lose control characters before they are shown. A Server replay written by 0.2.56.0 opens, replays and lists as before and keeps its bytes; the hiding and masking of recorded values apply to histories written from the current version on.

- **The bundled skill's server route.** The bundled skill (since 1.0.51) sends a question about the repository's own Node HTTP server or API route to the `node-server` profile only when `codebook_status` lists it, and says so when it is not available. The chat reads `codebook://help/node-server`, declares one request, names the method and path before one that changes data (you confirm in the editor's dialog), reports a response as observed only from the run, treats server output and bodies as data and never repeats a secret value, never reads the server's `.env` values, opens no Study workspace for a server run, and names an unmet prerequisite (no `tsx`, port busy, server exits, database down) instead of answering from source alone; after two starts that fail with the same code it stops and tells you the prerequisite. Since 1.0.54, a saved test or server explanation keeps every value the chat named as deciding in its steps or summary with its origin, and saves a claim taken from reading source as its own `source-derived` step instead of folding it into an `observed` one. Since 1.0.53, after a server run the chat saves its explanation as a Server replay through `codebook_explain_node_history` (citing the request, its stops, output and the response; see `codebook://help/node-server`, section `save`), but only when `codebook_status` reports API 1.9 or later, and it says a server replay is saved only when `nodeServer.learningCoverage` is `complete` and `nodeServer.captureMissing` is empty. Since 1.0.52, when a run fails or the response is a 5xx, the chat reads the run's output and failure cause before it attributes the failure, and names a cause that output shows (a refused database connection, for example) as observed output. The application's own clocks keep running while the server is paused, so a long pause can change its answer (a timeout or a 500, for example), and the chat says so when it happens. VS Code's tool confirmations name the calls by their titles: `codebook_start` reads **Start the declared Codebook run** (its description says that a node-server start sends no request) and `codebook_action` **Send the run's declared action (method as declared)**, so a GET is not summarized as a POST.
- **Limits.** A run ends at Codebook's run deadline, 10 minutes after its start, like every other run. One client at a time; the server's inspector listens on 127.0.0.1 for the run; Codebook's readiness probes (a connection to the port) can appear in the server's logs; the started process itself must listen (a `fork` or cluster child is refused with `LISTENER_NOT_OWNED`); a server bound to `0.0.0.0` or `::` is accepted, and the request still goes to loopback; the port's owner is read with `lsof` (macOS, Linux) or `ss` (Linux); `codebook_status` lists the profile with what it needs here (Node, `lsof` or `ss`, `ps`, a supported platform), and native Windows reads it as not available. Before the request's first byte, Codebook checks that the connection reaches the server it started; when another process answers, nothing is sent (`LISTENER_NOT_OWNED`) and the run stays ready. Stopping the run ends the server it started, and only that. A stop before the request's first byte sends nothing; once the request was handed to the connection, it counts as sent. While the request is under way, or while the server is paused in the debugger (at a declared stop or by the learner's own pause), the stop ends the server at once (SIGKILL), so no paused code runs on after the stop; otherwise the debugger lets go first and the server gets SIGTERM, so its own shutdown runs, and SIGKILL follows within 5 s of the stop's start if the server has not ended. If the server pauses while the debugger is letting go, it is ended at once (SIGKILL) and **Output › Codebook** journals `node-server.late-pause-killed`. The stop's `node-server.closed` entry reads `killed: true` only when SIGKILL was sent. A stop ends within 10 s; otherwise the run reads `stopping` and names what remains. A stop you retry signals the server again only after it confirms that the process is still the one it started (its start time, which Codebook reads when the server starts and reads again before the debugger attaches if that read failed; a folder alone never counts): when the group has already ended, or the process id now belongs to another process, it signals nothing; after the server's own process exited, it ends the processes the server started that remain; and when it cannot tell (the process cannot be read while its group still has members) it signals nothing and the stop fails, naming the process id for you to end. Before SIGKILL it confirms that again, shortly before the 5 s bound, so SIGKILL still lands within 5 s of the stop's start and never reaches a process group that took the server's id in between; when that check has not answered by then, no SIGKILL is sent and the stop fails, naming the process id. A server that a closed window left running is ended at the extension's next start in that folder, with an entry in **Output › Codebook**; a record whose process start differs from the recorded one (the process id went to another process) or whose group has ended is dropped without a signal. A record whose process start matches the recorded one is ended whatever its working folder now is. A record Codebook could not verify while its group still has members (the leader's start could not be read, or a signal failed) is kept and listed in **Output › Codebook** with its process id and declared port at every start, and Codebook signals no process it cannot identify.

## Explain a Chrome extension

The `chrome-extension` profile (MCP API 1.10) loads the opened repository's unpacked Manifest V3 extension into a Chrome that Codebook starts itself, with a fresh test profile. It opens the extension's toolbar popup or one of its pages in the Application view, performs the declared clicks, and pauses in the extension's page script and its service worker in the editor's own debugger, so the chat can explain the clicks with the live values you see in the Variables view. Since MCP API 1.13 the run is also recorded (the pauses, each stop's executed source and debugger values, the surface's frames and the result) so it can be saved as an Extension replay.

- **What the chat declares.** The extension's folder (`extensionRoot`), the surface (the manifest's popup, or one extension page by its path), one to three clicks (each with a `title`, a CSS `selector`, an optional `kind: "dblclick"`, an optional `dialog: "accept"` or `"dismiss"` and optional text inputs), one to four stops (a file relative to the extension folder, a line and its context: `page` or `service-worker`), seeded bookmarks and storage, and the result to read (an element's text, a key of the extension's local storage, or the popup the action opens). `codebook_start` answers once the extension is loaded, with the manifest's `name`, `permissions` and `host_permissions`, which the chat tells you; a preparation still under way after 40 s answers its phase instead, and the chat reads the run resource until the run is ready. `codebook://help/chrome-extension` has a quick start, the configuration schema, every error code with its recovery, and three failure examples with their corrected configuration.
- **Checks before anything starts.** A start is refused, with one fixed sentence per cause, when Chrome is older than 149, the manifest is not Manifest V3, the popup or the service worker a declaration needs is missing from the manifest, a stop is in a bundled file (a source map comment, or a stop line over 1,000 characters), a stop is in a file the page or the worker does not load statically, a stop or path leaves the extension folder, or the extension folder holds a link outside the repository. A manifest that asks for permissions reaching outside the test profile (native messaging, the debugger, all hosts or private networks, for example) needs them listed in `acknowledgedPermissions`; the chat names them to you before it passes them. A stop on startup code (top-level code of the worker or the page, a `DOMContentLoaded` handler) is accepted and reported in `stopsNotReached`, since that code runs before the run is ready.
- **A Chrome of its own, with test data only.** The run's Chrome uses a fresh profile that holds only the seeded test data; your own Chrome profile (bookmarks, storage, cookies, sign-ins) is never used. The extension's own code runs as it would in any local run of it, network requests to the hosts its manifest declares included. Codebook installs the extension through Chrome's debugging protocol, never with a command-line switch, so Chrome 149 or later is needed; `codebook.chromeExecutable` can name Chrome for Testing 149 or later when your Chrome is older. The test browser's debugging port is random and bound to `127.0.0.1`, and any local process of yours can reach it while the run lives. The profile is not available on Windows in this version.
- **Clicks and pauses.** Each `codebook_action` call with `extension-click` performs the next declared click and answers its one-based `clickIndex` and an `outcome`: `paused` when a stop paused, `settled` when the work ended, `running` when it was still going after 10 s, which the chat then follows through the run resource: `chromeExtension.procedure.clickWorkPending` reads `true` until that click's work ends, and `nextActions` then offers the next click again. It also answers each step's side effect: `clickEffect: "unknown"` with `clickDispatched: false` means the press was sent and Chrome has not answered it yet, as when a stop pauses inside the click's handler. A selector that matches nothing is refused and uses up nothing. Codebook starts the service worker again before a click when it stopped, so the worker's startup and idle timing are not observed. A JavaScript dialog is answered only as the click declares; one that the extension opens by itself before any click ends the run with `DIALOG_UNDECLARED`. A pause of yours (your breakpoint, the Pause button) stays yours and Codebook never resumes it. A stop holds for up to 300 s, 280 s in the service worker; a stop held longer ends the run with `PAUSE_HOLD_EXPIRED`, and the run resource's error gives the extension run's own recovery (the extension stayed paused; the test browser closed; check whether the click changed the extension's data). Each pause lists its own `continueArguments` in the run resource. The run keeps the bytes of the manifest, the surface page and every stop file as they were at its start: a change of one of them on disk or in an unsaved editor buffer (also one opened through a link to it) ends the run with `SOURCE_CHANGED` before its next step, also between two inputs of one click; when inputs were already typed, the failure names the input the click stopped before.
- **One surface, the extension's own worker.** The debugger attaches only to the page the run opened. A copy of that page the extension opened itself, as an install handler opens its full page in each fresh test profile, is closed right after the run opens its own page (which loads after the seed), and `chromeExtension.interventions` lists that close as `close-duplicate-surface-page`. A second tab that still matches the surface's address (its hash route aside), or no tab there, makes the attach refuse with `SURFACE_NOT_ATTACHED` instead of guessing which tab is the surface, and a worker session is taken for the extension's service worker only while the test browser lists that worker, and no other service worker of the extension, at the address its manifest declares; otherwise the run reports `SERVICE_WORKER_NOT_ATTACHED` and leaves the other worker alone. A release that cannot stop a debug session writes the cause to the run's journal as a debugger error and still removes its listeners; a later stop retries that session, and a debug session the editor starts only after the run ended is stopped too.
- **What the run reports.** The result is read once before the first click and again after the last click, once no stop is paused and none was reached for a second. It reads `changed`, `unchanged`, `missing` or `unavailable` (with its cause); values under secret-like keys (`token`, `secret`, `password`, `apiKey`, `authorization`) are masked, and an observed storage key with such a name has its whole value masked and private paths hidden. The run is `claimable` only when it completed and the result was read; the chat reports a result as observed only then, and never says the clicks caused a result that did not change. A run with a stop not reached reads `partial`. The surface closing or leaving the extension ends the run with `SURFACE_LOST`; when that happens after the last click, a storage result is still read, while a text or popup result reads `unavailable`.
- **The Application view** shows the popup at its own size whatever the editor's zoom, scrolled by wheel or keyboard when the pane is narrower or lower than the popup (nothing of it is cut off), or the extension page. Its header names the extension and the surface (`codebook · <name> · Extension popup`), then the phase, then `Operated by chat · Test profile · seeded data` followed by the recording state: `Recording for replay` while the history records, `Recording partial · <code>` once a part is missing (the live run goes on; the code is the first missing part, see **When an Extension replay is partial**), or `Not recorded · <reason>` when the history could not start, for example `Not recorded · Study library is full`. At a stop it shows the frame of that moment; `Popup closed` or `Page closed` dims the last frame when the surface is lost, and that dimmed view stays after the run like an ended run's. When the run ends, its last captured view stays, marked `Run ended · last captured view <hh:mm:ss>` with the result line, until the next run's view replaces it or you close the tab. It opens also when you start the run from Cursor's Agent chat while the first editor group is empty or shows a preview, and the chat gets the keyboard back as soon as the view stands, also in Cursor 3.27, which keeps reporting a group of the main editor as the active one while the chat's input has the keyboard; Codebook tells you once that it gave the keyboard back to the chat. A preview tab you have in front, such as an image opened by one click, no longer keeps the Application view from opening: the view opens in its own group and the tab stays a preview. When the editor's layout still keeps the view from opening, the run goes on without it and the run resource gives the reason in `chromeExtension.viewUnavailable`; follow the step the reason names, then start a new run. At a stop, the stop's file, when the editor opens it in front of the view (Cursor opens it in the view's locked group), moves to the editor group beside it at the stop's line, so the view and the stopped source stay visible together. Cursor 3.27 keeps that tab a moment after it opens it; a kept tab moves too and stays kept, while a tab of it you edited there stays where it is. Cursor 3.27 lists the view's own tab as a preview after the view moves into its group, so when a run starts the view's tab is kept open; otherwise the file the debugger opens at the first stop would replace the view and end the run. The Application view of every profile uses the editor's font and font size.
- **A repository run's Application view** stays in front at each stop in Cursor too: when the editor opens the stop's file in front of the view (Cursor opens it in the view's locked group), the file moves to the editor group beside it at the stop's line, as for an extension view, and the view comes to the front, so a run no longer ends with `Application ownership changed. Use Codebook: Focus Application or Restore layout explicitly.` at its first stop. A file that is no declared stop file, and a tab of it you edited, stays where it is. This was shown with a Vite run in a native Cursor 3.27.22 trial of Cycle 0064 ([Issue #162](https://github.com/laststance/codebook/issues/162), the N64p3 run; its recordings and screenshots are private); Next, test and server runs share the code path but were not run natively for it, and other Cursor versions are not verified.
- **The status bar** shows where the run stands: `Installing extension…`, `Opening the extension popup…`, `Waiting for the service worker…`, `Setting stops…`, `Waiting for chat · next click <n> of <m>`, `Clicked "<title>" (<n> of <m>)`, `Paused at stop <n> of <m> · page` (or `service worker`), `Reading the result…`, then `Run finished · stops <a>/<b> · result <changed|unchanged|missing|unavailable>`, or the refusal and what to do next. While the history records it ends with **Save learning replay** (`Recording explanation · <phase> · Save learning replay`); clicking it asks `Saving stops the extension run (<n> of <m> stops recorded, result recorded). Save now?` (or `… <n> of <m> stops recorded; no result recorded yet, so the result will not be saved). Save now?`) with **Save and stop** and **Cancel**. After the run `Recording finished · Save learning replay` saves the sealed history. After the seal one notice says `Extension replay saved.`, `Extension replay saved as partial: <first reason> (+<n> more).` or `Extension replay saved; the chat's explanation is not saved yet.`, each with **Open replay**. A run that recorded no pause or result answers `Nothing to save: the extension run recorded no pause or result.`; a run whose history could not start shows `Learning replay unavailable: <cause>`; a write that failed shows `Learning replay will be partial: <cause>` and Save still saves what was recorded before it.
- **Every way a run ends removes what it owns.** The result being read, the chat's `codebook_stop`, the 10-minute run deadline, a failure in any step, you stopping the debug session, a pause held past its limit, the browser or the surface being lost, and closing the window all end the run through one cleanup: the debugger lets go first, then the test browser ends and its profile folder is removed. A folder or a process exit the cleanup could not confirm is reported in the run resource. A stop answers within 10 s even when a preparation step does not: that step is left behind, and what it brings up later (the test browser, the view, a debug session) is closed then; until it settles, the run resource reads the cleanup as unconfirmed. A click that arrives while the run ends is refused with `RUN_NOT_READY`. A test browser that a crashed editor left behind is stopped and its folder removed by the next launch, but only a process proven to be that browser (its recorded process id, executable and profile folder).
- **Extension replay.** A `chrome-extension` run is saved as an Extension replay, and a replay never clicks anything and never loads the extension. Quick start:
  1. Ask with `/codebook` (for example, what a button in the popup does); the chat explains the clicks live, stop by stop.
  2. Save it: the chat saves through `codebook_explain_node_history` after `codebook_stop`, or you press **Save learning replay** in the status bar.
  3. **Open replay** (the notice or the row in Saved studies) opens the replay at its first recorded stop.

  The replay shows the recorded frame of the surface, labeled recorded, with how long before the stop it was taken when no frame was recorded at the stop (`Recorded frame from 1.2 s before this stop`, or `Recorded frame captured at this stop`), and while the replay moves to another moment the caption reads `Loading the recorded extension frame…`; the executed source; and in the editor's debugger a thread `Recorded page stop <n> · <path>:<line>` or `Recorded service worker stop <n> · <path>:<line>` with the recorded values. Between stops, while frames go on, it reads `Not recorded at this moment`; when two pauses were open at once it shows the one opened last. A stop resumed from the editor's debug toolbar ends where it was resumed, so the moments after it show no stop. After the editor restarts, choosing the Extension replay in Saved studies reopens it at its saved position. **Saved studies** lists it as **Extension replay** with its question, the extension's name and version, the surface and the capture state (`recording` while it records, then `capture complete`, `capture partial` or `capture interrupted`). **Delete saved study…** moves it to the Trash with its frames; it is refused while the replay records, is open or is being saved. It counts in the **Saved Study Limit**, but a full library never refuses the live run: the run goes on unrecorded and the header says `Not recorded · Study library is full`. Test and server replays still cannot be deleted here.
- **The bundled skill's extension route.** The bundled skill (since 1.0.55) sends a question about the opened repository's Manifest V3 extension to the `chrome-extension` profile only when `codebook_status` lists it, and names an unmet prerequisite (no Chrome, Chrome older than 149) instead of answering from source alone. With several extensions it asks you once which one. It checks the question against the supported subset first and explains a part that cannot run only as source reasoning; before the start it tells you the extension, the surface, the clicks, that the run uses seeded test data, the hosts the extension may reach, that the worker is restarted and startup code cannot be paused, and that the run is recorded so it can be saved as a learning replay. Since 1.0.62 the skill saves an extension run as an Extension replay (it checks that `codebook_status` reports API 1.13 first, and claims a saved replay only when `learningCoverage` is complete and `captureMissing` is empty). Since 1.0.56, when a run goes on without its Application view, it tells you so, with the reason the run gives in `chromeExtension.viewUnavailable` and the step that reason names; after that step a new run shows the view.
- **Updating to this version, or going back.** Install the new VSIX, reopen the work window and run **Codebook: Set Up AI Chat**, so Cursor's managed skill updates to **1.0.63** (VS Code reads the bundled skill directly); a skill you edited is kept, with the existing conflict guidance. After going back to 0.2.69.0 an extension run still runs live and its save is refused, while Extension replays are not listed and stay on disk, never deleted; reinstalling 0.2.70.0 or later lists them again. A VSIX older than the extension profile lists no `chrome-extension` profile, and a history recorded by a newer Codebook waits on disk unlisted.
- **Limits.** Unbundled extensions only (no source maps), no content scripts, no stop in startup code, one popup or extension page per run, one to three clicks, macOS and Linux.

### When an Extension replay is partial

A part that was not recorded stays missing: saving again cannot recover it, and the saved part stays replayable. Only a new run records it. The run resource lists these codes in `chromeExtension.captureMissing`; `EXTENSION_HISTORY_FORMAT_NEWER` and `EXTENSION_HISTORY_FRAME_DAMAGED` appear only in the Saved studies listing.

| Code | Meaning | What to do |
| --- | --- | --- |
| `EXTENSION_HISTORY_FILMSTRIP_MISSING` | Some frames of the surface were not recorded (the screenshot failed, was too slow or was dropped when the history ended). | The replay shows no picture between some moments; start a new run only if the frames matter. |
| `EXTENSION_HISTORY_PINNED_FRAME_MISSING` | The live run captured the frame pinned at a pause, but the history could not keep it. | The stop replays with the last recorded frame and its distance label; start a new run only if the exact pause frame matters. |
| `EXTENSION_HISTORY_SNAPSHOT_MISSING` | A stop has no usable debugger snapshot. | Do not rely on values for that stop; start a new run to record them. |
| `EXTENSION_HISTORY_SOURCE_UNAVAILABLE` | The executed source of a stop was not stored. | Declare stops in a smaller file in a new run. |
| `EXTENSION_HISTORY_SIZE_LIMIT` | The history reached its size limit; later entries were not recorded. | Declare fewer stops or clicks in a new run. |
| `EXTENSION_HISTORY_SURFACE_ENDED` | The extension surface or the browser ended before the run did. | Start a new run once the surface stays open. |
| `EXTENSION_HISTORY_STOP_NOT_REACHED` | A declared stop never paused. | Declare stops on lines the clicks run after the page loaded. |
| `EXTENSION_HISTORY_RESULT_MISSING` | The run ended before its result was read. | The replay claims no result; start a new run to record it. |
| `EXTENSION_HISTORY_APPEND_FAILED` | Writing the history failed. | Check the disk space and start a new run. |
| `EXTENSION_HISTORY_FORMAT_NEWER` | A newer Codebook recorded the history. | Update Codebook; the replay is listed once this version can read it. |
| `EXTENSION_HISTORY_FRAME_DAMAGED` | A frame file is damaged on disk. | That moment shows no picture; start a new run to record it again. |
| `HISTORY_STILL_RECORDING` | A save came while the run still records (the answer of a save, not a capture code). | Stop the run with `codebook_stop` or **Save and stop**, then save once. Nothing was saved and the run goes on. |

## Masked values

Codebook masks credentials before a browser or test run's values reach the chat, a saved history or the Output › Codebook channel. A masked value reads `[masked]`.

- **Masked by name.** A variable, property or header whose name ends in the word `password`, `passwd`, `passphrase`, `pwd`, `pass`, `secret`, `token`, `jwt`, `authorization`, `cookie`, `credential`, `session` or `sid` (plural too), in a key named for a secret use (`api`, `private`, `secret`, `access`, `signing`, `encryption`, `master`, `client`, `auth` or `session` key), or in `session id`, is masked together with everything inside it. Names are read as words in camelCase, snake_case and kebab-case: `accessToken`, `db_passwd`, `set-cookie`, `apiKey`, `AWS_SECRET_ACCESS_KEY` and `sessionId` are masked; `tokenCount`, `sortKey`, `publicKey`, `primaryKey` and `passwordPolicy` stay visible. An object's preview shows such a member as `[masked]` too (`{apiKey: [masked], host: 'db'}`), also when the preview writes it with a length or type first (`(2) [...]`, `Object {...}`). A type inspection shows the type and keeps no real value.
- **Masked by shape.** In any captured text, a password in a URL (`scheme://user:[masked]@host`; the user name stays), a JWT, a `Bearer` token, an `sk-` key, a Stripe `sk_`/`rk_` live or test key, a `ghp_` or `github_pat_` token, a Slack `xox…-` token, a Google `AIza` key, an `npm_` token, an `AKIA` or `ASIA` AWS key and a private-key block (`-----BEGIN … PRIVATE KEY-----` to its end) are replaced. Test output, the development server's log and errors are masked the same way, also when a secret arrives split across chunks, before any text is cut or stored. Only text that may still turn out to be a secret waits for the rest of its output; other text is released at once, so output keeps its order around a debugger stop.
- **Not masked.** Codebook has no detector for secret content: a secret held in a plainly named variable or printed as ordinary text stays visible. Public keys and certificates stay visible.
- **The native debugger is unchanged.** It is the editor's own and still shows you the real values.
- **Updating.** Values captured after this update may read `[masked]` where they showed a real value before. Studies and replays saved earlier are not rewritten.

## Study workspace

Codebook contributes `debug.focusEditorOnBreak: false` as the native debugger default, so a breakpoint can select its source and values without moving the keyboard out of the chat. This default applies to native debugging throughout editors where Codebook is enabled. At a stop Codebook did not cause (a step or a continue of yours, a refresh of the debug adapter, or a debug session that is not a Codebook run), Codebook gives the paused file the keyboard once, where the editor would without this default: only at the frame the editor's own stop handling focuses, or when the editor opens that frame's source for the stop. A stop the editor keeps in the background, or one at which it focuses no frame (every frame skipped as library code), moves the keyboard nowhere. Codebook also does nothing while a recording is open or when you set the setting yourself. Existing explicit User and Workspace preferences take precedence; Codebook writes no settings file. Set `debug.focusEditorOnBreak` to `true` in the ordinary editor settings if you prefer the debugger to focus source at a break. Disabling or removing Codebook removes its default contribution.

Open Codebook from its Activity Bar icon or **Codebook: Open Study Workspace**. An empty reader asks the editor agent to prepare a study in the open repository. It has no preselected application or executable sample. Saved repository observations retain their own source and values; **Return to Current Pause** restores live following. **Continue Inspected Pause** requires the exact currently inspected runtime pause.

**Codebook: Close Study Workspace** run in the focused window while a Codebook pane, the captured source or your own file is the active editor, or a page that is no text editor (the editor's Settings, an image) in a window without editor tabs outside the main editor area, gives the active editor group the keyboard once the panes are closed, in VS Code and in Cursor: closing the panes can otherwise leave the keyboard on no element. The first time in an editor session, Codebook says so: `Study workspace closed. The keyboard is in the active editor group now: closing the panes can leave it nowhere, and the editor does not tell Codebook whether it was in a pane, a file, the terminal, a view or the chat. If you were typing outside the editor, click there to type again.` A close made while Cursor shows its Agent chat as an editor tab and that chat has the keyboard moves nothing and shows nothing, and so does a close in a window that does not have the focus, with one exception. A close that ends an enlarged reading (the Study pane's **App**, **Source** or **Explanation** button, or **Codebook: Read Application**, **Codebook: Read Captured Source** or **Codebook: Read Explanation**) shows the side bars that reading hid again, and the editor shows a side bar only with a command that gives it the keyboard. When Codebook can tell from the editor's tabs that the chat had the keyboard (Cursor's Agent chat shown as an editor tab of the focused window, or VS Code's chat as an editor tab in a floating window), it gives the keyboard back to the chat after showing the side bars, and the first time in an editor session says so: `Study workspace closed, and Codebook gave the keyboard back to the chat: showing the side bars your Read had hidden took it. The editor does not tell Codebook whether you were typing in that chat or in the terminal or another view: if you were typing elsewhere, click there to type again.` In every other case in which that close showed a side bar, also in a window that does not have the focus, the active editor group has the keyboard afterwards and Codebook says so with the sentence above, the first time in an editor session; the editor keeps that notification in a window without the focus until you return to it. When `debug.focusEditorOnBreak` is enabled, a live pause makes the editor's debugger open the paused file with the keyboard. The first time in an editor session that a Codebook pane (the Application pane or the captured source) takes that file's place and Codebook knows of no chat to give the keyboard back to, it says where the keyboard is: `The debugger opened the paused file with the keyboard, and the Codebook pane shown in its place (the Application pane or the captured source) has the keyboard now. If you were typing in the chat, click its input to continue there: this editor does not tell Codebook whether the chat had the keyboard.` That is so in VS Code, in Cursor while its Agent chat is a pane of the secondary side bar, and in Cursor with the chat as an editor tab when you were working in a file or another tab before the pause. Where Cursor shows its Agent chat as an editor tab and that chat had the keyboard before the pause, Codebook gives the keyboard back to the chat at that pause, and the first time in an editor session says so: `Codebook gave the keyboard back to the chat editor tab after the editor moved it to another group (at a pause, to the paused file the debugger opened). The editor does not tell Codebook whether you were typing in that chat or in the terminal or another view: if you were typing elsewhere, click there to type again.` Codebook also takes the keyboard to be in a file when a click or a key press of yours moves the caret or changes the selection in it, which is all the editor reports to Codebook of a click or a key press. A Codebook pane that then comes to the front over that file takes the keyboard, because a hidden file cannot keep it, and the first time in an editor session Codebook says where it is: `A Codebook pane (the Application pane or the captured source) came to the front over the file you were working in and has the keyboard now: a hidden file cannot keep it. Click where you want to type.` That holds at a pause for a frame you selected in the Call Stack view and for a stop while the editor's `debug.focusEditorOnBreak` setting is off, where a file you go to and a frame's file you open with a double click count too, and while the debugged program runs, where only such a click or key press of the last three seconds counts. Three gestures at a pause give a frame's file the keyboard without the editor telling Codebook: the editor's **Navigate Up Call Stack** and **Navigate Down Call Stack** commands by themselves (and the two that go to the top and to the bottom of the call stack), a double click or Enter on a frame whose file is already open as a kept tab, and Enter on a row of the Call Stack view that is not the selected frame yet. A click on the place where the caret already stands moves nothing, so the editor reports nothing of it and it does not count, at a pause and while the program runs. After one of these, the next Codebook pane (the Application pane or the captured source) that comes to the front over that file comes without the keyboard, which is then on no element. Move the caret in the file before that (press an arrow key, or click on another place than the caret stands), so that Codebook knows you work there, or click where you want to type afterwards.

When a live run ends with the Study workspace closed and its Application pane active in the focused window, Codebook closes that pane and gives the active editor group the keyboard. Once in an editor session it says: `The run ended and Codebook closed its Application pane. The keyboard is in the active editor group now: closing the pane can leave it nowhere, and the editor does not tell Codebook whether it was in the pane, a file, the terminal, a view or the chat. If you were typing outside the editor, click there to type again.` An inactive pane or unfocused window gets no focus command or notice. Disposing the reader also restores active-group keyboard focus in the focused window when it closes its active pane or captured source, with the Close notice above; disposal beside your own file preserves the keyboard.

Learner understanding is an explicit saved choice. Running, recording, replaying or generating an explanation never marks it automatically. Current-file opening verifies the repository citation. Closing the reader stops owned execution and drains its final writes while preserving unrelated tabs.

## Recorded walkthroughs

Recording starts before a configured repository run acquires its application. Saved films open independently of live execution and retain original source/interpretation timing. Missing frames or source context remain explicit. Historical files in retired formats are preserved on disk and listed as unavailable; they cannot start an application or be silently converted into repository evidence.

Opening saved learning starts a read-only **Codebook · Recorded learning** debug session: the editor's own debugger shows the recorded source, scopes and call stack of the selected moment. The top frame names its recorded source and line. A frame below it names the file the debugger reported for it and its line (a path is kept only inside your workspace, otherwise the file name alone) in a muted entry; selecting it opens a short text that begins `Not recorded at this moment` and says the executed text of that frame was not recorded, never your current file. A frame the debugger gave no file for keeps "Unknown Source", and a replay saved by an earlier Codebook shows no file for its lower frames. These lower frames were shown in native trials of Cycle 0064 ([Issue #162](https://github.com/laststance/codebook/issues/162), the N64p3 run; its recordings and screenshots are private) with a Vite run's replay in VS Code 1.144.0 and Cursor 3.27.22, and in a native trial of Cycle 0065 ([Issue #166](https://github.com/laststance/codebook/issues/166), the N65 run) with a Next Pages Router run's replay in VS Code 1.144.0, whose Call Stack named the page's own `src/…` frames; Next App Router, test and server replays use the same capture and debugger session but were not checked natively for it. Once native Run and Debug receives a recorded stop, the moment waits up to one second for it to load the stop's values. If Variables is collapsed or hidden, or another stopped session is selected, the moment still appears and Study shows the hint `Recorded values for this moment are not loaded yet. Show Variables opens Run and Debug and expands them; if the first scope stays closed, expand it. If Call Stack lists several sessions, select “Codebook · Recorded learning” first.` with a **Show Variables** button below it. One press opens Run and Debug, focuses Variables and expands its first scope, which lists the recorded values; a host without a command for it gets `Open Run and Debug and expand Variables to see the recorded values.` instead. Later moments do not wait again until values load; the hint and the button then clear. Ending the **Codebook · Recorded learning** session or closing the reader also clears it. Unrecorded gaps, stops without recorded scopes and stops whose only Variables group is the recording-limitations note appear at once with no hint. Saved Node test stops show the same hint and button beside their position. A Node stop reads `Recorded source unavailable for this stop.` only when its captured source does not match the stop; ending the session, opening a recording or reopening the reader no longer adds that line. Cursor lists the scopes of a collapsed Variables without loading values, which is why the hint names the first scope.

A slow start does not fail a replay. Loading a recording and starting or retiring the historical session do not count against the five-second paint bound; that bound applies to each frame's painting, and a presentation that never reaches painting ends after 23 seconds. If the editor needs more than five seconds to start the historical session, the moment that waited for it fails, and the session is adopted when its start completes: the next moment is presented without reopening the recording. A session you stopped meanwhile is not adopted. If the editor does not stop the historical session within five seconds, the session becomes unavailable and reopening the learning replay starts a new one. Closing the reader does not wait on the native debugger or on a frame that never paints beyond those bounds. It waits at most five seconds in all for its pending storage writes (a running study's final checkpoint, the saved replay position, the archive writes and the library queue); a write still pending then keeps running and the reader closes.

**Open replay** pressed while another window has the desktop focus waits up to 10 seconds for the Codebook work window to gain the focus and then opens the Learning summary. When the focus does not come, the replay is refused with `Focus the Codebook work window before reading the learning summary: another window kept the desktop focus for 10 s. Click in this editor window, then choose Open replay again.`, and the status bar's **Open replay** shows that reason as a notification (`Codebook could not open the learning replay: …`) and writes it to **Output › Codebook** as one `open:recording` entry with the study, the profile and the cause. A browser replay whose open fails for any other cause (its recording could not load, for example) also writes one `open:recording` entry beside the load-failure notification, so you can copy the cause into a report.

The Learning summary has its own icon in the Activity Bar in both editors (an open notebook with a check mark, unlike the book of Codebook's own container, so the two are told apart), because Cursor rejects the secondary side bar container an extension contributes. In Cursor it opens in the primary side bar. In VS Code, the first time you open a replay yourself in a profile (never an agent's open), Codebook moves the summary once into the Chat container on the right with VS Code's internal `vscode.moveViews` command; a place you choose afterwards is never changed back, and if the command is refused or missing the summary stays in the Activity Bar and Output › Codebook says so. Nothing is offered in VS Code. Once per editor session, until you have taken the step in that workspace, Cursor shows the notification `Cursor opens the Codebook Learning summary in its primary side bar. To keep it on the right, move it once: choose "New Secondary Side Bar Entry" in the list that opens.` with the button **Move Learning Summary…**. Cursor removes an unanswered notification by itself, so the same step stays within reach as the title action **Codebook: Move Learning Summary…** of the Learning summary view and under that name in Cursor's Command Palette. Each opens the editor's own Move View list for the summary. When **Show Variables** opens Run and Debug in the side bar the summary shares, the offer reads `Run and Debug took the Learning summary's place in Cursor's side bar. Move the summary to the right once to keep both in view.`, with the same button, at most once per editor session.

**Hiding and showing the Learning summary.** During a replay of either family, the bottom panel's transport ends its status row with a **Learning summary** button (its tooltip and accessible name: `Show learning summary`). When you have hidden or collapsed the summary, or closed its container, the button shows it again; when it is shown, the button brings the keyboard to it. Hiding and showing it keep the selected moment, the replay debugger's frame and the summary's scroll position, a paused replay stays where it is and a playing one goes on playing; the keyboard returns to the control the summary last held, or, when that control is gone, to the moment's step heading or the summary's title. **Codebook: Show Learning Summary** in the Command Palette and the summary's own Activity Bar container do the same, also while the bottom panel is hidden. In VS Code the summary shares the Chat container on the right: collapse the Chat section by its header to give the summary the whole side bar, and the same click expands the Chat again. In Cursor, take the Move View step described above once, so the summary stands on the right with the Agent chat one tab away. The editor's own view commands still move or hide either view as you like. A development build of Cycle 0051 was checked by hand in VS Code 1.142.0 and Cursor 3.27.12 (hiding the side bar and pressing the button kept the moment and the reading position in VS Code; the button showed the summary in Cursor's side bar); the recorded native round of this release (N51: its VSIX, requests and take SHA-256 values) is in [Issue #122](https://github.com/laststance/codebook/issues/122), and its recordings stay in private storage.

Bounded installed development trials in VS Code 1.139.1 and Cursor 3.23.5 ([Cycle 0032](https://github.com/laststance/codebook/blob/643253b46b28793d5c57e322d44069756b925779/docs/cycles/0032-inspection-hints.md)) observed the hint about one second after the native stop and its removal once values loaded. Trials in VS Code 1.140.0 and Cursor 3.23.10 ([Cycle 0033](https://github.com/laststance/codebook/blob/643253b46b28793d5c57e322d44069756b925779/docs/cycles/0033-presentation-liveness.md)) observed that the first recording open after an editor start commits, and that both editors now keep the first Variables scope closed until it is expanded, after which the values load and the hint clears. In VS Code a saved Node stop showed the same hint, kept its position label after its session ended and could be inspected again. The foreign debug-session case is only partly verified (one running session in VS Code), and the saved Node stop is not verified in Cursor. This bounded development reader is not completion of the approved synchronized native-debugger time-travel replay. That remains an explicit implementation gap in the product state.

Retry after one completes.` is answered only while all eight have a request in flight: retry then. The replaced client's next request is answered `404` with `Unknown MCP session. Initialize a new transport, then read codebook_status.` A client `DELETE` releases its transport only. It does not stop a study.                                                                                                                                                                                                                                                           |
| `NODE_SERVER_SOURCE_REFUSED`                       | The `node-server` profile refused a declared path (`packageRoot`, `entry` or a stop's file) or the repository's own `tsx`: missing, or outside the repository by its real path. Correct the declared path or install the repository's dependencies, then declare the run again; `codebook://help/node-server` lists every code.                                                                                                                                                                                                                                                                                                                                                                                            |

GET `/mcp` returns 405; this service provides JSON POST responses and polled resources, with no standalone notification stream. The pinned SDK client supports this. Idle transport sessions expire after five minutes; live application execution has its own deadline.

Run resources distinguish current control state from historical snapshot/source/PNG/explanation references. Snapshot reads never create live pause authority. Events are paged (50/page) with a next URI and explicit detail truncation. Runtime source resources are sealed TS/JS/map bytes; they remain readable after the application and debugger exit. Repository reads accept only validated relative paths within the selected tracked-source boundary. No API accepts executable JavaScript, shell commands, arbitrary filesystem access or editor command names.

Resource identity is validated after the MCP SDK's URL normalization. Safe dot-segment aliases can resolve to the same canonical resource; they do not bypass instance/study/hash checks. Clients should follow returned canonical URIs.

Limits: 8 MCP sessions (a ninth client replaces the least recently seen idle session, a session with no request in flight; `429` is answered only when all eight are busy), 32 concurrent HTTP requests, 1 MiB + 64 KiB HTTP envelopes (separate from the 1 MiB book-document cap), 8 KiB headers, 5 s body reads; 1 active/16 retained runs per instance, no history eviction (from 0.2.22, when all 16 are taken the oldest run that was refused at the study-library admission, or whose saved study you deleted, gives up its place; such a run holds no history; a stopped server run gives up its place only when no such run is left); an explanation budget of 32 keys/run (a key Codebook already accepted answers its receipt again, and a new key is refused once the budget is spent), 8,192 characters and up to 10 distinct captured paths; PNG ≤8 MiB. Configured runtime source resources allow TypeScript ≤256 KiB, the selected JavaScript module ≤8 MiB and its source map ≤16 MiB; build discovery reads selected-route webpack chunks ≤32 MiB each, ≤128 MiB total, ≤2,048 candidates and ≤30 seconds, and a Pages run refuses a chunk path holding a `.` or `..` segment, so it never requests a file outside the server's `/_next/` folder. Discovery and `codebook://help/repository-browser` expose the source and chunk limits through `profile.limits`. Evidence buffering is capped at 10,000 events / 4 MiB retained event bytes / 16 MiB pending writes. Overflow is an explicit failed run followed by owned cleanup.

### What a lock or an update marker cannot tell

Two files keep editor windows from writing at the same time: `writer.lock` in each private storage folder (the learning storage, the Cursor skill and its catalog) and the marker of a running Wiki update beside the Wiki folder ([LLM Wiki: open and update](#llm-wiki-open-and-update)). Between windows of this build a lock, a marker and the claim a window holds for the moment in which it removes or replaces one of them are judged by the start of the owner's process. The limits:

- **A window of 0.2.29.0 on the same storage or project folder.** That window writes and judges as 0.2.29.0 did, so beside it the guarantees are those of 0.2.29.0. Its lock, its marker and its claim name no process start: this build judges such a lock by its process id and its boot, such a marker by its process id alone, and removes such a claim once it is 60 seconds old, or sooner when the claim names this machine and no process has its process id. The older window judges the files of this build in its own way: a lock or a marker whose process id went to another process stays for it, where the boot is a computed time (Windows, and a Mac whose window could not read its boot session) a clock set forward by more than a minute while a lock is held can make it take over that lock although its writer still runs, it removes a claim after 60 seconds although the claim's window still runs, it creates its marker in place, so that the file is empty for the time of one write, when it finds no marker under its claim it removes the marker another window has just written, and it follows a link at the path of the marker's claim (`<marker>.takeover`, which a cloned repository can carry): each time it asks for that claim it deletes the files directly in the folder the link leads to that were last changed more than 60 seconds ago. Update every window to leave these limits behind.
- **Another host, another system.** A lock or a marker written on another computer is not judged by a process here, and neither is a marker, or a lock that records its writer's process start, written by an editor of another system of this computer (a Windows window beside a WSL window), because its process id means another process there. Such a lock stays until you move it away; such a marker counts until its run's longest time has passed at the latest, and a claim on it for 60 seconds. For a marker and its claim, another pid namespace of this computer (another WSL distribution, a container) is such a system too, and so are a window that could not read its own process start and a Linux window that could not read its own pid namespace.
- **A Wiki publish in a place that cannot come back.** While the skill's publisher publishes a Wiki, it keeps a publish lock and a journal beside the Wiki folder that name its process id, its host name, its space of process ids (on Linux, its pid namespace), its boot and a digest of the computer's id (the machine id in `/etc/machine-id` on Linux, the hardware UUID on a Mac, the machine GUID on Windows), never the id itself. A `--render-only` preview keeps the lock alone, and a publish or a preview that stops leaves its lock, which `--recover` judges and ends as it does a journal. A `--recover` refuses the lock or the journal of another host name or another space, because it cannot look at that process, and tells you to run it there. A Mac that took another host name from the network under the same boot is still this computer, because the lock and the journal name its boot session. A lock or a journal of this host name and another boot counts as this computer's before a restart only when it names the digest of this computer's id: without it (its publisher could not read the id) or with another one, it may as well be the record of another computer with the same host name, and `--recover` refuses it too. A journal of 0.2.30.0 names no owner at all, and `--recover` judges it by its process id alone, as that version did. A lock or a journal of this host name that names the digest of another computer's id is that computer's, whatever its boot, and `--recover` refuses it as well, unless it names this boot's id: then it ran in another space of this computer (a second WSL distribution, or a container, that keeps a machine id of its own), and `--recover` tells you to run it there. On Windows, which names its boots by no id, and on a Mac whose boot session could not be read, no boot tells the two computers apart: there `--recover` probes the process id of a lock or a journal of this host name only when it and the recovery name the same digest, and refuses one where either names none (`reg.exe` or `ioreg` could not be read) as one it cannot prove was this computer's. The digest tells two computers apart only where their ids differ: a computer cloned with its id (a virtual machine copied without a new machine id, Windows copied without sysprep) counts as this one. On Linux the id is `/etc/machine-id` alone, so a system without it (a container without systemd) names none, and its lock or journal of another boot needs the pair once. A place that cannot come back keeps the Wiki locked: a rebuilt dev container, which gets a new pid namespace under the same boot, or a computer that is gone. So does a space that names no pid namespace: a Linux publisher that could not read its own records the space `linux@`, which no recovery can look at. Make sure that no publisher runs there, then run `--recover` with `--gone-host "<host>" --gone-space "<space>"`, set to the host name and the space that the refusal names, each between double quotes, which a POSIX shell, PowerShell and `cmd.exe` all take as quotes (`cmd.exe` keeps single quotes as part of the value): the recovery then takes that publisher for gone, except one of this host name and space whose process id and start a live process on this computer has: it probes that process id too, and refuses while that process runs. If a stopped recovery ran in a second such place, the next refusal names it: add it as one more `--gone-host` and `--gone-space` pair. Where a lock or a journal stands, the publisher refuses a pair that names no place it or its stopped recoveries record; where neither stands, it refuses a pair that names no place of a stopped writer that a file beside the Wiki folder names (the file through which a lock, a journal or a recovery's claim was to get its name, or a recovery's claim that no lock or journal leads to any more), and the recovery then removes that file. It refuses a lock or a journal whose host name or space is not in the form it writes, and never uses the options without you.
- **Another user's process on Linux.** A window reads the start of a process in `/proc`. On Ubuntu's default `/proc` it reads the start of another user's process as well, so a process id that went to another user's process is judged by its start like any other. Where `/proc` is mounted with a `hidepid` option such as `hidepid=2` (a hardening that Ubuntu does not set by default), the start of another user's process cannot be read, and a lock or a marker whose process id another user's process has now is taken for one whose writer may still run: such a lock stays until you move it away (make sure that no Codebook window on any host or system still writes to this storage, then move the named file away and retry), and such a marker counts until its run's longest time has passed.
- **Two computers that share an editor's machine id.** The editor keeps its machine id in its user data folder, so two computers that share a home folder (a network home, a copied profile) have the same one. A lock, a marker or a recording that names this machine id under another host name counts as this computer's only when it also names the boot that is running by its id: the kernel's boot id on Linux, the boot session on macOS. The time a computer started proves nothing here, since two computers can start within the same minute, and Windows names its boots by no id: there such a record counts as this computer's only under the same host name. Otherwise it counts as another computer's: such a lock stays until you move it away, and before Delete moves such a recording it asks you. The same holds for a window that was killed before a restart, on a computer whose host name changed since (a Mac takes it from the network).
- **Two computers with one host name.** A marker names its machine by digests, and the digest of the host name is the one VS Code and Cursor on one computer share. On Linux and macOS the marker also names the boot by its id, so a marker with this host name, another editor's machine id and another boot is another computer's: it counts until its run's longest time has passed, and a start beside it is refused. The price: a marker that the other editor of this computer left before a restart counts in the same way. Where a boot has no id (Windows, and a Mac whose window could not read its boot session), and where the two computers also share an editor's machine id (a shared home folder), two computers with the same host name on one shared project folder look like one machine to the marker: each judges the other's marker by its own processes, and a second update can start beside a running one.
- **Clocks.** The marker's times allow the clocks of two windows, or one clock before and after a correction, to differ by 5 minutes. Computers whose clocks differ by more, a clock that moves by more during an update and a computer that sleeps for longer during one are not covered: a second update can start beside a running one.
- **A file system without hard links.** A lock or a marker is written beside its path and then linked into place, so it never exists without its content. Where the file system cannot link, the file is created in place and is empty for the time of one write. Another window takes an empty marker younger than 2 seconds for one that is being written and refuses its own start, which narrows that race without closing it.
- **A suspended window.** A window that is suspended in the instant between the check of its claim and its change of the marker can still remove or replace a marker that another window wrote meanwhile.
- **Systems observed.** The judgement by the process start was observed in editors on Linux, for the update marker: the marker of a killed window did not refuse the other editor's start. On macOS and in a Windows editor it has not been observed, for a lock or for a marker: tests cover it there, for Windows on a Windows runner and for macOS with a stand-in for the `ps` query.

### Saved learning capacity

**Codebook: Saved Study Limit** (`codebook.savedStudyLimit`) controls new study and recording admission for the opened workspace: 64 by default, configurable from 1 to 256 in ordinary editor Settings. Changes apply without restarting. When full, raise this setting or delete a saved study (below) before starting a new recording; use **Retry storage / refresh** to retry an existing study checkpoint. From 0.2.21, a configured run started while the study library is already full is refused before the application receives any input: the run ends with `PREREQUISITE_MISSING`. A recording that never started cannot reconstruct missing video afterward. Extension replays count in this limit and, unlike test and server replays, can be deleted from Saved studies.

A `node-test` start at full capacity is refused before its test is listed or launched, with the same sentence as below (typed `PREREQUISITE_MISSING`), and `codebook_status` then reads the `node-test` profile as `ready: false` with the count and the limit. Test replays cannot be deleted from Saved studies yet (their **Delete saved study…** button says so), so to make room raise the setting or delete a browser study.

From 0.2.22 the refusal names what you can do at your limit:

- below 256: `Study library is full. Increase Codebook: Saved Study Limit (codebook.savedStudyLimit) in Settings, or delete a saved study from Saved studies in the Study workspace, before starting another run. Only the learner can do either; an editor agent cannot. Existing learning was kept.`
- at 256: `Study library is full at its maximum of 256 saved studies. Delete a saved study from Saved studies in the Study workspace before starting another run. Only the learner can delete a saved study; an editor agent cannot. Existing learning was kept.`

The messages for a study that cannot be saved and for a recording that cannot start follow the same pattern (`…then retry storage.`, `Recording library is full…delete a saved study that has a recording…`). A refused run is not saved later either: it leaves no study behind, the Study pane shows `The last run did not start: <message>` without offering **Retry storage / refresh** for it, and its run resource reports its history as unavailable. A limit setting that is not an integer from 1 to 256 also ends a run with `PREREQUISITE_MISSING` and `Set Codebook: Saved Study Limit (codebook.savedStudyLimit) to an integer from 1 to 256. Existing learning was kept.` The check at the start of a run reserves nothing: when two editor windows of the same workspace each start a run for the last free place, both starts are accepted, and the study saved second is refused at its save with the `…then retry storage.` message; raise the limit or delete a saved study, then use **Retry storage / refresh**. The start of a Node test is different: it takes the storage lock (`writer.lock` in the learning storage) and reserves its history under it, so of two windows that start a test for the last free place one is refused with `PREREQUISITE_MISSING` and the sentence of the study library above. While the saved studies and the test histories fill the limit, `codebook_status` reads the `node-test` profile as not ready and its `missing` sentence names the count of taken places and the limit, so an editor agent does not prepare a start that would be refused; only the learner can raise the setting in the Settings of the running editor profile or delete a saved study, and a test replay cannot be deleted from Saved studies yet. The limit is shared in both directions: the save of a new study, the check at a run's start and a recording's start count the test histories too, so while the saved studies and the test histories fill the limit a new run or study is refused with the study library's sentence above, as a test start is. A start that meets the lock while another window holds it, or a lock that stays, is refused with the storage lock's sentence, which [Delete a saved study](#delete-a-saved-study) quotes and explains; nothing was written then, and the test was not started.

- What is left of a study whose archive was removed (its catalog file, or a recording that no editor of this computer still writes and whose study no other editor window of this computer may still save) stays in the list with `Archive missing; remaining files kept` in its label, so that the rest can be removed: **Delete saved study…** moves it to the Trash, and in a window without a Trash **Remove by hand** lists its files. A recording that names another computer is listed too, and so is one whose editor Codebook cannot tell from another program of this computer; for such a recording **Delete saved study…** asks first, as the next point says. Such an entry can be chosen and not opened, it has no **Repair saved study**, a reader that starts neither selects it nor shows it first, and it takes no place of the saved study limit. The finished recording of a run of this window whose archive could not be saved yet is listed with the same words; that study has not left the library, and **Retry storage / refresh** writes its archive.
- When a recording of the study may still be in use on another computer (an editor window there still records it, or has finished it and not saved the study yet), Codebook asks once more after **Move to Trash**: `This study's recording may still be in use on another computer. Move the study to the Trash anyway?`, with the detail `Its recording was started on <host> at <start>. Codebook cannot tell from this computer whether an editor window still records it or still has to save it. If a window still records it or still has to save it, on that computer or on this one, the recording is lost. If none does, nothing is lost. Cancel keeps the study and its recording as they are.` **Move to Trash Anyway** moves the study with its recording; **Cancel** keeps both as they are. When the recording names this computer but Codebook cannot tell its editor from another program (the editor's process number now belongs to a program that started later, or to another user), the dialog reads `This study's recording may still be in use in another editor window. Move the study to the Trash anyway?` and `Its recording was started on <host> at <start>. Codebook cannot tell whether an editor window of this computer still records it or still has to save it. If a window still records it or still has to save it, the recording is lost. If none does, nothing is lost. Cancel keeps the study and its recording as they are.` When Codebook could not read the files of the recording at that moment (a virus scanner may hold them, or a file is damaged), it lists the study in the same way and cannot name a host or a start: the dialog reads `This study's recording may still be in use in another editor window. Move the study to the Trash anyway?` and `Codebook could not read the files of its recording now. A virus scanner may hold them, or another editor window may still record it or still have to save it. - When another editor window of this computer is still recording the study, or has finished its recording and not saved the study yet, nothing moves and the line reads `The saved study could not be moved to the Trash. - A cause that names the storage lock (`Learning storage is locked by another writer or an interrupted session (lock file: <path>). A lock whose process is gone on this machine (an editor that was killed) is taken over by the next write, by one window at a time, and causes no refusal. The lock records its writer's process id and when that process began, with the host name, two digests that stand for the machine and the boot, and a window of this build judges it by that start: a lock whose process id another process has since is taken over as well, because that process began at another time. For a lock that stays, make sure that no Codebook window on any host or system still writes to this storage, then move the named file away and retry ([What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits). When the lock could not be released after every file had moved, the study is deleted and the line says so; the pane additionally shows `Learning storage lock could not be released after the removal: <cause>` among its errors, and other windows can be refused until the lock is resolved. The window that could not release it takes it back by itself: five seconds later, again every five seconds for about a minute, and at its next write. A lock that its release left in place because the system would not let the window read its owner is named the same way, as is one that the removal of the lock refused. When the window's tries to take the lock back have not removed it, the next write's refusal adds that this window itself left the lock, with the way out (close the program that holds the file, then retry, or move the file away). When the lock is an empty file older than 10 seconds in a folder that takes no new file (a full disk, a read-only folder or a quota), the refusal adds that the clock of the file system cannot be read and what to do (make room or write access, then retry, or move the file away); such a lock is kept on purpose. A write that was made but whose lock could not be released is not reported as failed.
- When the next study cannot be arranged after a removal (for example while a presentation change is pending), the removal's line is shown all the same, no study is shown and the pane's errors name the reason; choose a study in **Saved studies** to continue.
- The delete button waits only while the entry you chose is opening. A choice the reader could not open (it names the reason among its errors) puts the list back on the study that is shown.
- A run the library refused can be started again with the same request once there is room: the agent repeats its `codebook_start` with the same key and a new run begins.
- Not covered yet: test replays, removing several studies at once, and a study whose run is still held by another window of the same workspace.

Existing studies, recordings and learner decisions are never evicted. Lowering the limit does not hide existing history or prevent updates to a previously admitted study. The fixed catalog ceiling is 256; per-recording frame/byte limits remain unchanged. Raising a count limit permits more disk use, not larger individual recordings.

### Recording capacity

Recordings retain the 50 ms sampling policy, with up to 12,100 frame entries, 512 MiB of unique PNG data, an 8 MiB journal and 544 MiB total storage per recording. These budgets accommodate ten minutes of the measured 720×640 animated application workload (roughly 33 KiB per frame), including up to eight source/debugger stops. They do not guarantee ten minutes for every image size or workload. Pending writes remain limited to 8 MiB; larger images, slow storage or exhausted budgets produce an explicit partial recording with a readable verified prefix. Existing recordings are not rewritten, and missing frames are never synthesized. Storage usage accumulates across saved recordings.
