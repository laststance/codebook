## Set up editor AI chat

The same VSIX includes `skills/codebook/SKILL.md` with its version in the skill frontmatter. VS Code registers it through `contributes.chatSkills`. Cursor's setup command installs those exact bytes to `~/.cursor/skills/codebook/SKILL.md` only when the target is absent or an existing directory is empty, or updates a skill whose file identity and bytes still match Codebook's private ownership receipt. The VSIX manifest records the packaged file's SHA-256. A pre-existing nonempty unowned directory, later manual edit, symlink or mismatched receipt is preserved and reported instead of overwritten.

1. Install the **same identified** preview VSIX in the editor being used, then open the intended trusted local Git repository in a **new** dedicated work window. If that repository was open while updating the VSIX, save its work, close only that work window, and reopen the repository in a new window. Keep other work windows and files intact.
2. Run **Codebook: Set Up AI Chat** in that window. VS Code starts its workspace-local server and advertises it through its MCP provider. Cursor installs the bundled user skill and registers a local stdio bridge for this window's authenticated MCP instance. To wake Cursor's MCP catalog after dynamic registration, setup updates only the modification time of an existing nonempty `~/.cursor/mcp.json`, preserving its bytes; if absent, it creates a private `0600` file containing `{"mcpServers":{}}` and records that exact file's identity in private extension storage. An existing empty file is preserved and reported for inspection before retrying setup. It does not add a static Codebook server or place a credential in the skill, MCP configuration or chat.
   For the tested VS Code 1.139.1 / Copilot 0.67.0 client, configure [inline image transfer](#copilot-image-transfer) before a runtime question.
3. In Cursor, check **Customize > MCPs** for the connected Codebook entry with 16 tools and 6 resources before chatting. Setup records a registration request; its notification alone does not prove Agent has those tools. If the entry is absent, save and close only the dedicated work window, reopen this repository in a new window, and recheck; run setup again if the extension reports a failed reconnect. Then open a new Copilot Chat (VS Code) or Agent chat (Cursor), choose `/codebook` from the slash list, and ask a natural source/runtime question. If the skill is not visible in Cursor, reopen that dedicated window and use the same workspace. Check that the AI's first Codebook call is `codebook_status` for this repository. A general source explanation without Codebook calls is not runtime evidence. If the chat cannot open a returned `codebook://` MCP resource URI, it should use `codebook_read_resource` with that exact URI; this reads the same guarded help, run, manifest, snapshot, recording or image content through a tool.

   `codebook_status.build.dirty` reports whether the packaged Codebook extension source differed from its recorded revision. `workspaceGitStatus: not-inspected` means that status call did not check the selected repository for uncommitted changes; confirm that separately before describing its Git state.

4. To remove a Codebook-owned Cursor user skill, run **Codebook: Remove Managed Cursor Skill** and confirm the shared-user-skill warning. This also retires the empty `~/.cursor/mcp.json` only when Codebook created and receipted that exact unchanged file. A pre-existing, edited, replaced, symlinked or older unreceipted config stays in place; removal does not erase other MCP entries. **Codebook: Restore Managed Cursor Skill** repeats setup and creates a new receipted empty config only if none exists. If another skill is present under the name `codebook`, Codebook will not replace it: the refusal names its folder, and that folder is yours to keep. Rename that folder to keep the skill beside Codebook's, or move it elsewhere, then run **Codebook: Set Up AI Chat** again; as long as it stays where it is, Codebook installs no skill. A skill file that was edited or replaced after setup is left alone too, as long as it is there: delete or rename that file, then run the command again; setup then installs Codebook's skill again, and the removal finishes. A previous owned skill version and an explicitly retired empty config are retained privately during managed changes.

A Cursor setup/update/removal that an editor or process crash interrupted leaves its `writer.lock` behind. A lock whose process is gone on this machine is taken over: the next setup, update or removal removes it by itself, one window at a time, and resumes the journal. The lock records its writer's process id and when that process began, the host name, two digests that stand for the machine (of the host name, and of the editor's machine id where the window has one), the boot and, in a local window, the editor's machine id. A window of this build judges a lock that names this machine by the start of its writer's process: the lock counts as left behind when no process has its process id any more, when the process that has that id now began at another time (the id went to another process), or, on Linux, when the lock names another boot of the kernel than the running one. A correction of the clock changes none of this. A lock without a process start (written by 0.2.29.0, or by a window that could not read its own start) is judged as 0.2.29.0 judged it, by its process id and its boot. A lock that was created and stayed empty for 10 seconds counts as left behind too. A lock stays when its writer may still be alive: a process that still runs, a lock written on another host (a home directory shared between machines), a lock written by an editor of another system of this computer (a Windows window and a WSL window that reach the same file: they share the host name, and a process id of one names another process, or none, in the other), or a file without a readable owner record. [What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits. The operation then fails with `Learning storage is locked by another writer or an interrupted session (lock file: <path>). No data changed; retry after resolving the lock.`, where `<path>` is the lock file. For such a lock the manual steps remain: preserve the skill/config and their private recovery records. Save open work, close every window using that Cursor profile, and inspect the named file, `User/globalStorage/laststance.codebook/cursor-skill/writer.lock` or `User/globalStorage/laststance.codebook/cursor-mcp-catalog/writer.lock` under that profile's user-data directory (the default macOS profile is under `~/Library/Application Support/Cursor/`). Confirm on the host the lock names that the process with its `pid` has exited (Activity Monitor on macOS); if the process is live, missing from the file or uncertain, leave the lock untouched. With the profile closed and that process confirmed gone, **move** `writer.lock` to a distinct retained name in the same private directory, then reopen the intended workspace and run **Codebook: Set Up AI Chat** to resume either journal. Keep the moved lock for diagnosis. Do not delete a pending or removal record, a retained file or another user's skill/config on your own to force setup through. The one exception is a record that a refusal names: where Codebook can neither finish nor undo an interrupted step by itself, or cannot read a record, the refusal names what to delete and ends with how to start over, for example `To start over, delete <record path>, then run Codebook: Set Up AI Chat again.` If catalog cleanup alone failed after skill removal, the warning leads with the cause and ends `The managed Cursor skill itself was removed; Codebook left the Cursor MCP config in place and deleted no unverified file. When the cause above is resolved, run Codebook: Remove Managed Cursor Skill again: it goes on with the config.` Resolve that cause, then run **Codebook: Remove Managed Cursor Skill** again: it retires the empty config Codebook created and leaves an existing or changed config in place.

**Cursor setup needs a file system with hard links.** Codebook puts its Cursor skill (`~/.cursor/skills/codebook/SKILL.md`) and the empty `~/.cursor/mcp.json` it creates in place with a hard link, because that is the one call that never replaces a file that is already there. On a home folder whose file system has no hard links (exFAT, FAT, some network shares) **Codebook: Set Up AI Chat** cannot finish in Cursor. It ends with a sentence that names the path and the file system's code, for example "Cursor skill could not be installed: the file system refused to put Codebook's new file in place as <path> (EPERM). No existing file was changed. Check that this folder allows new files and hard links, then run Codebook: Set Up AI Chat again.", and a setup that had no skill of Codebook's to replace changes no file. An update of a skill Codebook installed earlier has moved that skill aside before the link is tried; when the link is refused then, the previous skill stays under the name it was moved to, and the sentence says `Codebook's previous skill is kept as <kept path>; move it back to <path> to go on using it.` where the other says `No existing file was changed.` Codebook does not place the file another way. VS Code installs no such file and is not affected.

**Cursor setup does not go below a link.** When `~/.cursor`, `~/.cursor/skills` or `~/.cursor/skills/codebook` is a link (a home folder whose settings are linked from elsewhere), Codebook refuses the setup, the reconnect and the removal, and leaves the link and what it points to as they are. The refusal names the path and the step, for example `Codebook will not follow a non-directory skill path: /home/user/.cursor/skills. That path is a link, and Codebook leaves what it points to as it is. Put the folder it points to in the link's place, or remove the link, then run Codebook: Set Up AI Chat again.` Either step ends the link at `~/.cursor` and at `~/.cursor/skills`. At `~/.cursor/skills/codebook` the step reads `Remove the link or give it another name`, because what that link points to may be a skill of your own.

These are development-candidate instructions. Ordinary-install development trials have exercised slash discovery and AI-owned Codebook calls, but the exact final candidate, both-host restart, unavailable-state guidance and full product acceptance still require the checks in [G12](https://github.com/laststance/codebook/blob/main/PRODUCT_GOAL.md#bundled-thin-skill-and-explicit-chat-entry) and [Cycle 0019](https://github.com/laststance/codebook/blob/main/docs/cycles/0019-bundled-codebook-skill.md). ## Save learning replay

During a Codebook explanation, the editor's bottom status bar shows **Recording explanation · Save learning replay**. Clicking it (or running **Codebook: Save Learning Replay**) finishes that Codebook run and waits for the saved recording and matching source/explanation context. It does not repeat application inputs or mark anything understood.

- **Saving learning…**: finalization is pending; repeated clicks share the same operation.
- **Learning saved · Open replay**: the saved evidence includes the summary, sequence and captured debugger history. Click to open that saved replay.
- **Learning partially saved · Open replay**: available evidence is retained. The tooltip identifies missing summary/history or incomplete execution/capture evidence; inspect the retained replay before relying on it.
- **Learning save failed · Retry**: completion was not verified. The tooltip reports the failure; retry after resolving it. Existing saved material remains retained.

The status bar remains available while reading standard chat or native source/debugger panes. New agent annotations invalidate the earlier saved label until saved again. This development implementation still needs installed-host validation in both editors; its unit tests do not establish full product acceptance.

Replace it with a real folder (if it is a link to your Wiki’s folder, move its files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then press Update LLM Wiki again.`) or when a folder above it is one (`Update not started (<time>): the Wiki folder’s path in the project passes through a link or a file (<path>), and the publisher writes only into the project’s own folders, so nothing was written. Replace it with a real folder (if it is a link to a folder of yours, move that folder’s files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project, then press Update LLM Wiki again.`). The publisher refuses it too and writes nothing (`The Wiki folder <path> is a link, a file or a folder that leads out of the project. Nothing was written. Replace it with a real folder, or choose an output folder outside the project.` for the Wiki folder itself, and `The Wiki output lies inside the project, but its path passes through a link or an entry that is no folder of the project’s own: <path>. Nothing was written. Replace it with a real folder, or choose an output folder outside the project.` for a folder above it). **Codebook: Open DeepWiki in Browser** and the Wiki reader read nothing through it (`The Wiki folder <folder> is a link or a file, or leads out of the project. Codebook reads no Wiki through it. Replace it with a real folder (if it is a link to your Wiki’s folder, move its files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project`, and for a folder above it `The Wiki folder <folder> lies behind a link or a file in the project (<path>). Codebook reads no Wiki through it. Replace it with a real folder (if it is a link to a folder of yours, move that folder’s files into the new folder), or set codebook.wikiOutputDirectory to a folder outside the project`; the editor's notice adds `. Generate it through /codebook in this project, then retry.`). An output folder outside the project stays your choice, and a link on its path there is followed. One limit: on Windows an output folder whose last name is written as a short name (`WIKI~1`) is taken for no folder of its own and gets the update's sentence of a Wiki folder that is itself a link or a file; write the folder's long name in `codebook.wikiOutputDirectory`.

While an update runs, its window keeps a marker file beside the output folder, `<folder>.update-run.json` (`.codebook/wiki.update-run.json` unless the setting names another folder), so that a second editor window on the same project does not start a second update. That window's start is refused with `Another editor window is updating this Wiki (<editor>, started <time>). Wait for it to finish, then press Update LLM Wiki again.` Two shorter refusals name no run. `Another editor window is starting an update of this Wiki. Wait a moment and try again.` is shown while another window is writing its marker (a marker file without content that is younger than 2 seconds). `Another editor window is starting or ending an update of this Wiki. Wait a moment and try again.` is shown while another window holds the claim under which a marker is removed or replaced, and a leftover marker is in the way. The marker usually lies in your project folder, so it holds nothing that names the computer, its host or its user in clear: it records the process id of the window's extension host and when that process began, a random id of the window, the editor, the time the run started, the kernel's boot id on Linux, and two digests that stand for the machine. A digest is a pseudonym and no secret: a commit of the file publishes it, and the digest of a common host name can be found by trying names. When the run ends, its window removes the marker; after a stopped VS Code watch the file stays as that window's note that the chat may still publish, and the window removes it later or the next update does.

A marker of a running update that a killed editor left on this machine does not refuse a start: a window of this build judges a marker by the start of its owner's process, so the marker counts as nobody's when that process is gone and also when another process has its process id since, and the next start removes it. A marker whose owner cannot be judged here counts until its run's longest time has passed at the latest: 21 minutes after the run began for Cursor and 21 minutes 30 seconds for VS Code (the 15 minutes of a run, in VS Code after the 30 seconds for the chat's first answer, then 1 minute, then the 5 minutes by which two clocks may differ). That is a marker written on another computer (a project folder shared between machines), in another system or another pid namespace of this computer (a Windows window beside a WSL window, another WSL distribution, a container), where its process id means another process, by a window that could not read its own process start, or by a Linux window that could not read its own pid namespace (such a window also judges no other window's marker by its process). A running update's marker of this computer that names another boot of the Linux kernel than the running one is nobody's all the same. A marker of 0.2.29.0 counts that long when a process still has its process id. [What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits.

A stopped VS Code watch's reservation describes a chat that can still publish. If the editor could not store that watch's record, Codebook keeps the reservation when the window closes or reloads. Another window, including the reloaded one, still waits until 15 minutes after the watch ended, also when the former extension host's process is gone. Stop that chat, then choose Update anyway if Codebook still waits for it; a publish the reader recognizes ends the wait sooner.

For tools: `GET <reader>/api/update-status` answers the current state as JSON (`Cache-Control: no-store`). `state` is one of `idle`, `running`, `succeeded`, `already-current`, `failed`, `cancelled`, `timed-out` or `conflict`; only `running` is not final. An `already-current` answer carries `addedFilesUnchecked: true` when the folder has no Git repository, so only the indexed sources were compared. Any other method answers `405` with `Allow: GET`.

## Build and verify a package

Package builds require a POSIX host (macOS or Linux); Windows builds are rejected before launching tools because the cleanup contract uses owned process groups. Maintainers use **Node 24.21.0** and the integrity-pinned **pnpm 12.4.2** in `package.json`. Installed-editor support remains the separately validated macOS matrix above. From the repository root:

```sh
pnpm --dir extension install --frozen-lockfile
pnpm --dir extension package
pnpm --dir extension package:check "$PWD/artifacts/packages/codebook-0.2.30.vsix"
```

The package command checks pnpm, clears only the extension compiler output, rebuilds, bundles production modules and stages an explicit file allowlist. Test/application fixtures and experimental dependencies are rejected. The independent checker validates archive entries, hashes, manifests and dependency notices before accepting the VSIX.

The VSIX includes `package-manifest.json` with file hashes, captured dependency/input identity, the running Node/pnpm/esbuild versions and the resolved extension TypeScript/vsce package versions, plus `dist/build.json` with source revision, dirty state and source hashes. `THIRD_PARTY_NOTICES.md` links the bundled dependency licenses. The separate check command verifies archive structure and metadata without executing supplied extension code; its self-consistency checks are not a publisher signature. The build additionally loads its own verified artifact in an unrelated temporary directory without repository dependencies. Normal installed activation and native workflow evidence are separate checks.

Archive checking and the reported SHA-256 use the same captured bytes. The checker rejects archives larger than 64 MiB, more than 2,048 entries, or more than 64 MiB of declared expanded content. Each package subprocess has a three-minute timeout and an 8 MiB limit for each output channel. The runner terminates its owned process group and waits up to five additional seconds for cleanup before returning. A failure to confirm cleanup rejects the build; combined failures retain the original error code/signal alongside the cleanup error. Failures preserve the previous VSIX. SIGINT/SIGTERM/SIGHUP/SIGQUIT during a package command reject with an interruption error after retiring its group, allowing the caller to remove its stage before the CLI exits nonzero. Existing caller signal handlers remain installed. Signal ownership ends when that command and its cleanup settle. A first or later signal during outer bundling, staging, verification or publication can terminate the process and leave scratch; transaction-wide cancellation is not promised. SIGKILL, immediate termination by a caller handler and independently detached descendants are outside this cleanup contract. Duplicate dependency-notice paths are rejected before their content is hashed again.

Local builds can record a dirty source tree; CI and accepted validation candidates require clean provenance. Clean means every selected source, fixture, script, patch and listed package/configuration input matches the raw bytes stored by its recorded Git revision. Ignored additions, index-hidden edits/deletions and clean/smudge transformations that change selected bytes remain dirty even if `git status` appears clean. Ambient `GIT_*` overrides and replacement refs cannot redefine that identity; provenance reads disable Git's optional index writes. Clean source identity does not attest that pre-existing `node_modules` or tool binaries match the lockfile and patch bytes. Run the frozen installs above before building an accepted candidate; CI repeats those installs and the package records the dependency bytes actually bundled. The inventory/checker accepts SHA-1 and SHA-256 Git revision formats; this does not establish a full build or native installation from a SHA-256 repository.

The private VSIX intentionally includes relative source/test paths and hashes in its build metadata. Those inventories are visible to anyone receiving the archive. Review or minimize that metadata before any public Marketplace/Open VSX distribution.

CI runs the product/runtime tests and real packaging/failure tests before uploading only the VSIX, build receipt, verification receipt and checksum, with clean provenance required. Native recordings and connection descriptors stay outside distribution. Workflow artifacts expire after 14 days; preserve any artifact needed for later acceptance together with its checksum in the private evidence store. For local regression testing, build the extension, run `node --test extension/dist/tests/*.test.js`, then run `pnpm --dir extension test:package`. Run packaging after runtime tests finish because its integration test cleans shared compiler outputs.

## Learn this repository

Run **Codebook: Open Repository Wiki** and connect your external MCP agent. Ask it to explain the selected repository with cited articles and relationships. Source-only authoring requires a trusted local workspace at its Git working-tree root; it does not require Chrome, a debugger or a runtime adapter for that repository.

1. Read `codebook_status.repository` and `codebook://help/repository`. Call `codebook_sources` with the current `instanceId` and follow `nextCursor`. A changed tracked-file set requires fresh discovery.
2. Call `codebook_source` for eligible tracked paths. Each result contains the path, the SHA-256 of the file's full bytes, a line count and `numberedText`: the source's lines, each after its one-based number and a tab. The lines are answered once; since API 1.7 the result has no `text` beside them. Take the line of every citation and every stop from `numberedText` instead of counting lines. Citations use that path/hash and inclusive `startLine`/`endLine`; they are checked again before publication. A book's cited source read through `codebook_read_resource` answers `numberedText` in place of its text as well; an MCP `resources/read` of that source's URI answers the exact text.
3. Author a complete plain-text document: a title, summary, uniquely identified article nodes with sections and citations, and relationships between existing nodes. Relationships describe source interpretation. They do not establish observed runtime order.
4. Call `codebook_publish_book` with a stable `bookId`, intent `key`, `expectedRevision: 0` for the first version, and the document. Later complete revisions use the current revision as `expectedRevision`. Reuse the identical key and input after response loss: the original immutable receipt remains recoverable after source changes. A different payload under that key is a conflict.
5. Read the returned book URI, then explicitly call `codebook_open_book` with its exact book/revision/node and optional citation index. Publication does not navigate or mark understanding. A cold reader opens the retained source in a read-only native editor beside the article. When the Wiki is already open, the agent's article request preserves the learner's chat or file input and returns the prepared immutable source URI; a focused primary file stays in place until the learner selects the Wiki and its cited source appears. **Open verified current file** is a separate action and requires matching current bytes.

Articles provide continuous prose, a contents menu, citation controls and source-derived relationships. Below 800 CSS pixels, the article occupies one column and relationships follow it. A newer publication offers **Load latest** while preserving the version being read. Selecting another article or citation opens that exact retained context; reopening restores its book, revision, article, citation, reading section and focus. Missing retained revisions are errors, with an explicit retry path.

The lowercase **understand** checkbox records only the learner's explicit decision. Its identity includes every unique citation's path, full hash and inclusive line range. Reordering or repeating identical citations, or changing only prose, retains the decision. Changing a secondary citation or range requires a new understanding decision. Current-file drift shows **Review needed** while retaining the earlier decision and captured source. Reading, publishing, execution and agent explanations never mark understanding.

Optional observation links must identify an exact saved study, observation and source hash. The store binds and verifies the saved facts; a runtime `learningItemId` alias additionally requires a matching linked observation for the article's primary source. Omit that alias for articles without runtime evidence. An existing article keeps its original learning identity across revisions; adding later observations does not require changing that identity. **View observation** opens saved evidence; **View recording** seeks its verified recorded time while paused. A missing recording disables only its recording link. **Return to Wiki** restores the retained article and reading position without rerunning the application. Partial studies stay labeled partial; source-only articles do not imply runtime support for the repository.

Evidence navigation and explicit **Open Study Workspace** preserve the current visibility of the outline and timeline panels. Hide those panels when more editor area is needed; the Study pane retains saved-moment controls and a **Show learning outline** action. This visibility behavior alone does not guarantee a readable three-pane grid in a compact window at high zoom. Returning to Wiki switches a layout only while Codebook still owns it; manual group moves, sizes and zoom-induced changes are preserved. Use **Restore Study workspace layout** for an explicit reset after changing the available editor area, and heed its error if the editor cannot retain the requested proportions.

Source discovery excludes hidden paths, dependency/build directories, lockfiles, secret/key filenames, symlinks and unsupported extensions. It is not a secret-content detector. Reads are bounded to regular tracked UTF-8 files: 5,000 tracked names, 100 names per page, 256 KiB per source and 32 sources per revision. Publication accepts at most 1 MiB of document JSON, 64 articles, 128 relationships, 12 sections per article and 8 citations/observation links per article. Retention is bounded to 64 books, 20 revisions per book, 4 MiB per revision and 8 MiB per book, without automatic eviction. Capacity, corruption, changed source and concurrent-revision failures preserve existing data.

```sh

import { readFile } from 'node:fs/promises';
import { z } from 'zod';
import { StudyClient, connectionSchema } from './dist/client.js';
import { repositorySourceSchema } from './dist/repositorySchemas.js';

const connectionPath = process.env.CODEBOOK_CONNECTION;
const sourcePath = process.env.CODEBOOK_SOURCE;
if (!connectionPath || !sourcePath) throw new Error('Set CODEBOOK_CONNECTION and CODEBOOK_SOURCE.');
const connection = connectionSchema.parse(JSON.parse(await readFile(connectionPath, 'utf8')));
const agent = await StudyClient.connect(connection);
try {
  await agent.discover();
  const source = await agent.tool('codebook_source', {
    instanceId: connection.instanceId, path: sourcePath,
  }, repositorySourceSchema.omit({ text: true }).extend({
    instanceId: z.uuid(), numberedText: z.string(),
  }));
  console.log(JSON.stringify(source, null, 2));
} finally {
  await agent.close();
}
NODE
```

## Recorded walkthroughs

Recording starts before a configured repository run acquires its application. Saved films open independently of live execution and retain original source/interpretation timing. Missing frames or source context remain explicit. Historical files in retired formats are preserved on disk and listed as unavailable; they cannot start an application or be silently converted into repository evidence.

Opening saved learning starts a read-only **Codebook · Recorded learning** debug session: the editor's own debugger shows the recorded source, scopes and call stack of the selected moment. Once native Run and Debug receives a recorded stop, the moment waits up to one second for it to load the stop's values. If Variables is collapsed or hidden, or another stopped session is selected, the moment still appears and Study shows the hint `Recorded values for this moment are not loaded yet. Show Variables opens Run and Debug and expands them; if the first scope stays closed, expand it. If Call Stack lists several sessions, select “Codebook · Recorded learning” first.` with a **Show Variables** button below it. One press opens Run and Debug, focuses Variables and expands its first scope, which lists the recorded values; a host without a command for it gets `Open Run and Debug and expand Variables to see the recorded values.` instead. Later moments do not wait again until values load; the hint and the button then clear. Ending the **Codebook · Recorded learning** session or closing the reader also clears it. Unrecorded gaps, stops without recorded scopes and stops whose only Variables group is the recording-limitations note appear at once with no hint. Saved Node test stops show the same hint and button beside their position. A Node stop is labelled **captured source unavailable** only when its captured source does not match the stop; ending the session, opening a recording or reopening the reader no longer adds that label. Cursor lists the scopes of a collapsed Variables without loading values, which is why the hint names the first scope.

A slow start does not fail a replay. Loading a recording and starting or retiring the historical session do not count against the five-second paint bound; that bound applies to each frame's painting, and a presentation that never reaches painting ends after 23 seconds. If the editor needs more than five seconds to start the historical session, the moment that waited for it fails, and the session is adopted when its start completes: the next moment is presented without reopening the recording. A session you stopped meanwhile is not adopted. If the editor does not stop the historical session within five seconds, the session becomes unavailable and reopening the learning replay starts a new one. Closing the reader does not wait on the native debugger or on a frame that never paints beyond those bounds. It waits at most five seconds in all for its pending storage writes (a running study's final checkpoint, the saved replay position, the archive writes and the library queue); a write still pending then keeps running and the reader closes.

**Open replay** pressed while another window has the desktop focus waits up to 10 seconds for the Codebook work window to gain the focus and then opens the Learning summary. When the focus does not come, the replay is refused with `Focus the Codebook work window before reading the learning summary: another window kept the desktop focus for 10 s. Click in this editor window, then choose Open replay again.`, and the status bar's **Open replay** shows that reason as a notification (`Codebook could not open the learning replay: …`).

In Cursor the Learning summary opens in the primary side bar, because Cursor rejects the secondary side bar container an extension contributes; in VS Code it opens on the right and nothing is offered. Once per editor session, until you have taken the step in that workspace, Cursor shows the notification `Cursor opens the Codebook Learning summary in its primary side bar. To keep it on the right, move it once: choose "New Secondary Side Bar Entry" in the list that opens.` with the button **Move Learning Summary…**. Cursor removes an unanswered notification by itself, so the same step stays within reach as the title action **Codebook: Move Learning Summary…** of the Learning summary view and under that name in Cursor's Command Palette. Each opens the editor's own Move View list for the summary. When **Show Variables** opens Run and Debug in the side bar the summary shares, the offer reads `Run and Debug took the Learning summary's place in Cursor's side bar. Move the summary to the right once to keep both in view.`, with the same button, at most once per editor session.

Bounded installed development trials in VS Code 1.139.1 and Cursor 3.23.5 ([Cycle 0032](https://github.com/laststance/codebook/blob/main/docs/cycles/0032-inspection-hints.md)) observed the hint about one second after the native stop and its removal once values loaded. Trials in VS Code 1.140.0 and Cursor 3.23.10 ([Cycle 0033](https://github.com/laststance/codebook/blob/main/docs/cycles/0033-presentation-liveness.md)) observed that the first recording open after an editor start commits, and that both editors now keep the first Variables scope closed until it is expanded, after which the values load and the hint clears. In VS Code a saved Node stop showed the same hint, kept its position label after its session ended and could be inspected again. The foreign debug-session case is only partly verified (one running session in VS Code), and the saved Node stop is not verified in Cursor. This bounded development reader is not completion of the approved synchronized native-debugger time-travel replay. That remains an explicit implementation gap in the product state.

GET `/mcp` returns 405; this service provides JSON POST responses and polled resources, with no standalone notification stream. The pinned SDK client supports this. Idle transport sessions expire after five minutes; live application execution has its own deadline.

Run resources distinguish current control state from historical snapshot/source/PNG/explanation references. Snapshot reads never create live pause authority. Events are paged (50/page) with a next URI and explicit detail truncation. Runtime source resources are sealed TS/JS/map bytes; they remain readable after the application and debugger exit. Repository reads accept only validated relative paths within the selected tracked-source boundary. No API accepts executable JavaScript, shell commands, arbitrary filesystem access or editor command names.

Resource identity is validated after the MCP SDK's URL normalization. Safe dot-segment aliases can resolve to the same canonical resource; they do not bypass instance/study/hash checks. Clients should follow returned canonical URIs.

Limits: 8 MCP sessions (a ninth client replaces the least recently seen idle session, a session with no request in flight; `429` is answered only when all eight are busy), 32 concurrent HTTP requests, 1 MiB + 64 KiB HTTP envelopes (separate from the 1 MiB book-document cap), 8 KiB headers, 5 s body reads; 1 active/16 retained runs per instance, no history eviction (from 0.2.22, when all 16 are taken the oldest run that was refused at the study-library admission, or whose saved study you deleted, gives up its place; such a run holds no history); an explanation budget of 32 keys/run (a key Codebook already accepted answers its receipt again, and a new key is refused once the budget is spent), 8,192 characters and up to 10 distinct captured paths; PNG ≤8 MiB. Configured runtime source resources allow TypeScript ≤256 KiB, the selected JavaScript module ≤8 MiB and its source map ≤16 MiB; build discovery reads selected-route webpack chunks ≤32 MiB each, ≤128 MiB total, ≤2,048 candidates and ≤30 seconds. Discovery and `codebook://help/repository-browser` expose the source and chunk limits through `profile.limits`. Evidence buffering is capped at 10,000 events / 4 MiB retained event bytes / 16 MiB pending writes. Overflow is an explicit failed run followed by owned cleanup.

### What a lock or an update marker cannot tell

Two files keep editor windows from writing at the same time: `writer.lock` in each private storage folder (the learning storage, the Cursor skill and its catalog) and the marker of a running Wiki update beside the Wiki folder ([LLM Wiki: open and update](#llm-wiki-open-and-update)). Between windows of this build a lock, a marker and the claim a window holds for the moment in which it removes or replaces one of them are judged by the start of the owner's process. The limits:

- **A window of 0.2.29.0 on the same storage or project folder.** That window writes and judges as 0.2.29.0 did, so beside it the guarantees are those of 0.2.29.0. Its lock, its marker and its claim name no process start: this build judges such a lock by its process id and its boot, such a marker by its process id alone, and removes such a claim once it is 60 seconds old, or sooner when the claim names this machine and no process has its process id. The older window judges the files of this build in its own way: a lock or a marker whose process id went to another process stays for it, where the boot is a computed time (macOS, Windows) a clock set forward by more than a minute while a lock is held can make it take over that lock although its writer still runs, it removes a claim after 60 seconds although the claim's window still runs, it creates its marker in place, so that the file is empty for the time of one write, when it finds no marker under its claim it removes the marker another window has just written, and it follows a link at the path of the marker's claim (`<marker>.takeover`, which a cloned repository can carry): each time it asks for that claim it deletes the files directly in the folder the link leads to that were last changed more than 60 seconds ago. Update every window to leave these limits behind.
- **Another host, another system.** A lock or a marker written on another computer is not judged by a process here, and neither is a marker, or a lock that records its writer's process start, written by an editor of another system of this computer (a Windows window beside a WSL window), because its process id means another process there. Such a lock stays until you move it away; such a marker counts until its run's longest time has passed at the latest, and a claim on it for 60 seconds. For a marker and its claim, another pid namespace of this computer (another WSL distribution, a container) is such a system too, and so are a window that could not read its own process start and a Linux window that could not read its own pid namespace.
- **Two computers that share an editor's machine id.** The editor keeps its machine id in its user data folder, so two computers that share a home folder (a network home, a copied profile) have the same one. A lock, a marker or a recording that names this machine id under another host name counts as this computer's only when it also names the boot that is running: the kernel's boot id on Linux, elsewhere the time the computer started, within a minute. Otherwise it counts as another computer's: such a lock stays until you move it away, and before Delete moves such a recording it asks you. The same holds for a window that was killed before a restart, on a computer whose host name changed since (a Mac takes it from the network). Two such computers without a kernel boot id (macOS, Windows) that started within the same minute look like one.
- **Two computers with one host name.** A marker names its machine by digests, and the digest of the host name is the one VS Code and Cursor on one computer share. Two computers with the same host name on one shared project folder therefore look like one machine to the marker: each judges the other's marker by its own processes and its own boot, and a second update can start beside a running one.
- **Clocks.** The marker's times allow the clocks of two windows, or one clock before and after a correction, to differ by 5 minutes. Computers whose clocks differ by more, a clock that moves by more during an update and a computer that sleeps for longer during one are not covered: a second update can start beside a running one.
- **A file system without hard links.** A lock or a marker is written beside its path and then linked into place, so it never exists without its content. Where the file system cannot link, the file is created in place and is empty for the time of one write. Another window takes an empty marker younger than 2 seconds for one that is being written and refuses its own start, which narrows that race without closing it.
- **A suspended window.** A window that is suspended in the instant between the check of its claim and its change of the marker can still remove or replace a marker that another window wrote meanwhile.
- **Systems observed.** The judgement by the process start was observed in editors on Linux, for the update marker: the marker of a killed window did not refuse the other editor's start. On macOS and in a Windows editor it has not been observed, for a lock or for a marker: tests cover it there, for Windows on a Windows runner and for macOS with a stand-in for the `ps` query.

### Saved learning capacity

**Codebook: Saved Study Limit** (`codebook.savedStudyLimit`) controls new study and recording admission for the opened workspace: 64 by default, configurable from 1 to 256 in ordinary editor Settings. Changes apply without restarting. When full, raise this setting or delete a saved study (below) before starting a new recording; use **Retry storage / refresh** to retry an existing study checkpoint. From 0.2.21, a configured run started while the study library is already full is refused before the application receives any input: the run ends with `PREREQUISITE_MISSING`. A recording that never started cannot reconstruct missing video afterward.

From 0.2.22 the refusal names what you can do at your limit:

- below 256: `Study library is full. Increase Codebook: Saved Study Limit (codebook.savedStudyLimit) in Settings, or delete a saved study from Saved studies in the Study workspace, before starting another run. Only the learner can do either; an editor agent cannot. Existing learning was kept.`
- at 256: `Study library is full at its maximum of 256 saved studies. Delete a saved study from Saved studies in the Study workspace before starting another run. Only the learner can delete a saved study; an editor agent cannot. Existing learning was kept.`

The messages for a study that cannot be saved and for a recording that cannot start follow the same pattern (`…then retry storage.`, `Recording library is full…delete a saved study that has a recording…`). A refused run is not saved later either: it leaves no study behind, the Study pane shows `The last run did not start: <message>` without offering **Retry storage / refresh** for it, and its run resource reports its history as unavailable. A limit setting that is not an integer from 1 to 256 also ends a run with `PREREQUISITE_MISSING` and `Set Codebook: Saved Study Limit (codebook.savedStudyLimit) to an integer from 1 to 256. Existing learning was kept.` The check at the start of a run reserves nothing: when two editor windows of the same workspace each start a run for the last free place, both starts are accepted, and the study saved second is refused at its save with the `…then retry storage.` message; raise the limit or delete a saved study, then use **Retry storage / refresh**. The start of a Node test is different: it takes the storage lock (`writer.lock` in the learning storage) and reserves its history under it, so of two windows that start a test for the last free place one is refused with `Saved study storage is full. Increase Codebook: Saved Study Limit (codebook.savedStudyLimit) before starting another test; existing history was kept.` A start that meets the lock while another window holds it, or a lock that stays, is refused with the storage lock's sentence, which [Delete a saved study](#delete-a-saved-study) quotes and explains; nothing was written then, and the test was not started.

#### Delete a saved study

Only you remove saved material; an agent has no tool for it. In the Study pane, **Saved studies** lists every saved study of the opened workspace, newest first. Choose one and press **Delete saved study…**. A native dialog names the study and asks **Move this saved study to the Trash?**; **Move to Trash** moves its archive, its catalog file, any saved recording and the raw evidence of its run (the screenshots, the sealed source and the event journal in the extension's agent storage) to the system Trash (Recycle Bin on Windows), where you can restore them with the operating system. Codebook has no permanent delete. Afterwards the pane shows a line such as `Saved study moved to the Trash. The library now holds 63 of 64 saved studies.`; when the removal made room for a run that was refused, the line ends with `Ask your editor agent to start the run again.`

- When the deleted study was the one shown, the pane shows the next older study (the next newer one when none is older).
- What you marked as understood is kept. A Repository Wiki link to the removed study shows as unavailable.
- The raw evidence stays in place when the run belongs to another Codebook window that may still be open; the line then ends with `The run's raw evidence was left in place because its Codebook window may still be open.` Evidence of runs that were never saved as a study is not touched.
- After the removal an agent that reads the run's evidence (`manifest`, `events`, observations, explanations) or adds an explanation gets `EVIDENCE_UNAVAILABLE` with `The learner moved this saved study to the Trash.`; the run resource itself still answers and names the same reason.
- When a study's files were removed by hand (the only way in a window without a Trash) or the study was deleted in another Codebook window, the next **Retry storage / refresh** finds its archive gone. An agent that then reads a run of this window whose study that was, or adds an explanation to it, gets `EVIDENCE_UNAVAILABLE` with `The archive of this run's saved study is no longer in the study library: its files were removed by hand or by another Codebook window.`; the run resource still answers and names the same reason.
- The button says why it cannot be used: `Wait for the chosen saved study to open.`, `Choose a saved study to delete.`, `Node test histories cannot be deleted here yet.`, `Stop the run before deleting its study.` or `Choose Overview or Live to leave Recording before deleting this study.` (also while a recording is still opening).
- An entry that cannot be opened (an older format, a study whose catalog file is missing, or what is left of a study whose archive was removed) can still be chosen and deleted. For a study whose catalog checkpoint is missing or out of date the pane says `This saved study's catalog checkpoint is missing or out of date. Repair it, or delete the study.` and offers **Repair saved study** beside the delete button.
- What is left of a study whose archive was removed (its catalog file, or a recording that no editor of this computer still writes) stays in the list with `Archive missing; remaining files kept` in its label, so that the rest can be removed: **Delete saved study…** moves it to the Trash, and in a window without a Trash **Remove by hand** lists its files. A recording that names another computer is listed too, and so is one whose editor Codebook cannot tell from another program of this computer; for such a recording **Delete saved study…** asks first, as the next point says. Such an entry can be chosen and not opened, it has no **Repair saved study**, a reader that starts neither selects it nor shows it first, and it takes no place of the saved study limit. The finished recording of a run of this window whose archive could not be saved yet is listed with the same words; that study has not left the library, and **Retry storage / refresh** writes its archive.
- When a recording of the study may still be running on another computer, Codebook asks once more after **Move to Trash**: `This study's recording may still be running on another computer. Move the study to the Trash anyway?`, with the detail `Its recording was started on <host> at <start>. Codebook cannot tell from this computer whether an editor window still records it. If a window still records it, on that computer or on this one, the recording is lost. If none does, nothing is lost. Cancel keeps the study and its recording as they are.` **Move to Trash Anyway** moves the study with its recording; **Cancel** keeps both as they are. When the recording names this computer but Codebook cannot tell its editor from another program (the editor's process number now belongs to a program that started later, or to another user), the dialog reads `This study's recording may still be running in another editor window. Move the study to the Trash anyway?` and `Its recording was started on <host> at <start>. Codebook cannot tell whether an editor window of this computer still records it. If a window still records it, the recording is lost. If none does, nothing is lost. Cancel keeps the study and its recording as they are.` For a study with several such recordings the title begins `Some of this study's recordings may still be running` and names the places that apply (`on another computer`, `in another editor window`, or `on another computer or in another editor window`), and the detail names each host and start. Nothing moves while the dialog is open. If a recording of another computer appears, or another window opens Recording, before you answer, **Move to Trash Anyway** moves nothing and the line says why.
- When another editor window of this computer is still recording the study, nothing moves and the line reads `The saved study could not be moved to the Trash. Nothing was deleted. Another editor window is still recording this study. Stop its run in that window, then delete the study again.`
- The recording of a run that saved no study is listed in the same way, with `Archive missing; remaining files kept`, once no editor of this computer still writes it, and **Delete saved study…** moves it to the Trash. While a run of this computer may still write it, that run holds it and it is not listed.
- A study saved by a newer Codebook is listed and kept: `This study was saved by a newer Codebook and is kept as it is. Update the extension, then delete it there.`
- A window opened through the WSL remote has no Trash, so nothing is deleted there: the pane says `This window has no Trash, so Codebook cannot delete a saved study here. Choose a saved study, then open Remove by hand to list its files.`, and for a chosen study it offers **Remove by hand**, closed. Opening it asks for that study's files (`Listing this study's files…`) and lists them under `This window has no Trash, so Codebook cannot delete a saved study here. Remove these files by hand, then press Retry storage / refresh.`, with **Copy paths** and **Retry storage / refresh**. **Copy paths** answers `Copied 4 paths.` (the number of paths on the clipboard), or `Could not copy the paths. Select them in the list above and copy them by hand.` when the clipboard took nothing. When nothing is left to remove the pane says `No file of this study is left. Press Retry storage / refresh to update the list.` The notes and reasons of such a window name the removal by hand instead of a deletion, for example `Stop the run before removing its study's files by hand.`
- If the Trash refuses, the line starts with `The saved study could not be moved to the Trash. Nothing was deleted.` and names the cause: the study, its recording and its run are as they were, and the run can still be saved with **Save learning replay**. If only part of the study could be moved, the line says `The saved study was only partly moved to the Trash; delete it again to finish.` and the study stays listed; the same delete finishes the removal. If Codebook cannot look at a file again after the Trash rejected it, the line says `Codebook could not tell whether the saved study was moved to the Trash; delete it again to finish.` and names the cause; the same delete finishes the removal.
- While a study is being moved, it cannot be opened or played, **Save learning replay** for its run is refused with `Study archive is unavailable.`, and an agent's `codebook_explain` for that run answers `BUSY` with `The learner is deleting this run's saved study; wait for it to finish.`; the agent can repeat the call.
- A cause that names the storage lock (`Learning storage is locked by another writer or an interrupted session (lock file: <path>). No data changed; retry after resolving the lock.`, where `<path>` is the file `writer.lock` in the learning storage) means that another Codebook window is writing, or that a lock stays whose writer may still be alive: a process that still runs, a lock written on another host, a lock written by an editor of another system of this computer (a Windows window and a WSL window that reach the same file), or a file without a readable owner record. A lock whose process is gone on this machine (an editor that was killed) is taken over by the next write, by one window at a time, and causes no refusal. The lock records its writer's process id and when that process began, with the host name, two digests that stand for the machine and the boot, and a window of this build judges it by that start: a lock whose process id another process has since is taken over as well, because that process began at another time. For a lock that stays, make sure that no Codebook window on any host or system still writes to this storage, then move the named file away and retry ([What a lock or an update marker cannot tell](#what-a-lock-or-an-update-marker-cannot-tell) lists the limits). When the lock could not be released after every file had moved, the study is deleted and the line says so; the pane additionally shows `Learning storage lock could not be released after the removal: <cause>` among its errors, and later saves can be refused until the lock is resolved.
- When the next study cannot be arranged after a removal (for example while a presentation change is pending), the removal's line is shown all the same, no study is shown and the pane's errors name the reason; choose a study in **Saved studies** to continue.
- The delete button waits only while the entry you chose is opening. A choice the reader could not open (it names the reason among its errors) puts the list back on the study that is shown.
- A run the library refused can be started again with the same request once there is room: the agent repeats its `codebook_start` with the same key and a new run begins.
- Not covered yet: Node test histories, removing several studies at once, and a study whose run is still held by another window of the same workspace.

Existing studies, recordings and learner decisions are never evicted. Lowering the limit does not hide existing history or prevent updates to a previously admitted study. The fixed catalog ceiling is 256; per-recording frame/byte limits remain unchanged. Raising a count limit permits more disk use, not larger individual recordings.

### Recording capacity

Recordings retain the 50 ms sampling policy, with up to 12,100 frame entries, 512 MiB of unique PNG data, an 8 MiB journal and 544 MiB total storage per recording. These budgets accommodate ten minutes of the measured 720×640 animated application workload (roughly 33 KiB per frame), including up to eight source/debugger stops. They do not guarantee ten minutes for every image size or workload. Pending writes remain limited to 8 MiB; larger images, slow storage or exhausted budgets produce an explicit partial recording with a readable verified prefix. Existing recordings are not rewritten, and missing frames are never synthesized. Storage usage accumulates across saved recordings.
