## Candidate freeze and Stage 1: main-agent practical validation

Use the packaged, normally installed extension and published setup/operations as a paying customer would, in ordinary VS Code Copilot Chat and Cursor Agent with explicit `/codebook`. A development extension host is not acceptance evidence. Freeze source revision, VSIX/version/SHA-256, common skill body/version/hash, registration/setup and guide revisions, host/OS/chat/debugger/browser identities, target revisions, natural questions/objectives and observable criteria before results. Do not supply repository answers, correct stopping locations or expected variable-value lists to the chat. Record unknown identities honestly.

The main agent personally completes every required project/host/use-case row first. Open the actual target repository using ordinary onboarding, execute the actual processing relevant to the natural understanding question, stop at meaningful locations, inspect actual variables/arguments/state/call stacks through the native debugger, explain their source correspondence in standard chat, step and resume as needed. Save that explanation as learning replay with summary and sequence diagram; reopen it after runtime exit. Separately generate/update/open the project Wiki without runtime or replay prerequisites and follow its editor source links. Verify both features' ownership and independence; they need not be displayed together. Record setup effort and whether ordinary users can understand errors and follow documented recovery.

Do not rescue the flow with internal manual MCP calls, direct source fixes, developer-only operations, prepared stop/value answer keys or unpublished wiring. Publicly documented debugger configuration is permitted, with its steps and burden recorded. Read-only audit of evidence can verify a performed action; it cannot complete a missing product action. Preserve failures when development repairs are needed, then install a newly identified package and retest normally.

**Stage 2 cannot start until all nine projects, both hosts and every required use case pass Stage 1, and the complete candidate has all active capabilities and integrated feature evidence under version 10.** Development successes do not retrospectively become Stage 1 passes.

## Stage 2: nine independent junior-developer reviewers

Assign one fresh independent SubAgent per project, nine total. Each takes the role of a junior developer unfamiliar with that project's internal implementation. The owner explicitly authorizes these evaluators. Each reviewer personally operates and evaluates the assigned project in both hosts, with separate results and all required use cases (including tests plus Examples for libraries). This requires at least 18 project-host evaluations, and more use-case rows where applicable.

Give each reviewer only the frozen candidate, normal product documents, available target documentation, neutral natural understanding tasks and this protocol. Do not fork development history or provide main-agent model answers, internal workarounds, right stops/value lists or previous evaluations. Reviewers may inspect actual source and runtime to establish their own understanding. The main agent must not perform missing operations or finish interpretation for them. Serialize native operations when needed to avoid contention; results need not pass consecutively and one failure does not prevent independent evaluation of another ready target.

The central question is: does normal use make this project's code easier to understand without a material obstacle for a paying user, and can the reviewer justify that judgment with confidence at least 9/10? Confidence is subjective assurance about the evaluation, never a statistical success probability.

## Verdicts and evidence

Record NOT RUN for an unattempted row; attempted evaluations issue PASS, FAIL or BLOCKED. Distinguish product defects, external/editor/provider prerequisites, observer failures and missing evidence. BLOCKED is not PASS. Every Stage 2 report supplies:

- Project and pinned revision; source/build revision, extension version and VSIX SHA-256; host/version and relevant dependencies; bundled and actually loaded skill identities; public setup/connection identity.
- Questions/objectives, actual operations, setup and prerequisites, timestamps, host order and assistance.
- The actual processing followed, pause identities, observed values/state/arguments/call stacks and source/runtime correspondence.
- The junior's own-word explanation of what was learned and evidence establishing that understanding's correctness against source and execution.
- Learning save/replay with synchronized video/source/native-debugger history, repeated backward/forward seeking, summary/sequence diagram and learner-owned test progress, independent Wiki/update/source links and feature-screen results with stable sanitized evidence references.
- Stuck points, support needed, misleading explanations, errors, unverified items, videos/inspected frames and cleanup.
- Separate host/use-case PASS / FAIL / BLOCKED, confidence score and specific supporting reasons, plus project verdict and independence attestation.

A score alone never passes. An unexecuted mandatory use case, material source/behavior mismatch, indispensable developer-only assistance, or important unknown prevents PASS regardless of confidence. Every required Stage 2 assessment must PASS with evidence-grounded confidence >=9/10. All nine projects, both hosts and all required use cases must satisfy this. The main agent checks completeness but cannot rewrite a reviewer's adverse verdict. Keep implementation, development checks, Stage 1, independent Stage 2, package/distribution verification and owner acceptance distinct.

## Retesting and final artifact validity

There is no consecutive-pass counter and no reset to reviewer 1. Preserve failed attempts and explanations of fixes; retest the failed or affected target/host/use cases. Any extension, common skill, registration/setup or connection-path change requires a recorded impact assessment against existing passes. Changes affecting shared execution, recording or explanation require retesting all affected targets. An unaffected conclusion also needs explicit technical grounds; do not infer it from unchanged version labels or test counts.

Maintain an append-only attempt ledger and a validity map linking each final PASS to the final fixed distributed VSIX, skill and setup identities. Record old/new hashes, changed paths/mechanisms, affected rows, regression evidence and any justified byte-equivalent/unaffected carry-forward. Never aggregate incompatible implementation versions into a claimed final pass. Reviewer fixes must be evaluated by the assigned independent reviewer, not completed by the main agent on their behalf. Withhold prior answers/verdicts from neutral evaluation packets.

Final closure requires all valid Stage 1 and Stage 2 rows, complete active-capability/integrated feature evidence, verified distribution artifact and Raphtalia's separately recorded acceptance. A subagent cannot provide the owner's acceptance.
