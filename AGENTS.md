## Where things live

- **The cycle Issue** (label `cycle`, title `Cycle NNNN: <outcome>`) holds the state. Its body has four sections: Outcome, Tasks, Owner decisions, Next action. Tasks are a numbered checklist, one line each: source, defect, what closes it. A closed task ends with "fixed in <sha>" or "evidence: <one line>". A finding found during a bug-fix cycle becomes one more task. The agent edits the body when the state changes. When the body nears GitHub's limit of 65,536 characters, the list goes on in one pinned comment.
- **The pull request** holds the results (gate, CI, a summary of the native QA) and a non-closing reference to the Issue. No close, fix or resolve word comes right before `#N`: `.claude/settings.json` runs `extension/scripts/refuse-closing-keywords.mjs` before each Bash command and refuses pull request text (`gh pr create`, `edit` or `merge`; `gstack-post pr-body`, `pr-create` or `pr-title`) that puts one before an Issue reference, naming its line; `CODEBOOK_ALLOW_CLOSING_KEYWORD=1` before the command allows a deliberate closing reference.
- **The Issue's closing comment** holds the outcome and every carried defect; the next bug-fix cycle's Issue copies that list.
- **CHANGELOG.md** says what each version changes for users.
- **The tag `docs-archive-2026-10-20`** keeps every record and document removed here.

Before work they govern, read the archived [behavioral design](https://github.com/laststance/codebook/blob/docs-archive-2026-10-20/docs/designs/codebook.md) (live, capture, replay, runtime, storage, evidence ownership, cross-feature architecture), [UI state and interaction review](https://github.com/laststance/codebook/blob/docs-archive-2026-10-20/docs/plans/cycle-0029-product-design.md) (UI implementation, visual verification), [G12 bundled skill plan](https://github.com/laststance/codebook/blob/docs-archive-2026-10-20/docs/plans/bundled-codebook-skill.md) (shared skill, onboarding) and [Wiki generation skill plan](https://github.com/laststance/codebook/blob/docs-archive-2026-10-20/docs/plans/deepwiki-generation-skill.md) (Wiki generation, update). Other records, prompts and external references: only when needed. Bring relevant GStack cache findings into the Issue; never leave needed evidence only in chat or a cache.

## Cycle rule

Every carried defect is fixed in the next cycle. The rule is absolute: no planning choice, review outcome or skill default overrides it, so that a feature cycle starts clean.

- A **feature cycle** builds an increment of the final product. It starts only when nothing is carried into it, planned from the final product alone (`/spec` and the plan reviews, from PRODUCT_GOAL.md and the gap audit). Every defect it leaves unfixed is carried.
- A **bug-fix cycle** follows any cycle that left a defect and fixes those defects, nothing else. Its Issue holds every one as a task (source: cycle and finding label; the fix or evidence that closes it; the test that fails without the fix), with no increment and nothing selected, dropped or reduced. It carries nothing: every defect found in it (implementation, review, delegated review, native trial, audit) is fixed in it. It closes when every carried and found defect is closed; a feature cycle follows.
- A defect closes by a fix with a test that fails without it, or by recorded evidence that it is not a defect or no longer applies.
- Carried defects live in the bug-fix cycle's Issue, as tasks. A TODOS file, backlog or ledger of them is forbidden: a list that only records lets the work end at the recording. Later candidate increments are at most a short list, never holding a carried defect.
- In a feature cycle's delivery a critical finding is fixed before the merge and every other finding (review, delegated review, native trial, audit) is carried. In a bug-fix cycle's delivery every finding is fixed before the merge.

## Working loop

Goal and visual target → gap audit → one observable increment → implementation and proof → updated gaps. One active cycle, in its authorized phase.

1. **Audit** (the Issue is the gap ledger): every [acceptance map](PRODUCT_GOAL.md#product-acceptance-map) row at a new cycle, a goal or design change or an unassessed source change; else verify the baseline and changed paths, inspect affected rows, justify carrying the rest (a docs-only commit may keep the product-source baseline, said so). Per row, from source and evidence: implementation (match, concrete mismatch, or UNKNOWN plus the next inspection; an existing file, symbol or specification proves no behavior), proof (result, host, OS, identity, level, link; absent or stale is unverified; a source mismatch and missing runtime evidence are separate gaps), next action (a change or bounded experiment plus its verifying observation; UNKNOWN means investigate, never implemented or absent). Gate: all rows and active goals covered, baseline and affected IDs recorded; a read receipt, goal-link list, linked goal ID or old PASS proves nothing.
2. **Select** the smallest connected behavior or bounded experiment that closes a gap or settles the highest-impact unknown that could invalidate later work; core-experience blockers before polish; plan only that. Inspect the existing code, then freeze in the Issue: AC IDs (primary, dependency, regression), the gap and why now; starting action → expected result, failure behavior, modules, falsifying observation; procedure, target, host, evidence level, where the result is kept. A changed assumption is a new expectation version; keep old attempts. Gate: the action follows from the audit and has a checkable outcome. An open product gap does not override a documentation-only assignment. Repeated inconclusive attempts need a smaller question or a new hypothesis, never a silent loss of required behavior.
3. **Prove** the normal user entry through its result, recovery and preservation included; reuse modules and real package scripts; mechanism tests for logic, declared native checks for product claims. Record identities, actions, expected and actual results, artifacts and limits as NOT RUN, PARTIAL, FAIL or PASS; a listed command is no execution evidence. Gate: the evidence supports the outcome at its declared level. A failed or inconclusive experiment names the next hypothesis and proves nothing; code that resolves uncertainty is an experiment; increments need regression evidence; a plan grows only with its question; a build alone completes no live, replay or Wiki outcome.
4. **Reassess** changed and dependent rows and regressions; keep unaffected evidence only with an impact reason; compare gaps before and after, keeping missing implementation, missing proof and UNKNOWN; nothing advances because a checkbox, skill, image or PR is done. Keep, revise or replace the approach. Update the Issue with results and one executable next action; check that the route still reaches every goal and the next candidate hits the largest blocker. Gate: rows, checks and UI comparisons recorded; a fresh agent can recover product, gaps, proof, phase, failed approaches and next step from the repository and the Issue, never from chat (`/context-save` only speeds this up). Markdown gives an auditable procedure, not proof of comprehension.

## Delivery

The driving agent owns state, cycle selection and completion claims; GStack supplies workflows.

**Chain.** One bounded cycle at a time toward the complete product. After each merge, `/spec` (with the plan reviews the scope needs) writes the next cycle's Issue. Work on a `codex/` branch; keep existing edits; reuse a fitting checkout. Each cycle: review by the local CodeRabbit CLI and `open-code-review-delegate`, `/ship` as a PR, required CI, a separate exact-HEAD gate, then the merge as its own step with `--match-head-commit`. A large cycle may use up to three PRs (`cycle100-pt1`, `cycle100-pt2`, …), each passing reviews, CI and the gate alone, merged in order; the Issue closes after the last. Codex automatic review is off: no Codex cloud step. PR bodies carry no `@coderabbitai ignore` (owner, 2026-10-05).

**Delivery parameters.** The merge is a squash merge: `gh pr merge <n> --squash --match-head-commit <sha>`. `/ship`'s documentation candidate (`gstack-docs-candidate snapshot`) takes the kept documents as `--docs` roots: AGENTS.md, CHANGELOG.md, CLAUDE.md, PRODUCT_GOAL.md, README.md, `extension/README.md`, `extension/skills/codebook/SKILL.md` and the v9 PNG. CI packages the extension with `node extension/scripts/package.mjs --out artifacts/packages/codebook.vsix` and checks it with `node extension/scripts/check-package.mjs artifacts/packages/codebook.vsix` (`package.yml`). A release commit changes one test line besides the version files and CHANGELOG.md, the expected version in `extension/scripts/tests/package.test.mjs`; `/ship`'s Step 16 counts that edit as release metadata, not as a change to the reviewed tree.

**Background work.** `node extension/scripts/watch-background.mjs` (from the directory Claude Code started in, else with `--project <that directory>`) lists the current Claude Code session's background tasks and subagents (its `CLAUDE_CODE_SESSION_ID`), each with the time of its last output, and marks those silent for more than 20 minutes; a finished or stopped subagent is never marked, a shell's row stays marked after it ended (its task notification is the authority). Stop a review subagent that has written nothing for 20 minutes and dispatch it again on a narrower scope; dispatch a subagent that the API's safety filter stopped again at once, with the same brief, on the fallback model. While waiting longer than a few minutes, tell the owner what is awaited and since when.

**Ship review limit (owner, 2026-10-18).** After the installed `/ship`'s three fixing cycles, stop and report `converged:false`: no fourth cycle, no counter reset after a handoff, no round relabeled a repair; the no-carry rule does not waive this. An unconverged ship is no completed delivery. Only the owner starts a new invocation, with its own count. The owner's order for Cycle 0046's second invocation: if it also stops unconverged, its open findings become the next cycle's tasks and that cycle's PR holds only their fixes (Cycle 0047's delivery ended the same way).

**Skills.** Read each installed SKILL.md at invocation; this map guides and copies no workflow. Premise or final behavior: `/office-hours` or `/plan-ceo-review` (owner decision). Lasting API, MCP or integration change: `/plan-devex-review` (capability, error, lifecycle contract). Flow, layout, hierarchy, interaction: `/plan-design-review` (UX and state decisions). Architecture, concurrency, storage, meaningful code: `/plan-eng-review` after UX/API amendments (bounded implementation and test plan). Combined review on owner request: `/autoplan` (CEO → conditional Design → conditional DX → Eng). Unexplained failure: `/investigate` (root cause, new hypothesis). Working browser or webview flow: `/qa` or `/qa-only` (observed behavior, fixes). Implemented UI: `/design-review` (real visual and interaction evidence). Ready diff: `/review` (revision-bound findings, coverage limits). Releasable PR: `/ship` (actual commit, PR, checks). Merge or deploy: `/land-and-deploy` if available, else the established extension delivery. Changed public behavior: `/document-release`. Pause or handoff: `/context-save`, then `/context-restore`, reconciled with the repository and Issue. Ordinary coding is the agent's work; documentation-only changes need only the applicable reviews; a failed experiment may inform the next cycle before release. Browser QA, Reader DOM checks included, proves no native pixels, DAP targeting, MCP integration or installed VSIX behavior. Report a missing tool as missing coverage.

**Skills under the cycle rule** (each runs as installed). `/spec` plans a feature increment from PRODUCT_GOAL.md and the gap audit, or writes a bug-fix Issue from the previous closing comment: one task and acceptance criterion per carried defect, nothing ranked or selected. Plan reviews may change how a carried defect is fixed, never remove, merge away or defer one. In review steps (`/review`, `/ship`) a feature cycle answers non-critical findings Skip and applies no automatic fixes of informational findings; a bug-fix cycle answers none Skip. In `/ship`, the coverage audit's tests are committed; the plan completion audit counts an open bug-fix task NOT DONE and stops (no ship anyway, defer or drop); the TODOS step writes no TODOS.md; documentation-audit blockers are fixed before the commit. A test gap, deferral, non-blocking documentation debt or skill follow-up is carried in a feature cycle and fixed before the merge in a bug-fix cycle. A feature cycle's closing comment names every carried defect, and the bug-fix Issue comes before other work; a bug-fix cycle's states that nothing is carried, and `/spec` starts a feature cycle.

Claude Code CLI review stays owner-skipped and is no native chat acceptance.

**Status:** ready → planning → implementing → validating → closed, or blocked with its condition and unblocking action (say why work moves back). **Result:** pending, demonstrated, falsified, inconclusive. **Delivery:** not-applicable, local-only, committed, PR-open, merged, packaged, published, installed-verified. The three are independent.

**Closure.** Write any new owner rule into the required read it governs. Name the next cycle's kind; after a clean bug-fix cycle, at most one candidate increment. Run integrated checks once capabilities depend on each other. A shipping task stays open until its authorized gates finish.

**GitHub.** [laststance/codebook](https://github.com/laststance/codebook) is public: everything pushed, Issues and PRs included, is world-readable, a security defect before its fix too. Goal Issue [#1](https://github.com/laststance/codebook/issues/1) stays open until full acceptance and owner approval. Close a cycle Issue only for a demonstrated or falsified outcome with complete delivery; else keep non-closing references (an inconclusive investigation may stop with its outcome open). If GitHub is unreachable, keep the Issue edit pending. Tracking is authorized work; production deployment, publication and recurring automations need the user's authorization.
